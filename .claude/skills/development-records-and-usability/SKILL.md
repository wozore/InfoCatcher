# InfoCatcher 开发记录与可用性约束

本技能只适用于当前 InfoCatcher 项目。它与 `software-lifecycle-guard` 配合：先判断生命周期阶段和文件归属，再按本技能记录结果和计划。不要把本技能正文复制进项目文档。

## 1. 动手前：确认范围和记录位置

1. 先读取相关的 `开发计划.md`、`开发日志.md`，以及将要修改的代码/文档和适用的项目约定。
2. 判断任务属于需求、够用设计、编码测试、维护或后续环 C；遵守 `.claude/skills/software-lifecycle-guard/SKILL.md` 的阶段边界。
3. 将尚未完成的工作放入 `开发计划.md` 的对应任务或验收项。若任务很小，也至少确认它属于哪个现有计划项。
4. 不把“准备做”“建议做”“应该验证”写入开发日志的完成章节。
5. 如果任务改变了需求或架构边界，先更新对应的阶段文档，不用开发日志代替需求/设计文档。

## 2. 两份文档的硬边界

### 2.1 `开发日志.md`：只记录已经发生的结果

开发日志面向过去，记录可追溯的事实：

- 已实际修改的文件、模块、功能或文档；
- 实际执行的命令、测试、构建、部署或手动检查及其结果；
- 真实的提交、Actions Run、线上 URL、Issue 或用户反馈证据；
- 已知失败、降级、未覆盖范围和仍待验证的事实，但必须明确标记为“尚未验证”或“失败”，不能写成完成；
- 日期、冲刺、所属生命周期阶段和影响范围。

日志条目应回答：**实际做了什么？结果是什么？用什么证据知道？还缺什么证据？**

日志禁止：

- 把未来任务、方案备选、愿望或推测写成“已完成”；
- 代替 `开发计划.md` 维护活动任务清单；
- 在每次更新时重复整份计划或复制大量设计细节；
- 把“代码存在”当成“真实平台、线上页面或用户体验已经验证”。

推荐记录结构：

```markdown
## YYYY-MM-DD · 冲刺/任务

### 实际变更
- [x] 已完成的文件或行为变更（只写已发生事实）

### 验证结果
- `[x]` 命令/测试/运行结果及证据
- `[~]` 已实现但外部环境仍未验证的边界
- `[ ]` 本次未执行的验证（仅在说明范围时使用）

### 遗留事实
- 仍缺少的证据或已知问题；具体后续步骤见 `开发计划.md`。
```

### 2.2 `开发计划.md`：只记录尚未完成的工作

开发计划面向未来，记录下一步要做什么以及如何完成：

- 未完成任务、验收项、实施步骤和依赖；
- 优先级、所属阶段/冲刺、负责人或执行边界；
- `待开始`、`进行中`、`阻塞`、`待验证` 等当前状态；
- 下一验收条件、需要的真实证据和风险；
- 已完成任务的简短状态标记可以保留用于历史索引，但不得继续把它们列为活动工作，也不要重复日志中的实施细节。

计划条目应回答：**下一步做什么？为什么做？完成的判据是什么？依赖什么？**

计划禁止：

- 把已完成的实现细节写成当前待开发工作；
- 把日志中的测试输出、提交细节和历史过程大段复制进计划；
- 用模糊的“全部完成”“已上线”替代具体验收条件；
- 在没有真实证据时把待验证外部行为标为通过。

建议将“实现已完成”和“真实验收未完成”拆成不同任务。例如：

```markdown
| 任务 | 状态 | 完成判据 |
|---|---|---|
| 采集管线本地实现 | ✅ 已完成 | 本地测试通过（详见开发日志） |
| 首次真实 Actions 采集 | ⏳ 待执行 | Run 成功并检查生成 JSON |
| 第二次运行恢复验证 | ⏳ 待执行 | 确认 Registry 防重和游标恢复 |
```

## 3. 完成闭环：计划 → 实施 → 日志

完成一项工作后按以下顺序收口：

1. 只依据实际结果更新 `开发计划.md` 状态；未执行或失败的事项保持 `待验证`、`阻塞` 或相应状态。
2. 将已完成项从活动待办中移出，或拆出仅剩的验收工作；不要保留“代码已完成但任务仍像尚未开始”的混合描述。
3. 在 `开发日志.md` 新增一条简短结果记录，写明实际范围、验证命令/证据和未验证边界。
4. 如果没有变更或没有验证，不要为了“看起来有进度”新增日志条目。
5. 计划和日志只通过任务编号、日期、文件链接等轻量引用互相追溯；详细设计留在对应阶段文档。

推荐状态含义（项目已有标记应保持一致）：

- `[x]`：已实现，且有本地、CI 或文件证据；
- `[~]`：已实现，但仍需真实外部环境验证；
- `[ ]`：尚未完成或尚未执行；
- `[?]`：历史证据不完整，等待补证。

不得用 `[x]` 表示“计划已写好”，也不得用测试数量或代码行数推断真实平台/用户验收已经通过。

## 4. 代码和界面的用户可用性规则

InfoCatcher 是面向普通用户的静态信息站，同时包含构建脚本和 CLI。实现时优先降低用户理解和操作成本，而不是只追求代码能运行：

### 浏览器界面

- 每个视图都有清晰标题、用途说明和可识别的当前状态；
- 空数据、加载失败、部分降级和暂未采集要分别说明，不能用空白区域或误导性“暂无内容”代替原因；
- 按钮、筛选、排序和导航使用直观中文标签，状态变化有可见反馈；
- 外部来源、错误提示和下一步操作对用户可理解；
- 由外部数据进入 HTML 时进行安全转义，并限制外链协议；
- 保持现有原生 HTML/CSS/JS 风格和响应式布局，不为小改动引入大型依赖或无关重构。

### 构建脚本和 CLI

- 命令名、参数、帮助文字和错误信息清楚一致；
- 成功输出说明实际写入或跳过了什么，失败输出说明原因和可执行的下一步；
- `quota_paused`、`waiting_authorization`、`history_unsupported` 等降级状态必须向维护者明确展示，不能静默吞掉；
- 破坏性或难以恢复的操作（强制解锁、删除/覆盖、批量导入）先检查目标并保留审计信息；
- 使用说明、配置说明和数据边界应在相关 README 或命令帮助中同步更新。

### 可读性和维护性

- 优先复用项目现有模块、命名、错误处理和测试模式；
- 函数和数据结构名称表达业务含义，避免为了省行数牺牲可读性；
- 修改行为时补充最小必要测试，尤其是空状态、失败、边界和恢复路径；
- 不为了本技能进行与任务无关的重构；
- 保持项目既定的 Node.js 20、原生前端和零 npm 依赖约束，除非用户明确批准改变。

## 5. 验证与报告

根据任务选择适用验证，不声称执行过未执行的检查：

- 文档任务：检查日志/计划边界、链接和状态一致性；
- Node/数据任务：运行相关单元测试、静态校验和语法检查；
- 浏览器任务：实际启动并操作应用，检查视图、空状态、错误提示和既有功能回归；
- CI/外部平台任务：记录真实 Run、响应或线上页面证据；本地 fixture 不能替代真实外部验证；
- 所有修改：运行 `git diff --check`，查看 `git status --short`，确认没有无关文件变更。

最终向用户报告：修改文件、实际完成内容、验证命令及结果、未验证事项和下一步。失败要报告失败输出，不用“应该可以”代替结果。

## 6. 与现有项目 Skill 的关系

- `software-lifecycle-guard` 决定工作属于哪个生命周期阶段、哪个目录以及是否越界；
- 本技能决定 `开发日志.md` 与 `开发计划.md` 如何分工，以及实现如何面向用户保持可查看、可理解、可使用；
- 两者冲突时先停下来说明边界，必要时把需求、设计、编码和维护内容分别写入对应阶段文件；
- 本技能只存在于当前项目 `.claude/skills/`，不得创建全局规则或修改 `C:\Users\HelloWare\.claude`。
