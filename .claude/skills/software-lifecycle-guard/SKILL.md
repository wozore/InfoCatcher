# software-lifecycle-guard：软件工程阶段越界守卫

## 1. 为什么有这个技能

InfoCatcher 曾把需求分析、总体设计、编码、维护的内容全部塞进一份《可行性研究报告.md》，制造出一份 1147 行的"巨型混合文档"。2026-07-18 已按经典软件生命周期重构。

本技能的作用：**让 Claude Code 在动手前先判定"这件事属于哪个阶段"，严格只动该阶段的产物，不把后续阶段的工作提前写进当前阶段文档。**

## 2. 八阶段目录与行为边界（核心约束）

每个阶段只回答其核心问题，只在其目录内产出。下表是强制约束：

| 阶段 | 目录 | 核心问题 | 允许写入的产物 | 严禁越界写入 |
|:---:|------|----------|----------|----------|
| ① 问题定义 | `问题定义/` | 要解决的问题是什么？ | 问题陈述、调查证据、痛点分析 | 不写功能方案、不写技术选型 |
| ② 可行性研究 | `可行性研究/` | 有行得通的解决办法吗？ | 可行性报告、方案对比评分、PoC 验证、风险登记、Go/Conditional Go/Re-evaluate/No-Go 决策 | **不写功能需求条目(FR)、不写总体架构、不写 MVP 代码实现、不写贡献流程** |
| ③ 需求分析 | `需求分析/` | 目标系统必须做什么？ | SRS：功能需求(FR)、非功能需求(NFR)、范围边界、用例、需求建模、需求验证 | 不写技术栈、不写架构图、不写实现代码 |
| ④ 总体设计 | `总体设计/` | 概括地说，怎样实现？ | 系统架构图、模块划分、技术栈选型定型、数据设计(总体)、部署方案、演进路径 | 不逐条复述需求、不写函数级接口、不写测试用例 |
| ⑤ 详细设计 | `详细设计/` | 具体怎样实现？ | 数据字段表、接口/函数定义、算法设计、组件/页面详细设计、数据流图 | 不写可运行代码(那是⑥) |
| ⑥ 编码和单元测试 | `编码与单元测试/` | 写出程序 | 源代码、单元测试、运行说明 | 不重新定义需求或架构 |
| ⑦ 综合测试 | `综合测试/` | 集成 + 验收测试 | 集成/验收测试用例、测试报告、验收标准核验 | 不改需求、不改架构 |
| ⑧ 软件维护 | `软件维护/` | 改正 + 适应 + 完善 + 预防 | 贡献指南、纠错流程、更新流水线、Issue 模板说明 | 不新增功能需求(完善性维护应先回③) |

## 3. 强制三步流程（每次动手必走）

**Step 1 — 阶段判定**：根据用户请求的本质，判定它属于 8 阶段中的哪一阶段。
- "这个软件要解决什么问题" → ①
- "能不能做、哪种方案行得通、Go/No-Go" → ②
- "系统必须做什么、有哪些功能/非功能需求" → ③
- "整体怎么实现、用什么架构、怎么演进" → ④
- "具体怎么实现、字段/接口/算法" → ⑤
- "写代码、改代码" → ⑥
- "测试、验收" → ⑦
- "上线后纠错、贡献流程、更新机制" → ⑧

**Step 2 — 越界检查**：动手写之前，逐条自问——
- 这些内容是否属于当前判定阶段的"允许写入的产物"？
- 若属于表中"严禁越界写入"的范畴 → **停止**，转 Step 3。
- 若一句话里同时出现两个阶段的关键词（如"在可行性报告里写 Mvp 功能清单"）→ 这是越界信号，立刻拆分。

**Step 3 — 归属落地**：只在对应该阶段的目录文件中写入；若内容跨阶段，拆成多份分别落入各阶段目录，并在每份顶部用"前序/后序文档"建立追溯关系。

## 4. 跨阶段的正确衔接方式

阶段间不靠"塞进同一份文档"衔接，而靠**文档头部的追溯链**衔接。每个阶段产物顶部应标注：

```
> 前序文档：《xxx.md》（上一阶段）
> 后序文档：《xxx.md》（下一阶段）
```

跨阶段引用用相对链接，例如可行性报告引用 SRS：
`详见 [软件需求规格说明书.md](../需求分析/软件需求规格说明书.md)`

允许"索引式引用"——在当前阶段文档中用一两句话指向另一阶段产物，但**不复述另一阶段的内容细节**。

## 5. 常见越界模式（出现即警惕）

| 越界模式 | 错在哪 | 正确做法 |
|------|------|------|
| 在可行性报告里写"MVP 必须 P0 功能清单 + 验收标准" | MVP 功能定义属 ③ | 写入 `需求分析/软件需求规格说明书.md`，报告只引用 |
| 在可行性报告里画"三阶段架构演进图 + 周次里程碑" | 架构与演进属 ④ | 写入 `总体设计/总体设计说明书.md` |
| 在 SRS 里写"前端用 Lunr.js，后端用 Cloudflare Workers" | 技术栈属 ④ | 写入 `总体设计/总体设计说明书.md` |
| 在总体设计里逐条列出 FR-CORE-01..05 | 需求条目属 ③ | 引用 SRS，不重列 |
| 在详细设计里写完整可运行代码 | 代码属 ⑥ | 详细设计只写接口/算法，代码入 `编码与单元测试/` |
| 维护阶段私自加新功能模块 | 新功能属 ③ | 先回 SRS 登记 FR，再走设计→编码 |

## 6. 增量更新原则（与越界约束并存）

- 不破坏已有内容：剥离内容时，原章节保留索引指向新位置（如 `[已剥离 → ③]`），而非直接删除。
- 信息可追溯：每个需求条目能追溯到 PoC 证据/调查数据；每个架构决策能追溯到可行性方案的评分。
- 主动取证但控制范围：缺数据时说明缺口，不臆测；不擅自展开后续阶段工作来"填空"。

## 7. 进度记录的归属

- `开发日志.md` = 已完成工作记录（面向过去，跨阶段持续追加）
- `开发计划.md` = D1-D18 待办清单（面向未来）
- 两者不重复，互为补充。日志/计划本身不属于单一阶段，但记录的是"哪个阶段做了什么"，落点遵循本技能的阶段约束。

## 8. 约束冲突时的优先级

若用户指令与本技能冲突（如"把架构图画进可行性报告"）：
1. 优先指出越界并说明正确归属；
2. 若用户坚持，按用户指令执行但在该处显式标注"本内容属 X 阶段，应位于 Y 目录（此处为用户指定位置）"；
3. 不要默默顺从而破坏阶段边界，也不强抗用户。
