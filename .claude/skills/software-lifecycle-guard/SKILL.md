# software-lifecycle-guard：软件工程阶段越界守卫

## 1. 为什么有这个技能

InfoCatcher 曾把需求分析、总体设计、编码、维护的内容全部塞进一份《可行性研究报告.md》，制造出 1147 行的"巨型混合文档"。2026-07-18 已按经典软件生命周期重构。

2026-07-20 更新：经实践验证，现代软件开发不同于教科书中的瀑布模型。可行性之后如果严格等需求基线 → 总体设计 → 详细设计 → 编码，项目会陷入文档驱动陷阱。因此引入**三环混合模式**：

- **环 A**（①→②）：前期确认，线性执行 ✅ 已完成
- **环 B**（③④⑥⑧）：MVP 交付，**并发迭代**（每轮冲刺混合推进）
- **环 C**（④→⑤→⑦→⑧）：架构演进，回归顺序执行 ⏳ 待启动

## 2. 三环模式下的阶段边界

每个阶段的核心问题和允许写入的产物不变，但执行顺序因环而异：

| 环 | 阶段 | 核心问题 | 执行方式 | 说明 |
|:---:|:---:|---------|----------|------|
| **A** ✅ | ① 问题定义 | 要解决的问题是什么？ | 线性，完成即冻结 | 问题陈述、调查证据、痛点分析 |
| **A** ✅ | ② 可行性研究 | 有行得通的解决办法吗？ | 线性，完成即冻结 | 可行性报告、方案比选、PoC 验证、风险登记、Go 决策 |
| **B** ▶️ | ③ 需求分析 | 目标系统必须做什么？ | **冲刺中按需细化** | SRS 按冲刺取下一批需求细化，不追求完整基线 |
| **B** ▶️ | ④ 总体设计 | 概括地说，怎样实现？ | **够用即可，勿过度设计** | 只画当前冲刺需要的草图/决策，正式架构留环 C |
| **B** ▶️ | ⑥ 编码和单元测试 | 写出程序 | **冲刺主力** | 每个冲刺产出可用的软件增量 |
| **B** ▶️ | ⑧ 软件维护 | 改正 + 适应 + 完善 + 预防 | **现在就开始** | Issue 模板、纠错流程、社区反馈机制就位 |
| **C** ⏳ | ④ 总体设计（正式化） | 概括地说，怎样实现？ | 线性，环 B 稳定后启动 | 正式架构图、技术栈定型、模块划分、演进路线 |
| **C** ⏳ | ⑤ 详细设计 | 具体怎样实现？ | 线性，④完成后 | 数据字段表、接口定义、组件设计 |
| **C** ⏳ | ⑥ 方案 3 演进 | 写出程序 | 线性，⑤之后 | Serverless 后端、推荐引擎、自动采集 |
| **C** ⏳ | ⑦ 综合测试 | 集成 + 验收测试 | 线性，编码完成后 | 集成测试用例、测试报告、验收核验 |
| **C** ⏳ | ⑧ 维护运营 | 持续改进 | 持续 | 开源社区运营、数据更新、用户反馈 |

### 环 B 并发规则（关键约束）

环 B 允许 ③④⑥⑧ 在冲刺内同时推进，但不是无约束的：

| 可以这样做 | 禁止这样做 |
|-----------|-----------|
| 在 MVP 编码中参照 SRS 的已有需求条目 | 在编码中新定义一个从未在 SRS 登记的 FR 而不回头更新 SRS |
| 画当前冲刺需要的高层草图（如"这页大概长什么样"） | 在编码阶段写完整的架构文档（属④）、字段表（属⑤） |
| 编码同时建立 Issue 模板和 CONTRIBUTING.md（⑧先行） | 在维护阶段擅自添加新功能模块（应先回③登记 FR） |
| 编码中发现需求遗漏 → 回头更新 SRS 对应条目 | 在 SRS 里写入技术实现细节（属④） |
| 随时做冒烟测试/手动验证 | 把正式验收测试当作"编码附带的"（正式验收归⑦） |

### 三环之外的目录

| 目录 | 状态 | 说明 |
|:----:|:----:|------|
| `sandbox/` | 可随时使用 | 技术实验/原型验证空间，不属于任何阶段；实验结论成熟后移入对应阶段目录 |

## 3. 强制三步流程（每次动手必走）

**Step 1 — 阶段判定 + 环判定**：根据用户请求的本质，判定它属于哪个阶段、当前在哪个环。

| 用户请求 | 阶段 | 环 | 归属目录 |
|---------|:---:|:--:|---------|
| "能不能做、哪种方案行得通" | ② | A ✅ | `可行性研究/` |
| "系统必须做什么、细化某个需求" | ③ | B ▶️ | `需求分析/` |
| "整体怎么实现、用什么架构" | ④ | B ▶️或 C⏳ | `总体设计/` |
| "具体字段/接口/算法" | ⑤ | C ⏳ | `详细设计/` |
| "写代码、改代码、编码测试" | ⑥ | B ▶️ | `编码与单元测试/` |
| "测试、验收" | ⑦ | C ⏳ | `综合测试/` |
| "上线后纠错、贡献流程、更新" | ⑧ | B ▶️ | `软件维护/` |
| "技术实验、原型验证" | — | — | `sandbox/` |

**Step 2 — 越界检查**：动手写之前，逐条自问——
- 在环 B 中，这个内容能否在当前冲刺范围内有效产出？
- 若属于环 C（正式架构/详细设计/验收测试）且环 B 尚未稳定的内容 → **标记为环 C 待办，不在环 B 提前展开**
- 属于"禁止这样做"列表中的行为 → **停止**，转 Step 3
- 一句话里同时出现两个阶段的关键词 → 这是越界信号，拆开归属

**Step 3 — 归属落地**：只在对应该阶段的目录文件中写入。若内容跨阶段，拆成多份分别落入各阶段目录，并在每份顶部用"前序文档"建立追溯关系。

## 4. 跨阶段的正确衔接方式

阶段间不靠"塞进同一份文档"衔接，而靠**文档头部的追溯链**衔接。环 B 中跨阶段写入的文档也应标注追溯关系：

```
> 前序文档：《xxx.md》（前一个阶段的输入）
> 后序文档：《xxx.md》（本阶段产物的下游使用者）
```

跨阶段引用用相对链接。允许"索引式引用"——在当前阶段文档中用一两句话指向另一阶段产物，但**不复述另一阶段的内容细节**。

## 5. 常见越界模式（出现即警惕）

| 越界模式 | 错在哪 | 正确做法 |
|------|------|------|
| 在可行性报告里写 MVP 功能清单 | MVP 功能定义属 ③ | 写入 `需求分析/软件需求规格说明书.md`，报告只引用 |
| 在可行性报告里画架构演进图 + 里程碑 | 架构与演进属 ④ | 写入 `总体设计/总体设计说明书.md` |
| 在 SRS 里写技术实现细节 | 技术栈属 ④ | 写入 `总体设计/总体设计说明书.md` |
| 在编码中新定义 FR 而不更新 SRS | 需求条目应追回 ③ | 编码中发现需求遗漏 → 先补入 SRS 再实现 |
| 在总体设计里逐条复述 FR 清单 | 需求条目属 ③ | 引用 SRS，不重列 |
| 在环 B 就做完整的详细设计（字段表、接口） | 详细设计属 ⑤（环 C） | 标记为环 C 待办，环 B 只做够用的草图 |
| 维护阶段私自加新功能模块 | 新功能属 ③ | 先回 SRS 登记 FR，再走设计→编码 |

## 6. 增量更新原则

- 不破坏已有内容。剥离内容时原章节保留索引指向新位置（如 `[已剥离 → ③]`），而非直接删除。
- 信息可追溯。环 B 中的跳跃式追溯也是追溯——SRS 条目可追溯到调查数据，代码可追溯到 SRS 的对应需求。
- 主动取证但控制范围。缺数据时说明缺口，不臆测；不擅自展开后续阶段工作来"填空"。

## 7. 进度记录的归属

- `开发日志.md` = 已完成工作记录（面向过去，跨阶段持续追加）
- `开发计划.md` = 三环冲刺任务清单（面向未来，冲刺导向）
- `README.md` = 项目总览与三环路径说明

两者不重复，互为补充。日志/计划本身不属于单一阶段，但记录的是"哪个环的哪个阶段做了什么"。

## 8. 约束冲突时的优先级

若用户指令与本技能冲突：
1. 优先指出越界并说明正确归属；
2. 若用户坚持，按用户指令执行但在该处标注"本内容属 X 阶段（环 Y），应位于对应目录（此处为用户指定位置）"；
3. 不要默默顺从破坏阶段边界，也不强抗用户。
