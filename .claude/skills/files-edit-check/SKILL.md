# 项目文件创建、批量修改与批量删除检查

## 触发机制：Hook + Skill 双保险

本系统由两层机制协同工作：

- **Hook 层**（`.claude/hooks/files-edit-check.sh`）— **确定性拦截**
  注册在 `.claude/settings.json` 的 `PreToolUse` 事件中，匹配 `Edit|Write|MultiEdit` 工具。
  每次写操作执行前**必然触发**，以 `exit 2` 阻止操作并提示走 skill 流程。
  Hook 无法被 LLM 绕过，是**强制性的安全闸门**。

- **Skill 层**（本文件）— **引导性流程**
  被 Hook 触发后由 Claude 调用，提供"调查→计划→确认→执行→报告"的完整工作流。
  Skill 负责列出文件清单、获取用户确认。

**执行链路**：
  用户请求写文件 → Hook 阻止（exit 2）→ Claude 加载本 Skill → 列出清单 → 用户确认 → **使用 Bash 工具写入**

> ⚠️ **重要**：确认后**必须使用 Bash**（`echo`/`cat`/`printf`）执行文件写入，因为 Hook 会阻止 `Write`/`Edit`/`MultiEdit` 工具的直接调用。

## 常见漏触发场景（请自查）

以下表述经常被误判为"不需要触发"，但实际上必须触发：

| 用户说的话 | 为什么必须触发 |
|-----------|---------------|
| "把XX写入文档" | = 创建新文件 |
| "更新一下开发计划" | = 修改现有文件 |
| "在XX里补充一段" | = 修改现有文件 |
| "记下来" / "记录下来" | = 创建新文件 |
| "生成XX文件" | = 创建新文件 |
| "加一个XX功能" | 可能涉及创建+修改多个文件 |
| "补上XX任务" | = 修改现有文件 |
| "新建一个XX" | = 创建新文件 |
| "删掉XX目录/文件夹" | = 删除目录（内含文件全部删除） |
| "把XX目录改名/移动" | = 重命名或移动目录，改变项目结构 |
| "清理XX目录" / "把XX目录清了" | = 批量删除文件 |
| "用 rm -rf / del 删除" | = 删除操作，无论目标是文件还是目录 |

**判断法则**：只要你觉得下一步可能要调用 Write、Edit 或任何会变更文件系统的工具（Bash rm/mv/del/mkdir 等），就先触发本技能。不确定时，宁可多触发也不要跳过。

## 核心规则

在调用 Write、Edit 或任何会创建/修改/删除项目文件的工具之前，先检查本次操作是否满足下方的触发条件。如果满足，必须执行完整的"调查→计划→确认→执行→报告"流程，不可跳过。即使其他技能（如 software-lifecycle-guard）已经做了阶段路由，本技能的独立确认仍然不可省略。

> ⚠️ **写入方式**：用户确认后，**必须使用 Bash 工具**（`cat`、`echo`、`printf`、重定向等）执行文件写入。
> 因为 `Write`/`Edit`/`MultiEdit` 工具已被 PreToolUse Hook 拦截，直接调用会被阻止。
> 删除操作也建议使用 Bash（`rm`/`mv`）以避免 Hook 拦截。

## 目标

在当前项目根目录及其子目录中创建文件、进行多处修改或批量删除前，让用户清楚知道即将发生什么；取得确认后再执行，并在完成时准确报告实际结果。

本技能覆盖三类操作：

1. 创建一个或多个新文件；
2. 修改同一文件中的多个独立内容区域，或修改两个及以上现有文件；
3. 删除两个及以上现有文件；
4. 重命名或移动目录（如 mv / mkdir 后搬入文件），导致项目结构变化的操作。

项目外文件不在本技能的核验范围内。

## 与 software-lifecycle-guard 的协作

本技能和 software-lifecycle-guard 均会在项目文件写入操作前触发，但职责不同：

- **software-lifecycle-guard** 负责判定阶段归属、检查越界、路由到正确目录；
- **本技能** 负责在动手前列出文件清单并请求用户确认。

当用户请求同时匹配两个技能的触发条件时，执行顺序为：

1. 先执行 software-lifecycle-guard，完成阶段判定与目录路由；
2. 紧接着执行本技能，列出将要创建/修改/删除的具体文件清单，请求用户确认；
3. 两个技能都走完并得到用户同意后才动手操作。

两技能的职责不重叠，不可相互替代。即使 software-lifecycle-guard 已判定允许写入，本技能仍必须独立列出文件操作清单供用户确认。

## 触发判定

出现以下**任一**情况就必须触发：

- 创建一个或多个文件（无论通过 Write、脚本、生成器还是其他方式）；
- 修改现有文件（无论数量，改 1 个文件 1 处也触发，除非是纯格式/错字修正）；
- 删除文件或目录；
- 重命名或移动目录（改变项目结构）；
- 同一任务中创建 + 修改操作同时存在（例如：新建 1 个文件 + 修改 1 个文件 = 必须触发，不能拆成两个"单点"绕过）；
- 通过脚本、命令、构建、测试、导出、模板或代码生成器间接产生文件。

以下情况不触发：

- 只读取、搜索或分析（不产生任何文件变更）；
- 只创建空文件夹。

## 工作流程

### 1. 调查现状，但不要先行改动

在征求确认前，使用只读操作确定：

- 目标文件是否已经存在；
- 需要修改的章节、函数、配置项或其他内容区域；
- 生成器可能产生的文件路径或输出范围；
- 删除目标的实际路径、数量和用途，尤其是通配符、目录清理或脚本计算出的目标。

删除是难以撤销的操作。提出计划前必须查看目标，确认它们与用户描述一致；如果实际目标、数量或用途与描述不符，先向用户说明差异，不要继续。

不要在调查阶段创建、修改或删除文件。

### 2. 向用户说明计划并请求确认

执行任何创建、多处修改或批量删除前，先向用户展示计划。

创建文件时使用：

```markdown
## 计划创建

- [项目相对路径]：该文件将提供的功能或用途。

是否按以上计划创建？
```

修改文件时使用：

```markdown
## 计划修改

- [项目相对路径]
  - 修改部分：准备修改的章节、函数、配置项或内容区域。
  - 修改目的：这项修改要实现或修正什么。

是否按以上计划修改？
```

批量删除文件时使用：

```markdown
## 计划删除

- [项目相对路径]：文件当前用途；删除原因。

以上文件删除后可能无法恢复。是否确认删除？
```

逐项列出已经确定的删除目标。不要仅写文件夹或通配符来代替实际文件清单；如果目标只能在命令运行时确定，先用只读方式展开并展示匹配结果。目标很多时可以按用途分组，但仍要让用户看清具体文件路径和总数。

混合任务按实际情况同时列出“计划创建”“计划修改”和“计划删除”。对于输出路径无法完全预知的创建工具，不要把输出文件夹伪装成待创建文件；改用“预计输出范围”说明可确认的输出目录、文件名模式或文件类型、预计数量，以及每类输出文件的功能。例如：

```markdown
## 预计输出范围

- 输出位置：`generated/`
- 文件范围：由生成脚本定义的 3 个样例文件（具体名称执行后核验）。
- 文件功能：提供后续测试或演示所需的样例数据。

是否运行生成操作？
```

用户明确同意后才执行。如果用户调整范围，更新计划并按新范围执行；如果用户拒绝，则停止。用户在当前对话中已经针对同一份具体计划明确授权时，不要重复询问。

### 3. 用 Bash 执行实际操作

用户确认后，**使用 Bash 工具**（而非 `Write`/`Edit`）执行文件操作，因为 Hook 已拦截了 `Write`/`Edit` 工具：

- 创建/修改文件：用 `cat` heredoc、`printf`、`echo` 重定向
- 删除文件/目录：用 `rm`、`rmdir`
- 重命名/移动文件：用 `mv`

执行期间维护创建、修改和删除记录：

- 对计划创建的明确路径，记录执行前是否存在；
- 对生成器等动态输出，比较相关输出范围执行前后的文件清单；
- 区分新文件与原有文件的覆盖或编辑；
- 删除后核验每个目标是否确实不存在，同时检查未授权文件是否保持不变；
- 批处理只完成一部分时，逐项记录成功与失败；
- 不把文件夹当作文件操作结果。

如果执行过程中发现新增目标或操作范围扩大，暂停并重新说明增量计划，取得确认后再继续。

### 4. 核验并报告结果

完成后按实际状态报告，不要把未核验的操作声称为成功。

```markdown
## 成功创建

- [项目相对路径]：该文件的功能。

## 创建失败

- [项目相对路径]：计划用途；失败原因。

## 成功修改

- [项目相对路径]：实际修改的部分及作用。

## 修改失败

- [项目相对路径]：计划修改的部分；失败原因。

## 成功删除

- [项目相对路径]：原有用途；删除原因。

## 删除失败

- [项目相对路径]：计划删除原因；失败原因。
```

输出规则：

- 使用相对于项目根目录的路径；
- 每项都简要说明功能、修改部分、删除原因或失败原因；
- 没有对应项目时写“无”；
- 不列文件夹；
- 不把执行前已存在的文件误报为新文件；
- 不把仍然存在的文件报告为删除成功；
- 除非用户另有要求，不在结果清单之外重复长篇过程说明。
