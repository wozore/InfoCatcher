## 0. 文档说明

本说明书回答软件生命周期表中的问题：

> **④ 总体设计 —— 概括地说，怎样实现？**

内容来源：可行性研究报告的"候选方案技术栈评估""演进策略""实施里程碑"。本阶段把可行性研究的方案选型结论**固化**为系统总体架构，并规划从 MVP 到 v1.0 的演进路径。

> 与可行性研究的分工：可行性研究比较"哪条路走得通"并给出条件性结论；总体设计选定一条路并定义它的架构骨架、模块划分、部署方式、演进步骤。可行性报告中的加权评分、一票否决、敏感性分析不在此重复，但结论作为本设计的依据被引用。

## 1. 设计依据

- 可行性结论：**Conditional Go**。推荐方案 1（静态站）起步 → 演进至方案 3（SPA + Serverless）。
- 5 项成立条件（C1–C5）：W1 技术验证 C1+C3 已通过（见 `可行性研究/poc/verification_report.md`）。

## 3. 系统总体架构

### 3.1 阶段一：MVP（v0.1，方案 1 静态站）

```
┌─────────────────────────────────────────┐
│  浏览器（纯前端，无后端）                 │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌────────┐  │
│  │列表页│  │详情页│ │对比页 │ │热点/场景│ │
│  └──┬───┘ └──┬───┘ └──┬───┘ └───┬────┘  │
│     └───────┬┴────────┴─────────┘       │
│        ┌────▼─────┐  ┌──────────┐       │
│        │data/JSON │  │Lunr.js搜索│      │
│        └──────────┘  └──────────┘       │
│        ┌──────────────┐                 │
│        │localStorage │（行为偏好推断）   │
│        └──────────────┘                 │
└──────────────┬──────────────────────────┘
               │ 静态文件
       ┌───────▼────────┐
       │ GitHub Pages   │（免费托管 + CDN）
       └────────────────┘
```

**技术栈**：原生 HTML/CSS/JS + Markdown/JSON 内容 + GitHub Pages。
**部署**：`git push` → Pages 自动部署。

### 3.2 S2 B14：构建时热点采集（方案 1 内的够用扩展）

B14 不提前引入运行时 Serverless，而是利用 GitHub Actions 在部署前生成静态数据：

```
热点信息源清单.md（人工核验）
          │
          ▼
news-sources.json（运行配置）
          │
          ▼
GitHub Actions 每日触发 ── Secrets 注入凭据
          │
          ▼
build-news.js
  ├─ YouTube RSS + 官方 Data API
  ├─ X / TwitterAPI.io
  └─ B站人工精选（`news-manual-items.json`）
       └─ RSSHub（仅 `bilibili-only` 诊断，Provider阻断即熔断）
          │
          ▼
标准化 → 去重/溯源 → 主题关联 → 可解释评分
          │
          ├─ hotspots.json（内容、事件、评分、覆盖状态）
          └─ news-state.json（批次、游标、重试、降级）
          │
          ▼
GitHub Pages 静态热点视图
```

**设计边界：**

- 浏览器只读取静态 JSON，不直接调用外部平台；API Key 仅来自 GitHub Secrets。
- 统一 UTC 五层半开窗口：`[0,1)`、`[1,7)`、`[7,30)`、`[30,90)`、`[90,270)` 天；调度以时间层优先并持久化每个来源游标。
- YouTube 历史回溯使用低成本 uploads playlist（channels/playlistItems/videos 均按官方 quota 记账）；B站默认不做自动历史回溯，人工条目直接进入统一处理管线。
- `news-registry.json` 以 `platform:native_id` 保存每个检测视频的发现/处理状态，构建时加载为 Map 批量防重，高成本详情与分析只处理新记录。
- `news-quota.json` 管理 YouTube quota units；B站额度仅在显式 RSSHub 诊断探测中记录，不因默认构建消耗。
- `pending-authorizations.json` 保存超出默认270天范围的回溯请求和用户决定；CLI 提供来源添加、授权处理、额度恢复和锁处理，不增加大型管理 UI。
- JSON 写入采用唯一临时文件 + rename，并以构建锁避免两个任务同时修改 registry/state/hotspots。
- B站动态仍是热点内容来源之一，可参与主题和观点对比；当前默认通过人工精选进入，缺失不等同于来源沉默。
- B站不得调用内部 API、逆向 SDK、Cookie自动化或绕过风控；未来如有官方授权或明确允许的稳定Feed，再重新评估。
- 评分采用配置化规则、证据和置信度；未来 AI 只提供候选判断，正式启用前需评估。
- 采集失败不得用空结果覆盖上一版有效数据。

完整 Serverless API 代理、数据库/KV、实时采集、LLM 分析和个性化推荐仍属于环 C。

### 3.3 阶段二：v0.2-v0.3（方案 1 → 方案 3 渐进迁移）

在静态站基础上**增量**引入 Serverless：
- 后端最小化：Cloudflare Workers / Vercel Functions 做 **API 代理 + 数据缓存**。
- 浏览器端搜索 → 可选 Serverless 端搜索。
- 新增：自动数据采集（Serverless Cron）、AI 热点聚合、价格计算器、行为偏好推荐后端化。

### 3.3 阶段三：v1.0（方案 3，SPA + Serverless）

```
┌─────────────┐     ┌──────────────────────┐
│ SPA 前端    │────▶│ Serverless Functions│
│（JS 框架）   │     │  - API 代理          │
└─────────────┘     │  - 采集 Cron         │
                    │  - 推荐逻辑           │
                    └──────┬───────────────┘
                           │
              ┌────────────▼────────────┐
              │ Cloudflare KV / JSON    │（数据缓存层）
              └─────────────────────────┘
                           │ 采集
              ┌────────────▼────────────┐
              │ 外部 API + 网页（API 代理│
              │ 降低直接抓取法律风险）    │
              └─────────────────────────┘
```

## 4. 模块划分

| 模块 | 职责 | MVP | v1.0 |
|------|------|:---:|:---:|
| 工具信息库 | 数据存储与展示 | ✅ 静态 JSON | ✅ KV + Cron 更新 |
| 对比引擎 | 多维度对比表 | ✅ 前端 | ✅ 前端 |
| 检索 | 搜索 + 筛选 | ✅ 浏览器端 | ✅ 可选后端 |
| 推荐引擎 | 行为推断 + 破茧 | ⚠️ localStorage | ✅ Serverless |
| 热点聚合 | X/YouTube/Bilibili | ✅ S2 构建时采集（YouTube/X）+ B站人工精选 + 静态 JSON | ✅ 未来重新评估官方授权或明确允许的Feed |
| 反馈/维护 | 众包纠错 | ✅ GitHub Issues | ✅ Issues + AI 预审 |

## 5. 数据设计（总体）

- MVP：JSON 文件（`编码与单元测试/mvp/data/`）。工具信息采用手工 + 众包维护；S2 热点由 YouTube/X 构建时采集、B站人工精选共同组成，并保留来源证据与状态。
- v1.0：Cloudflare KV 缓存 + Serverless 采集写入；B站自动化仍须先完成官方授权或合规数据源评估。
- 数据更新流水线：用户提交 → AI 初审（v1.0+）→ 人工审核 → 入库（详见《软件维护/CONTRIBUTING.md》）。
