# 平台数据采集综述（历史快照）

> **整合日期**：2026-07-29
> 保留 YouTube、X、Bilibili 和知乎的历史方案、成本假设与否决理由。当前策略以 [采集文档](../acquisition.md) 为准；价格、配额、端点和法律判断均需重新核验。

## 平台结论

| 平台 | 当前策略 | 主要边界 |
|---|---|---|
| YouTube | 官方 Data API 自动采集 | 按 quota units 记账，受控回溯 |
| X | TwitterAPI.io 自动采集 | 公开内容、来源轮转、保留替换适配层 |
| Bilibili | 人工精选 | 默认不发网络请求；诊断遇阻快速熔断 |
| 知乎 | 暂缓 | 无官方数据 API，不维护 Cookie/反爬路线 |

所有平台统一保留来源、原生 ID、内容类型、时间、评分依据、主题、溯源和降级状态。

## YouTube

历史方案以 RSS 发现视频，再用官方 API 补元数据；曾考虑 Supadata 作为字幕备用层。原配额估算为每天 10,000 units，其中 `videos.list`、字幕和评论占主要成本，但具体单价、字幕权限和备用服务额度必须以执行时官方资料为准。

```text
RSS / uploads playlist → videoId
  → videos.list 补标题、描述、标签、时长、时间和互动
  → 可用时获取字幕/评论
  → 标准化入库
```

约束：字幕可能缺失、延迟或不准确，不应作为未经核验的精确引文；频道信息应缓存；发现、详情和评论分别记账，额度不足时优先保证来源覆盖与核心元数据。

## X

早期评估排除了需要自动登录的开源爬虫，原因是封号和持续维护风险；选择 TwitterAPI.io 是成本与稳定性的折衷，不等同于官方授权。

历史流程：缓存来源标识，调用用户最近推文接口并使用 cursor 分页，轮转来源以限制成本，再按关键词、时间和来源信号过滤并写入统一结构。第三方服务被封禁、涨价或变更格式时，应通过适配层切换服务或回退。

历史成本估算约为每天 300 条、每月约 2 美元；端点、价格、免费试用及“公开内容抓取风险低”的法律判断都是时间敏感结论，不能直接作为当前保证。

## Bilibili

### 当前结论

早期方案把公共或自部署 RSSHub 作为自动化入口；真实 Actions 遭遇 Cloudflare 403，且相关路由可能调用站内接口、依赖 Cookie 或浏览器模式。因此当前不批准 RSSHub-MCP、自部署轮转、Cookie、内部 API、FlareSolverr 或其他风控绕过路线。

B站视频、动态和专栏仍可作为内容，由维护者将公开链接加入人工暂存，再进入统一标准化、评分和主题管线。重新评估自动化的条件是官方授权、UP 主主动提供的稳定 Feed，或其他明确允许且无需绕过风控的公开来源。

### 历史候选能力

RSSHub 曾被评估用于发现 UP 主视频、动态、专栏和热门内容，但通常只能提供标题、描述、时间和链接，不能稳定提供字幕、精确互动或评论。BibiGPT/DownSub 属人工字幕候选，TikHub 属付费第三方数据候选；B站内部 API 因合规风险明确禁止。

历史自部署命令仅用于追溯，不代表批准执行：

```bash
docker run -d --name rsshub -p 1200:1200 diygod/rsshub:latest
```

## 知乎

知乎的问答、文章和观点具有内容价值，但没有公开开发者数据 API。历史评估发现 RSSHub 路由依赖定期失效的 Cookie、错误率高且反爬严格；第三方覆盖和开源爬虫也无法提供可接受的稳定、合规、低维护路径，因此不纳入 MVP。

重新评估条件：官方 API、明确允许且稳定的 Feed、可信第三方覆盖，或项目具备经批准的维护和合规资源。手工提取 Cookie、自部署 RSSHub 和持续反爬适配只是被否决的历史兜底路线，不应实施。

## 共通决策规则

1. 优先官方或明确允许的来源，保存核验日期和精确 URL。
2. 采集适配与内部数据结构分离，供应商替换不影响下游。
3. 先定义额度、成本、重试计费、熔断和恢复，再增加网络操作。
4. 能力不足时明确 `partial/degraded`，缺失不等于来源沉默。
5. 不因“公开可见”推导出可自动采集；ToS、法律、价格和端点结论都需定期复核。
