# 软件项目可行性研究方法

> 通用方法论，不代表 InfoCatcher 当前事实。目标是在投入大量资源前，判断项目是否值得做、能否做、如何做、成本和风险是否可控。

## 决策问题与产出

| 问题 | 需要确定 |
|---|---|
| 值不值得做 | 战略与用户价值、收益是否覆盖成本 |
| 能不能做 | 技术、数据、团队、基础设施和合规条件 |
| 怎么做 | 自研、SaaS、外包、低代码或混合方案 |
| 何时做 | 优先级、依赖、窗口和交付周期 |
| 花多少钱 | 一次性成本、长期 TCO 和机会成本 |
| 风险多大 | 技术、业务、安全、合规、供应商和组织风险 |
| 谁负责 | 业务、产品、研发、测试、运维、法务、财务职责 |
| 如何成功 | 指标、验收条件和收益跟踪机制 |

产出通常包括 Go / Conditional Go / No-Go 建议、推荐方案、成本收益估算、风险登记、成立条件、决策关口和阶段路线。

可行性研究位于机会识别与正式立项/需求分析之间。敏捷项目可用 Discovery、Spike、PoC 或 MVP 代替厚重报告，但不能跳过关键证据和决策。

## 八步流程

1. **定义问题与成功指标**：描述现状、可观察后果、不做的影响和目标指标，避免以“建设某系统”代替问题。
2. **识别利益相关者**：确定受益者、出资者、使用者、交付者、运营者和监管者，并明确决策权与责任。
3. **限定范围**：写清 In Scope、Out of Scope、假设、约束、依赖和验收边界。
4. **设计候选方案**：至少包括维持现状、最小方案和目标方案；统一比较口径。
5. **收集证据**：区分事实、估算和假设，记录来源、日期、版本、样本和不确定性。
6. **验证关键未知**：用原型验证交互，用 PoC 验证技术和集成，用 MVP 验证真实使用价值；每项验证先设成功/停止条件。
7. **评估风险与敏感性**：登记概率、影响、触发信号、缓解措施、责任人和残余风险，并测试结论对关键假设变化是否稳定。
8. **形成决策**：给出推荐、反对理由、成立条件、证据缺口、下一关口和退出方案。

## 评估维度

| 维度 | 核心问题 | 常用证据 |
|---|---|---|
| 业务/用户 | 问题是否真实、频繁且值得解决 | 调研、访谈、行为数据、竞品和替代方案 |
| 技术 | 架构、集成、性能和可靠性是否可达 | PoC、基准、接口验证、技术债清单 |
| 经济 | 投入和长期成本是否合理 | 报价、人月、资源单价、收益基线和情景分析 |
| 组织/运营 | 团队、流程和持续维护是否可承受 | 能力矩阵、RACI、运营工时和支持模型 |
| 进度 | 周期、依赖和资源是否匹配 | WBS、关键路径、历史交付数据和缓冲 |
| 法律/IP | 数据、许可证、合同和知识产权是否允许 | ToS、许可证、合同、法务意见 |
| 安全/隐私 | 威胁、权限、数据生命周期和合规是否可控 | 威胁建模、数据流、控制措施、审计要求 |
| 长期演进 | 可维护、扩展、迁移和退出是否可行 | 模块边界、替换成本、锁定和退役计划 |

对云、SaaS、开源、第三方 API、AI、DevOps、遗留集成和供应商锁定，应额外核查：服务可用性与退出、许可证和供应链、配额/涨价/接口变化、数据边界、模型误差与成本、可观测性、迁移窗口和替代供应商。

## 成本收益

成本至少包括开发、采购、基础设施、人力、迁移、培训、运维、升级、安全合规、退出和机会成本。按保守/中性/乐观三种情景估算，并说明时间范围和假设。

```text
开发成本 = 人员数量 × 人月单价 × 周期 × 利用率调整系数
基础设施成本 = 资源规格 × 使用时长 × 单价 + 冗余与灾备成本
年度运维成本 = 基础设施年费 + 运维人力 + 续费 + 安全合规 + 支持服务
TCO = 建设 + 采购 + 迁移 + 培训 + 运维 + 升级 + 退出成本
ROI =（总收益 - 总成本）/ 总成本 × 100%
投资回收期 = 初始投资 / 年净现金流入
NPV = Σ[第 t 年现金流 / (1 + 折现率)^t] - 初始投资
```

财务收益须有业务基线、归因方法和实现概率；学习、风险降低、体验改善等非财务收益应单列，不能强行货币化。

## 风险与决策模型

风险登记至少包含：编号、描述、概率 P、影响 I、等级、触发信号、预防/应对、责任人、残余风险和复核日期。可用 `P × I` 排序，但安全、合规、核心数据、不可逆锁定等事项可设一票否决，不应被加权平均掩盖。

候选方案统一使用 1—5 分并明确权重、证据和置信度：

```text
方案总分 = Σ（维度得分 × 维度权重）
```

决策应同时给出：原始分、加权分、否决项、敏感性分析和关键未知。证据不足时优先 Conditional Go，而非伪精确的 Go。

## 报告最小结构

1. 执行摘要与建议；
2. 问题、目标、成功指标和范围；
3. 约束、假设、资料来源和限制；
4. 利益相关者与责任；
5. 基线及候选方案；
6. 八维可行性分析；
7. 成本、收益和情景；
8. 风险登记与缓解；
9. 评分、否决项和敏感性；
10. 成立条件、决策关口、证据缺口和退出方案；
11. 附录（原始数据、PoC、引用和计算）。

## 立项检查清单

- [ ] 问题和用户证据是否独立于预设方案？
- [ ] 成功指标是否有基线、目标、时间和测量方法？
- [ ] 是否明确范围、依赖、假设和停止条件？
- [ ] 是否比较维持现状、最小方案和目标方案？
- [ ] 关键技术、数据和接口是否经过验证？
- [ ] 是否计算长期 TCO，并对成本和收益做情景/敏感性分析？
- [ ] 是否评估安全、隐私、合规、许可证和供应商退出？
- [ ] 是否有责任人、资源承诺、运营模型和关键路径？
- [ ] 风险是否包含触发信号、缓解和残余风险？
- [ ] 决策是否列出一票否决、证据缺口、下一关口和退出方案？

## 常见误区

| 误区 | 修正 |
|---|---|
| 先决定方案再补论证 | 从问题和证据出发，保留基线方案 |
| 只算开发费 | 计算多年 TCO、迁移和退出成本 |
| 假设上线即产生收益 | 记录基线、归因和实现概率 |
| 用演示替代验证 | 为 PoC/MVP 预设可判定的成功条件 |
| 忽略范围和依赖 | 明确边界、责任和停止条件 |
| 把安全合规留到最后 | 作为准入项和否决项前置 |
| 忽略运营与退出 | 评估持续工时、支持、替换和退役 |
| 用加权分掩盖高风险 | 同时呈现否决项和残余风险 |

可行性研究的价值不是证明项目应该做，而是用足够证据支持做、调整、暂停或放弃。
