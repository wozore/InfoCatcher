# R2 / R4 风险缓解方案（历史快照）

> **整合日期**：2026-07-29
> 当前任务和实现分别以 [开发计划](../../开发计划.md)、[运维文档](../operations.md) 和 [架构文档](../architecture.md) 为准。本文件保留当时的风险判断和缓解逻辑。

## 风险总览

| 风险 | 初始等级 | 残余判断 | 缓解方向 |
|---|:---:|---|---|
| R2：信息更新跟不上行业变化 | 20（极高） | 中—高，不能完全消除 | 时效透明、众包纠错、渐进自动化 |
| R4：用户不使用或不持续使用 | 12（中） | 待真实反馈验证 | 可分享场景、SEO、定向推广、回访机制 |

## R2：信息时效

静态内容会随价格、模型和功能变化而过时，直接损害可信度。单人维护决定了该风险只能持续降低。

### 分层措施

1. **时效透明**：每条记录保存 `last_updated`；价格、额度和模型等高频维度提示以官网为准，并附来源链接。
2. **众包纠错**：用户通过结构化 Issue 提交，维护者核验后入库。AI 初审仅是未来可选层，当前不得自动合并。
3. **构建时自动化**：优先用官方或明确允许的来源定时采集；失败保留旧数据，冲突进入人工确认。
4. **长期演进**：只有静态方案无法满足反馈验证后的需求时，才引入 Serverless、缓存和 Cron。

```text
用户提交 → 人工审核 → 入库
构建时采集 → 校验/冲突检测 → 入库或保留旧数据
```

历史草案曾规划 Bilibili API、每日采集和完整 Serverless Cron；这些不是当前承诺。当前 B站以人工精选为主，平台边界见 [采集文档](../acquisition.md)。

### 触发与复核

用户报告价格/功能已变化、过期条目增多或维护工时不可持续时，应复核 R2。关键指标包括过期率、纠错数量、审核周期、采集失败/冲突率和人工维护时间。

## R4：用户获取与留存

风险假设：学生样本主要从社交媒体获取信息，可能不会主动访问独立站；MVP 若访问和反馈不足，无法判断迭代方向。原始阈值（上线一周访客少于 30、Star 少于 10、无自发反馈）只是历史假设，尚未验证。

### 缓解路径

- **获客**：将场景页和工具页设为可搜索、可独立分享的入口；完善标题、描述、OpenGraph、sitemap 和必要的结构化数据。
- **激活**：用户首次访问应能迅速理解价值，并完成“选择场景 → 比较 → 决策”等有用动作。
- **回访**：通过 RSS、内容更新或未来订阅机制提供持续价值。
- **反馈**：使用 GitHub Issues 和种子用户访谈形成闭环。
- **推广**：优先在原问卷渠道、开发者社区、产品发布平台和 AI 导航目录定向提交；平台名单具有时效性，应执行前复核。

```text
搜索/社区/目录 → 场景页 → 完成比较 → 分享或订阅 → 反馈 → 改进
```

流量不是唯一指标，应同时观察核心任务完成率、回访、反馈质量和自然分享。推广渠道、Search Console、Analytics、Newsletter 及具体阈值是否仍适用，均需在执行前人工确认。

## 决策关口

- **MVP 审查**：时效标注、来源、纠错入口和分享基础是否就位；
- **反馈评估**：是否收到有效纠错/反馈，用户是否通过多个渠道进入并完成核心任务；
- **架构演进**：自动化收益是否高于新增运维和合规成本，静态方案是否确实成为瓶颈。

本文件不能证明用户需求、SEO 效果或渠道可用性；这些结论必须由实际数据更新。
