# InfoCatcher 可行性研究报告（精简归档）

> **原定稿**：v0.9，2026-07-14—07-18
> **职责**：回答项目是否存在可行方案，以及在什么条件下继续。当前实现与任务不由本归档维护。

## 决策摘要

**结论：Conditional Go。** 以纯静态站（方案 1）快速验证，再根据反馈决定是否演进至 SPA + Serverless（方案 3）。方案 2（C++ Web 后端）不适合作为当前起点；方案 0 虽成本最低，但不解决问题。

| 问题 | 结论 |
|---|---|
| 技术 | 方案 1 可直接实现；方案 3 有条件可行 |
| 经济 | 不支持商业盈利判断；低现金成本与学习/开源价值匹配 |
| 组织 | 单人可运作，但持续投入和单点故障是核心限制 |
| 环境 | 可使用静态 Web、GitHub Pages 和公开/授权来源；采集须持续合规复核 |
| 成本收益 | 现金成本低，时间与维护成本高；收益主要是学习、用户和社区价值 |

## 已确认约束

| 约束 | 值 |
|---|---|
| 团队 | 1 名开发者 + Claude Code 辅助；产品、开发、测试、内容和运维均由开发者负责 |
| 技能 | C/C++，基础 HTML/CSS/JavaScript |

| 开发 API 预算 | 200—500 元 |

| 定位 | GitHub 开源免费项目，可能接受打赏，不以直接收入为决策依据 |
| 用户策略 | 先验证学生群体，Demo 后补充职场人士、开发者和创作者调研 |
| 数据策略 | 官方/API 优先，必要时人工整理并标注来源；成本和合规优先 |

## 证据与限制

证据包括 N=112 调查、W1 采集 PoC、8 个来源的 ToS 初查和 20+ 竞品快照。它们只能支持当时的项目级判断：

- 样本中 86.6% 为学生、89.3% 为 18—24 岁，集中于广东高校，不能推广到其他人群或全国市场；
- 22.5% 性别缺失采用确定性插补，性别交叉结论不可靠；
- 调查报告存在若干总数、百分比和题号口径矛盾；引用数字须回到 [resources/survey/](../../resources/survey/) 中的编码数据复核；
- 计划问卷 41 题与实际执行问卷 22 题不是同一版本，题号不能直接互引；
- PoC、端点、配额、价格和 ToS 结论只代表验证日期，不是永久许可或法律意见；
- 竞品功能和规模是时间敏感快照；
- 团队、财务和进度数据来自开发者自评与区间估算，没有外部专家、正式报价或持续运营证据。

因此报告中的用户痛点只可表述为“学生样本内观察到”，不能写成普遍市场已验证。

## 基线与候选方案

| 方案 | 描述 | 主要优势 | 主要限制 |
|---|---|---|---|
| 0 维持现状 | 不开发 | 零成本、零风险 | 不解决已观察到的问题 |
| 1 静态内容站 | 原生 Web + 静态 JSON + GitHub Pages | 快、免费、技能匹配、易审计 | 动态能力有限，持续内容维护成本高 |
| 2 C++ Web | 自研后端 + Web 前端 | 全栈学习和架构控制强 | 学习、周期、服务器和运维负担最高 |
| 3 SPA + Serverless | 前端应用 + 函数/API 代理 + 缓存 | 动态能力强、免服务器运维 | 学习和交付压力高于方案 1，存在平台依赖 |

## 成本与收益

历史估算（人民币，不含开发者薪资）：

| 成本 | 方案 1 | 方案 2 | 方案 3 |
|---|:---:|:---:|:---:|
| 开发期 API | 0—100 | 0—100 | 0—100 |
| 年度 TCO | 0—300 | 650—1500 | 50—400 |
| 三年 TCO | 0—900 | 1950—4500 | 150—1200 |

主要投入是约 150—300 小时开发时间和每周约 3—5 小时持续维护。直接经济收益预计为零或极低；可主张的收益仅包括软件工程与 AI 生态学习、降低用户查找/选择成本，以及形成公开可追溯的中文信息资源。这些非财务收益仍须通过任务完成率和真实反馈验证。

## 技术、数据与合规判断

- 静态 Web 和 GitHub Pages 技术成熟，适合作为最小起点；
- Serverless 可后续学习，不应阻塞 MVP；
- 数据应优先取自官方 API、文档和定价页，受限来源采用人工整理；
- MVP 不让 AI 自动生成评测结论；AI 只辅助检索、整理和草拟，开发者最终核验；
- 评测须公开方法、来源和利益声明，不接受厂商赞助；
- MVP 无账户和敏感数据，偏好若存在仅存 localStorage；引入账户/UGC 后须重新评估隐私、安全和审核；
- 事实信息可在附来源的前提下整理，但不得全文搬运受版权保护内容或暗示厂商背书；
- 原报告对 B站内部 API、网页抓取和“0 高风险”的结论已被后续策略收紧，不能作为当前采集许可。

## 风险登记

风险等级为概率 P × 影响 I（1—5）。

| 编号 | 风险 | P×I | 触发信号 | 核心缓解 | 残余风险 |
|:---:|---|:---:|---|---|---|
| R1 | 采集违反 ToS/版权边界 | 3×4=12 | 投诉、DMCA、封禁、限流 | 官方来源优先、精确引用、人工降级、立即停用争议源 | 低，但须持续复核 |
| R2 | 信息快速过时 | 5×4=20 | 用户报告价格/功能过期，大版本集中发布 | 更新时间、来源、免责提示、纠错、受控自动化 | **中—高，无法消除** |
| R3 | 一个月 MVP 延期 | 3×4=12 | 技术验证、页面或内容连续落后 | P0 优先、缩减覆盖、预留缓冲 | 低—中 |
| R4 | 用户不使用/回访 | 4×3=12 | 访问和反馈不足 | 种子渠道、可分享场景、SEO、访谈 | 中 |
| R5 | 公正性被质疑 | 3×4=12 | 用户/厂商质疑或施压 | 方法透明、证据、利益声明、复核和更正记录 | 低—中 |
| R6 | 开发者投入不可持续 | 3×5=15 | 一周无进展、里程碑连续延期 | 小步交付、公开记录、范围控制、可归档发布 | 中 |
| R7 | 静态架构限制演进 | 4×2=8 | 动态能力请求频繁且静态替代不足 | 方案 1→3 的预设演进关口 | 低 |

“所有残余风险均为中或以下”是原报告内部误述；R2 明确仍为中—高，是最大长期风险。

## 方案评分

权重反映个人开源项目的技术和时间硬约束：

| 维度 | 权重 | 方案 0 | 方案 1 | 方案 2 | 方案 3 |
|---|:---:|:---:|:---:|:---:|:---:|
| 学习/战略价值 | 10% | 1 | 2 | 5 | 4 |
| 技术可行性 | 20% | 5 | 5 | 2 | 4 |
| 经济可行性 | 10% | 5 | 5 | 3 | 5 |
| 运营组织 | 10% | 5 | 3 | 2 | 4 |
| 进度 | 20% | 5 | 5 | 2 | 3 |
| 法律/IP | 5% | 5 | 4 | 4 | 4 |
| 数据安全 | 5% | 5 | 5 | 4 | 5 |
| 市场用户 | 15% | 1 | 3 | 4 | 4 |
| 可维护性 | 5% | 5 | 4 | 3 | 4 |
| **加权总分** | 100% | **4.00** | **4.10** | **2.95** | **3.95** |

评分规则：1=不可行/风险极高，3=基本可行但有明显风险，5=高度可行。方案 0 尽管分数高，因不解决问题/收益不可验证被否决；方案 2 的周期和运维不匹配；方案 3 接近 Go，但作为起点增加交付风险。

敏感性分析显示：降低进度权重、提高学习价值时，方案 1 与 3 可并列；提高市场权重或降低方案 3 进度分时，方案 1 仍领先。结论对合理权重变化较稳定，但评分依赖主观估计，不能替代实际反馈。

## Conditional Go 条件

| 编号 | 条件 | 历史判定 |
|:---:|---|---|
| C1 | 信息采集 PoC 达到预设覆盖门槛 | 已通过；报告一处写 ≥4/5、另一处写至少 3 个，口径不一致，以原验收记录为准 |

| C5 | 上线两周内获得至少 10 条有效反馈 | 尚待真实用户验证 |

## 未决证据

- 非学生用户的需求强度和差异；
- 可用性、任务完成率、信任与持续回访；
- 实际维护工时、采集失败率和自动化收益；
- 正式法律/合规意见；
- UI/UX 能力和无障碍表现；
- Serverless 迁移是否确有必要。

## 原始决策输入

2026-07-14 的问答确认了单人团队、200—500 元预算、不使用 LLM/Agent API、一个月 MVP/两个月基本完成、API + 人工整理的数据策略、GitHub 开源免费定位，以及先学生后补其他群体的调研顺序。这些回答已体现在本报告约束中，原始措辞不再重复。
