# YouTube 数据获取方案

> **原状态**：待实施
> **创建**：2026-07-22
> **关联**：B05（API Key 申请）、B14（AI 热点聚合）

## 方案总览

采用 **免费分层策略**：RSS Feed + 官方 API + Supadata Free 三层互补，零成本获取 YouTube AI 热点数据。

```
RSS Feed ──→ 拉取所有新视频 ID + 标题（免费，无限）
     │
     └─ 48 条重点视频 → 官方 API（元数据+字幕+评论，9,744 配额）

Supadata Free（100 条/月）→ 备用字幕 + 热点突发
```

## 数据源明细

| 层 | 来源 | 成本 | 额度 | 用途 |
|:--:|:----|:----:|:----|:------|
| ① | YouTube RSS Feed | 免费 | 无限 | 获取频道新视频 ID + 标题 + 发布时间 |
| ② | YouTube Data API v3 | 免费 | 10,000 配额/天 | 视频元数据、字幕下载、评论、频道信息 |
| ③ | Supadata Free | 免费 | 100 条/月 | 备用字幕/转录（独立于官方 API） |

## 每日配额分配

| 项目 | 计算 | 消耗配额 |
|:----|:----|:--------:|
| 48 条视频（元数据 `videos.list` + 字幕 `captions.download`） | 48 × (1 + 200) | **9,648** |
| 48 条视频各抓 ≤200 条评论（`commentThreads.list`，100条/次，2次/条） | 48 × 2 | **96** |
| **已用** | | **9,744** |
| **剩余** | | **256** |

### 剩余 256 配额的用途

| 用途 | 消耗 | 说明 |
|:----|:---:|:------|
| `channels.list` 查频道信息 | 1/次 | 首次缓存后日耗 ≤ 30 |
| `search.list` 发现新频道/新内容 | 100/次 | 按需使用 |
| 其他零散查询 | ≤ 10/天 | 纠错、验证 |

> 频道缓存建立后，256 配额日均消耗约 30-50，仍有充足余量。

## Supadata Free 月度分配

Supadata Free 作为独立备用层，不占用官方 API 配额：

| 用途 | 额度 | 说明 |
|:----|:---:|:------|
| 热点突发获取 | 60 条/月 | 突发 AI 新闻时快速拉取官方发布的新视频字幕 |
| 日常弹性余量 | 40 条/月 | 超出每日 48 条上限时兜底 |
| **合计** | 100 条/月 | Free 额度用满 |

## 单条视频数据获取流程

```
1. RSS Feed 推送 → 拿到 videoId + 标题 + 发布时间
2. videos.list(id=videoId, part="snippet,statistics,contentDetails")
   → 标题、描述、标签、时长、发布时间、频道 ID、观看数/点赞数
   → 消耗 1 配额
3. captions.download(id=videoId) → 字幕全文
   → 消耗 200 配额（自动字幕覆盖率高，跳过 captions.list 省 50）
   → 准确率约 60-70%，热点聚合够用
4. commentThreads.list(videoId=videoId, maxResults=100) × 2
   → 获取 ≤200 条评论，用于热度判断和舆论分析
   → 消耗 2 配额
```

## 技术约束

| 约束项 | 说明 |
|:----|:------|
| 字幕语言 | 自动字幕仅英语和主流语言可用，小语种可能缺失 |
| 字幕延迟 | 视频上传后数小时内字幕方可下载 |
| 准确率 | ASR 自动字幕约 60-70%，不做精确引用则够用 |
| IP 限制 | 未确认 Google 是否对非官方 IP 爬取做限制 |
| ToS 合规 | 三层均为合规接口（RSS/官方 API/商业 API），不依赖逆向爬虫 |

> **原状态**：待实施

## 方案选择

X 官方 API 2026 年起取消免费层，按量付费 $0.005/条，对学生项目成本过高。

### 已排除的开源方案

评估了三个 GitHub 开源爬虫（twikit、tweety、twscrape）后决定不使用：

| 问题 | 说明 |
|:----|:------|
| 登录即封 | 多个用户报告仅登录 Client 类、无任何操作就被标记为可疑活动 |
| 10-15 次搜索就封号 | twikit Discussion #291 实测报告 |
| 非频率问题 | X 检测的是自动化登录行为本身，不是请求频率 |

> **结论**：X 和 YouTube 不同——开源爬虫在 X 这边走不通。$2/月换专业团队处理反检测和代理轮换，比自己写爬虫被封号划算。

### 选用方案：TwitterAPI.io 第三方 API

| 对比 | 官方 X API | TwitterAPI.io |
|:----|:---:|:---:|
| 读取推文 | $0.005/条 | $0.15/1,000 条 |
| 读取用户 | $0.010/条 | $0.18/1,000 条 |
| 折合单价 | — | **低 33 倍** |
| 注册门槛 | 1-2 周审批 | 5 分钟，无需信用卡 |
| 免费试用 | 无 | 有（额度未公开） |
| 合规性 | 官方 | 第三方爬虫（参阅下方风险说明） |

## 法律与技术风险

### 法律判例支撑

2024 年 5 月，美国联邦法院驳回 X Corp 对数据抓取公司 Bright Data 的起诉，裁定：**公开推文属于公共领域，社交媒体公司不能垄断公开数据的使用权**。同期 Meta 对 Bright Data 的同类诉讼也被驳回。

对本项目的影响：InfoCatcher 为个人开源项目，仅抓取 AI 官方账号的**公开推文**，在现有判例下法律风险极低。

### 技术风险

| 风险 | 可能性 | 应对 |
|:----|:---:|:------|
| 服务被 X 封禁 | 中 | 切换其他第三方 API 或回退官方 API |
| 数据格式变更 | 中 | 适配层隔离，统一内部数据结构 |
| 服务涨价 | 低 | 按量付费，无长期合约锁定 |

> 实在不行就换——第三方 API 市场有多个备选（Apify、SociaVault 等）。

## 数据获取流程

```
1. 维护 AI 账号列表 → 优先缓存稳定的 userId
2. TwitterAPI.io 读取用户最新推文（官方文档核验：2026-07-23）
   → `GET /twitter/user/last_tweets?userName=OpenAI&cursor=`
   → Header：`X-API-Key: ...`
   → 每页最多 20 条，支持 cursor；userId 与 userName 二选一，优先 userId
3. 为控制约 300 条/日成本，当前每日轮转处理最多 15 个账号（31 个来源约 3 天覆盖一轮）
4. 筛选 AI 热点相关推文
   → 关键词匹配、时间分层、来源与互动信号
5. 提取有用信息存入静态 JSON
   → 推文内容 + 时间 + 互动量 + 链接 + 溯源/评分依据
```

> 官方接口文档：[Get User Last Tweets](https://docs.twitterapi.io/api-reference/endpoint/get_user_last_tweets)。旧方案中的 `/v1/twitter/user-tweets?handle=...&limit=...` 已不再作为实现依据。

|:----|:---:|:---:|

> **原状态**：历史候选方案，当前暂停实施（2026-07-26）
> **当前MVP策略**：B站保留为热点内容类型；默认通过人工精选录入，正常 `all` 构建不访问B站网络。RSSHub仅保留为显式诊断入口，遇到Provider/Cloudflare阻断立即熔断。

## 当前结论（覆盖本节早期推荐）

早期材料将公共或自部署 RSSHub 视为主要自动化路径；真实 Actions 已确认公共 `rsshub.app` 的B站视频、动态和专栏路由均遭遇 Cloudflare 403。进一步核对 RSSHub 当前实现后，B站路由还可能调用站内接口、依赖Cookie或浏览器模式。因此本项目当前不把RSSHub、RSSHub-MCP、自部署实例、Cookie、内部API、FlareSolverr或多实例轮换作为已批准的自动采集方案。

本节后续内容保留为可行性历史材料；其中“推荐自部署 RSSHub”等表述不代表当前计划。

## 早期方案背景（历史记录）

### 已死的路

B站对第三方数据获取的打击力度是三个平台中最严的：

| 时间 | 事件 | 结果 |
|:----|:------|:------|
| 2025.07 | 第三方客户端 PiliPala 收到律师函 | 停止更新 |
| **2026.01.28** | **bilibili-API-collect**（20k+ stars）收到律师函 | **永久删库** |
| **2026.07.06** | **bilibili-api** Python SDK 收到律师函 | **永久关停** |

律师函指控核心：“通过技术手段对非公开 API 接口进行系统性收集、整理，以文档和代码形式向不特定公众传播”，涉嫌违反《反不正当竞争法》《网络安全法》。B站开放平台面向内容创作者/机构，提供稿件分发能力，**不提供视频元数据检索的开发者 API**。

### 早期判断（已被当前事实覆盖）

早期材料曾将 RSSHub 描述为抓取公开网页的唯一合规免费路径；该判断未覆盖当前 RSSHub B站路由的实际实现，也未经过本项目真实 Actions 验证。请以本节开头的“当前结论”为准。

## 深度数据补充方案（历史候选）

### 字幕获取

| 方案 | 方式 | 成本 | 自动化 |
|:----|:------|:----:|:---:|
| **BibiGPT** | 粘贴B站链接 → 下载字幕（SRT/VTT/TXT） | 免费层可用 | ❌ 手动 |
| DownSub | 同上，纯字幕下载 | 免费 | ❌ 手动 |
| **TikHub API** | `/api/v1/bilibili/app/fetch_one_video` | 付费 | ✅ API |

BibiGPT 有个额外优势：视频没有字幕时，会用 AI 语音转文字自动生成字幕。

### 播放量/热度数据

B站内部 API（`api.bilibili.com/x/space/arc/search`）确实返回播放量、弹幕数、评论数等数据，但这就是 2026 年两封律师函针对的东西——**直接调用 B站内部 API = 踩红线，不能走**。

| 方案 | 风险 | 成本 |
|:----|:---:|:---:|
| B站内部 API | 🔴 律师函风险 | 免费 |
| **TikHub API** | 🟡 第三方扛合规风险 | 付费 |

### TikHub：收费但合规的深度 API

[TikHub](https://tikhub.io) 是国内第三方社交数据平台，提供 B站 web/app 双系列 API。和 TwitterAPI.io 一样的逻辑——他们扛反爬和合规风险，你付钱拿数据。

| 接口 | 返回数据 |
|:----|:------|
| `fetch_one_video` | 视频元数据 + **播放量/弹幕数/评论数/投币/收藏/分享** |
| `fetch_video_comments` | 评论内容（含子回复） |
| `fetch_user_info` | UP主粉丝数/播放量/获赞数 |
| `fetch_user_videos` | UP主视频列表（含每条视频统计） |
| `fetch_general_search` | 搜索结果（含视频+用户） |

**定价**：TikHub 采用按量付费/订阅制，具体价格未在文档页公开，需联系或注册后查看。

# 知乎数据获取方案

> **原状态**：待定（评估中）
> **创建**：2026-07-22
> **关联**：B14（AI 热点聚合）

## 知乎与其他平台

| 平台 | 内容形态 | 对 AI 热点的价值 |
|:----|:------|:------|
| YouTube | 长视频 | 深度评测、教程、行业分析 |
| X(Twitter) | 短推文 | **AI 消息首发地**，速度最快 |
| Bilibili | 中长视频 | 中文 AI 深度内容、UP主生态 |
| **知乎** | **问答/专栏/想法** | **AI 话题讨论、技术问答、专家观点** |

知乎的独特价值在于“问题驱动”——同一 AI 话题下汇集多方观点和深度回答，和视频平台形成互补。

## 可行路径分析

### 官方 API

知乎**没有面向开发者的公开数据 API**。和 YouTube 不同，知乎没有提供类似 YouTube Data API v3 的数据检索接口。

### RSSHub

RSSHub 有 10+ 个知乎路由，但情况比 B站差得多：

| 路由 | 功能 | 状态 |
|:----|:------|:----|
| `/zhihu/hotlist` | 热榜 | ⚠️ 不稳定 |
| `/zhihu/daily` | 知乎日报 | ⚠️ 不稳定 |
| `/zhihu/people/activities/:id` | 用户动态 | 🔴 高频报错 |
| `/zhihu/people/answers/:id` | 用户回答列表 | ⚠️ 不稳定 |
| `/zhihu/people/posts/:id` | 用户文章列表 | ⚠️ 不稳定 |
| `/zhihu/column/:id` | 专栏文章 | ⚠️ 不稳定 |
| `/zhihu/pin/daily` | 每日想法 | ⚠️ 不稳定 |
| `/zhihu/question/:questionId` | 问题新回答 | ⚠️ 不稳定 |
| `/zhihu/topic/:topicId` | 话题新内容 | ⚠️ 不稳定 |
| `/zhihu/weekly` | 知乎周刊 | ⚠️ 不稳定 |

| 问题 | 详情 |
|:----|:------|
| **需要 Cookie** | 必须维护 `d_c0` 和 `__zse_ck` 两个 Cookie，且会定期过期 |
| **反爬严格** | RSSHub 官方 FAQ 明确标注知乎“反爬严格”，公共实例不保证可用 |
| **高报错率** | `zhihu/people/activities` 在 RSSHub 公共实例的 Hot Error Routes 中排前列 |

### 第三方数据平台与开源爬虫

TikHub 等平台的接口目录中**未见知乎相关 API**。GitHub 上存在知乎爬虫项目，但考虑到知乎同样受中国法律管辖、反爬投入更激进以及人工维护 Cookie 的运维成本，**不建议走这条路**。

## 结论：暂不纳入一期

| 维度 | 评估 |
|:----|:------|
| 数据价值 | 🟡 有（AI 话题讨论/专家观点），但非“热点聚合”强需求 |
| 获取难度 | 🔴 高——比 B站更难，需要 Cookie 且不稳定 |
| 合规路径 | 🔴 无官方 API，RSSHub 也处在灰色地带 |
| 维护成本 | 🔴 高——Cookie 定期失效，需人工介入 |

**建议**：一期（MVP/B14）聚焦 YouTube + X + Bilibili 三个平台。知乎作为二期候选，等以下条件任一成熟后再评估：

- 知乎推出官方数据 API；
- RSSHub 知乎路由稳定性显著改善；
- 第三方平台（如 TikHub）新增知乎数据覆盖；
- 项目有条件投入人力维护 Cookie 和反爬适配。

## 如果一定要现在接入（历史兜底方案，不作为当前建议）

```
1. 浏览器手动登录知乎 → 提取 Cookie（d_c0 + __zse_ck）
2. 自部署 RSSHub（配置 Cookie）
3. 仅订阅热榜 + 特定 AI 话题
4. Cookie 过期时重新提取并更新配置
```

成本：$0，但需要定期手动维护 Cookie（估计每 1-2 周一次）。数据产出：热榜中 AI 相关条目 + 指定话题下的新内容。

> **后续**：当三平台方案稳定运行后，根据实际数据质量评估是否需要补充知乎内容。
