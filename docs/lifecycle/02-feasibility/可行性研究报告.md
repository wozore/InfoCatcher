## 此阶段主要任务及答案

### 1. 技术上能不能实现？

**答案：能实现。**

推荐的实施路径是“方案 1 静态内容站起步，验证后再演进到方案 3 SPA + Serverless”。该路径使用成熟的 Web 技术和免费托管服务，与开发者已有的 HTML/CSS/JavaScript 能力基本匹配，不要求在 MVP 阶段掌握复杂后端框架。

主要证据：

- W1 信息采集 PoC 已通过：Bilibili API 3/5 个测试端点可用，网页采集 3/5 个目标网站可直接获取，其余网站可改用官方 API、人工整理或替代数据源；
- 主要数据源均存在可行获取路径，信息采集不是不可克服的技术障碍；
- GitHub Pages、静态 JSON、浏览器端搜索等核心技术均成熟，方案 1 的技术风险较低；
- 方案 3 所需的 Serverless 能力存在学习成本，但可在静态 MVP 验证后渐进引入，不会阻塞首个版本。

**技术可行性结论：✅ 可行。** 方案 1 可直接实施；方案 3 有条件可行；方案 2（C++ 自研 Web 后端）在当前时间约束下风险过高，不建议作为起点。

### 2. 经济上是否值得？

**答案：从商业盈利角度暂时不能证明值得；从个人学习、用户价值和开源公益角度值得。**

本项目定位为开源免费项目，没有可靠的直接收入来源，打赏收入也不可预测，因此不能以投资回报率证明其商业价值。但是项目现金支出很低，预算可以覆盖，且能产生明确的非财务收益。

| 判断角度 | 结论 | 依据 |
|----------|:---:|------|
| 是否做得起 | ✅ 是 | 可用预算 200-500 元；方案 1 预计开发期现金支出 0-100 元，GitHub Pages 可免费托管 |
| 是否适合作为盈利项目 | ❌ 暂不能证明 | 开源免费，无稳定收入模式，打赏不可预测 |
| 是否具有学习价值 | ✅ 是 | 能覆盖问题定义、可行性研究、需求、设计、编码、测试、维护等完整软件工程实践 |
| 是否具有用户价值 | ✅ 是 | 112 份调查显示 63.4% 的用户曾选错 AI 工具，60.7% 认为信息分散，72.3% 缺少场景化真实表现信息 |
| 是否具有社区价值 | ✅ 有条件 | 竞品分析显示“场景化深度对比 + 透明评测方法论 + 开源免费”仍具有差异化空间 |

**经济可行性结论：⚠️ 有条件值得。** 如果目标是短期盈利，则不建议投入；如果目标是学习完整的软件开发过程并向用户提供开源工具，则低现金成本与较高非财务收益相匹配，值得继续。

### 3. 组织和环境是否允许？

**答案：允许，但依赖单人开发者持续投入，并须遵守数据来源和内容使用边界。**

组织方面，本项目由 1 名开发者负责产品、开发、测试、内容和运维，Claude Code 提供辅助。单人团队没有跨部门协调成本、决策速度快，但也形成明显的单点故障：开发者一旦时间不足或失去动力，项目可能停滞。

环境方面：

- **人员与时间**：开发者已确认每周可投入至少 15 小时，能够支撑方案 1 的 MVP；
- **技术环境**：GitHub Pages、公开 API、静态 Web 技术和 Serverless 免费额度均可获得；
- **运营环境**：GitHub Issues 和开源协作可以支持轻量反馈与内容纠错，但初期仍主要依赖开发者维护；
- **法律与合规环境**：8 个主要数据源的 ToS 初步审查结果为 0 个高风险源；项目可通过“官方 API 优先、仅整理事实性信息、人工采集受限来源、注明出处、不搬运完整受版权保护内容”降低风险；该审查属于项目级风险筛查，不等同于正式法律意见；
- **能力缺口**：无专职 UI/UX、法务、内容审核和运维人员，但在静态 MVP 范围内不会构成阻塞条件。

**组织与环境可行性结论：⚠️ 有条件允许。** 在控制范围、坚持合规采集并维持每周投入的前提下可以实施；主要限制来自单人维护能力，而不是外部环境禁止。

### 4. 项目的成本、收益、风险如何？

#### 成本

| 成本类型 | 估算或说明 |
|----------|------------|
| 可用开发预算 | 200-500 元 |
| 方案 1 开发期现金支出 | 0-100 元 |

| 隐性维护成本 | 每周约 3-5 小时的信息更新、核验和反馈处理 |

#### 收益

- **直接经济收益**：预计为零或极低，可能只有不确定的打赏；
- **学习收益**：积累完整软件生命周期、前端开发、Serverless、数据采集、开源协作和 AI 工具评测经验；
- **用户收益**：降低查找、比较和选择 AI 工具的时间成本与试错成本；
- **社区收益**：形成公开、可追溯、可共同维护的中文 AI 工具信息资源。

#### 主要风险

| 优先级 | 风险 | 初始等级 | 当前判断 |
|:---:|------|:---:|----------|
| 1 | 信息更新跟不上 AI 行业变化速度 | 极高（20） | 项目最大长期风险；需以来源标注、更新时间、用户纠错和后续自动采集缓解 |
| 2 | 开发者时间或动力不可持续 | 高（15） | 单人项目的根本风险；需缩小范围、分阶段交付和开源协作缓解 |
| 3 | 网页采集、转载和 ToS 风险 | 中（12） | C3 初步审查已通过，但必须坚持 API 优先、合理引用和人工整理边界 |
| 4 | 1 个月 MVP 不能按时完成 | 中（12） | 方案 1 可降低风险；必要时缩减内容覆盖，优先保证核心验证 |
| 5 | 用户不使用或不持续使用 | 中（12） | 需在 MVP 上线后通过 C5（两周内至少 10 条有效反馈）验证 |

**成本—收益—风险综合结论：**项目现金成本低，但时间和持续维护成本高；直接经济收益弱，但学习、用户和社区收益明确；主要风险可以通过控制范围、分阶段验证、人工审核和开源协作降低，但不能完全消除。因此不适合直接作出无条件 Go 决策。

# 1. 执行摘要

## 1.1 项目背景

本项目（代号 InfoCatcher）旨在解决用户在 AI 工具信息获取与选择过程中面临的系统性困难——信息分散在多平台、真伪难辨、更新过快、缺少场景化对比、付费决策缺乏依据。

## 1.2 核心结论

**建议：Conditional Go — 附条件继续。**

用户问题真实存在且强度较高（112 份调查证据支持）。在全部约束条件（1 人团队、200-500 元预算、1 月 MVP、开源免费）下，**推荐方案 1（轻量级静态内容站）作为 MVP 起点，渐进演进到方案 3（SPA + Serverless）作为 v1.0 目标架构**。

综合评分：方案 1 = 4.10（Go），方案 3 = 3.95（Conditional Go），方案 2 = 2.95（Re-evaluate），方案 0 = 一票否决。

## 1.3 推荐方案

**"静态起步，渐进增强"**：先用 HTML/CSS/JS + GitHub Pages 在 3-4 周内上线 MVP（AI 工具数据库 + 场景化对比 + 浏览器端搜索），收集用户反馈后，在 W5-W9 逐步引入 Serverless 后端实现动态功能（API 代理、自动采集、推荐引擎），最终以 SPA + Serverless 架构发布 v1.0。

## 1.4 投资预算

| 类别 | 估算 |
|------|------|
| 开发阶段 API 成本 | 0-100 元（一次性） |
| 年度运维成本（方案 1） | 0 元（GitHub Pages 免费） |
| 年度运维成本（方案 3） | 0-200 元（Serverless 免费额度内） |
| 三年 TCO | 0-900 元（方案 1）/ 150-1200 元（方案 3） |
| **主要投入** | **开发者时间（约 150-300 小时 / 2 个月）** |

## 1.5 主要收益

本项目定位为**开源免费项目**，无直接经济收益。收益体现为：
- **学习收益**（开发者）：全栈开发实践、AI 工具生态深度认知、开源项目维护经验
- **用户价值**：降低 AI 工具选择的搜索成本和决策错误率（63.4% 的用户曾选错工具）
- **社区价值**：填补中文 AI 工具信息聚合领域的开源空白

# 4. 项目问题定义

> 本章内容主要提取自《AI信息获取软件开发.md》，并对照调查结果进行验证。

## 4.1 业务现状与痛点

### 4.1.1 要解决的核心问题

**用户（尤其是国内用户）在发现、理解、比较和选择 AI 工具时面临系统性困难。** 这不是单一问题，而是由七个相互关联的根因构成的复合问题：

1. **AI 工具和模型更新速度过快**——用户刚了解一个工具，信息已过时
2. **AI 信息来源高度分散**——官方、媒体、社区、排行榜互不联通
3. **缺少统一的评判标准**——benchmark 分数无法翻译为场景适用性
4. **国内外工具在访问、语言、价格、使用门槛上存在结构性差异**
5. **宣传信息与真实能力之间存在显著落差**
6. **用户不知如何将 AI 工具对应到自己的真实需求**（"工具—场景"映射缺失）
7. **信息过载、不可信和滞后三重叠加**

### 4.1.2 问题验证状态

| 假设问题 | 调查验证结果 | 证据强度 |
|----------|-------------|----------|
| 信息太分散 | Q8 中 60.7% 选择，Q18 均值 3.24/5 | **强**（在学生群体中） |
| 软文太多、真假难辨 | Q8 中 45.5% 选择，仅 10.7% 信任网上评测 | **强**（在学生群体中） |
| 更新太快、信息过时 | Q8 中 43.8% 选择，Q19 中 23.2% 认为是最大问题 | **强**（在学生群体中） |
| 宣传与实际不符 | 51.8% 有过此经历 | **强**（在学生群体中） |
| 不知道工具适合什么任务 | Q18 均值 2.91/5，评分相对较低 | **中**（可能被低估，学生主要用少数工具） |
| 缺少场景化真实表现 | Q12 中 72.3% 最缺此信息 | **强**（在学生群体中） |
| 是否值得付费不确定 | Q18 均值 3.46/5（所有维度最高） | **强**（在学生群体中） |
| 选错工具的普遍性 | 63.4% 曾选错 | **强**（在学生群体中） |

### 4.1.3 不做项目的影响

- 用户继续依赖碎片化社交信息做决策，选择质量和效率低下
- "因不了解而选错→因选错而失望→因失望而放弃"的恶性循环持续
- 用户对 AI 工具整体信任度持续降低
- 国产 AI 工具与海外工具的信息不对称加剧

## 4.2 开发目标与成功指标

**开发目标**（来自问题定义文档）：提高对 AI 工具的熟悉程度和使用能力。

**成功指标（可行性层面，用于验证"项目收益可验证"——一票否决关联项）**：

| 目标维度 | 指标 | 当前基线（调查证据） | 目标值（MVP 后观察） |
|----------|------|----------|--------|

# 8. 候选方案说明

> 以下为候选方案的可行性层面描述，用于支撑方案比较与决策。各方案的**技术栈细节、总体架构、演进路径**已迁移至 **《总体设计/总体设计说明书.md》**（④ 总体设计）。

## 8.1 方案 1：轻量级静态内容站（GitHub Pages + 手动维护）

**核心思路**：利用静态站点 + Markdown 内容文件构建 AI 工具信息聚合站，API 辅助采集 + 人工整理。
**成本**：零托管费；**周期**：1-3 周。

**优势**：零服务器成本、匹配开发者 HTML/CSS/JS 技能、Git 深度整合、可渐进增强。
**劣势**：内容需手动更新、无后端动态功能、与"软件项目"定位略有偏差。

## 8.2 方案 2：C++ 后端 + Web 前端的自研软件

**核心思路**：C/C++ 后端 + HTML/CSS/JS 前端的完整 Web 应用，后端负责采集/处理/API。
**成本**：云服务器约 50-100 元/月；**周期**：1.5-3 个月。

**优势**：发挥 C/C++ 核心技能、完整后端能力、架构可控、学习价值高、性能优异。
**劣势**：C++ Web 框架学习曲线、生态不成熟、开发效率低、服务器运维负担、1 月 MVP 风险高。

## 8.3 方案 3：纯前端 SPA + Serverless/API 代理的混合方案

**核心思路**：前端 SPA + Serverless（Cloudflare Workers/Vercel）做 API 代理和数据缓存，避免传统服务器。
**成本**：Serverless 免费额度内零成本；**周期**：1-2 个月。

**优势**：免运维、免费额度充足、前端为主匹配技能、可渐进增强、部署自动化。
**劣势**：Serverless 学习成本、冷启动延迟、仍需后端逻辑、平台依赖（迁移成本低）。

## 8.4 候选方案初步对比

| 维度 | 方案 0：维持现状 | 方案 1：静态内容站 | 方案 2：C++ 自研 Web | 方案 3：SPA + Serverless |
|------|:---:|:---:|:---:|:---:|
| 解决用户问题 | ❌ 不解决 | ⚠️ 部分（信息聚合） | ✅ 较完整 | ✅ 较完整 |
| 前期成本 | 零 | 零 | 50-100 元/月（服务器） | 零（免费额度内） |
| 开发周期 | N/A | 1-3 周 | 1.5-3 个月 | 1-2 个月 |
| 匹配开发者技能 | N/A | ✅ HTML/CSS/JS | ⚠️ C++ 熟悉但需学 Web 框架 | ✅ 前端为主 + 少量后端 |
| 技术风险 | 零 | 极低 | 中（C++ Web 生态） | 低-中（Serverless 学习） |
| 可规模化 | ❌ | ⚠️ 受限于手动维护 | ✅ 高 | ✅ 高 |
| 运维负担 | 无 | 极低（GitHub Pages） | 中（服务器维护） | 低（Serverless 免运维） |
| 作为学习项目 | 无价值 | 低（偏内容运营） | ✅ 高（全栈实践） | ✅ 中-高（现代架构实践） |
| 长期演进能力 | N/A | ⚠️ 受限于静态架构 | ✅ 强（自有后端） | ✅ 较强 |

> 注意：以上为定性初判，详细加权比较见 §17。方案技术栈与架构细节见《总体设计/总体设计说明书.md》。

# 9. 技术可行性

## 9.1 团队技术能力

| 角色 | 人员 | 技能 | 本项目匹配度 |
|------|------|------|:---:|
| 后端开发 | 1 人（开发者本人） | C/C++ | ⚠️ 需学习 C++ Web 框架 |
| 前端开发 | 同上 | HTML/CSS/JS（基础） | ✅ 匹配静态页面和基础交互 |
| AI 辅助 | Claude Code | 代码生成、调试、架构建议 | ✅ 可显著提升开发效率 |
| 产品/设计/测试 | 同上（开发者兼） | — | ⚠️ 单人多角色，精力分散 |

**评估**：开发者具备编程基础，但 C/C++ 用于 Web 开发并非主流选择。HTML/CSS/JS 能力可覆盖前端展示层。Claude Code 可作为生产力倍增器，部分弥补单人团队的技能缺口。最大的技术风险在于：**开发者是否愿意且能够在项目周期内学会一个 C++ Web 框架（如 Drogon/Crow）并高效使用**。

## 9.2 技术栈评估

> 各方案的技术栈细节与架构评估已迁移至《总体设计/总体设计说明书.md》§3。本报告保留可行性层面的技能匹配度与开发效率判断（用于支撑 §17 评分）：

| 方案 | 技能匹配度 | 开发效率 | 运行性能 |
|------|:---:|:---:|:---:|
| 方案 1：静态内容站 | 高 | 高 | 高（CDN） |
| 方案 2：C++ 自研 Web | 中（需学 C++ Web 框架） | 低-中 | 极高 |
| 方案 3：SPA + Serverless | 中-高（需学 Serverless） | 中-高 | 高 |

## 9.3 数据获取技术路径 [部分剥离 → ④ 总体设计]

基于用户明确的方案偏好（API + 爬虫 + 手动整理混合）：

| 数据类型 | 获取方式 | 技术可行性 | 成本 |
|----------|----------|:---:|------|
| AI 热点新闻/动态 | X API、YouTube API、Bilibili API | ✅ 高（官方 API 成熟） | 免费额度内零成本 |
| AI 工具基本信息 | 网页抓取 + 手动整理 | ⚠️ 中（需反爬应对、页面结构变化） | 零（时间成本） |
| AI 工具价格/权益 | 网页抓取 + 手动更新 | ⚠️ 中（价格变化频繁） | 零（时间成本） |
| Benchmark 数据 | 排行榜 API（LMSYS、Artificial Analysis） | ✅ 高（公开 API） | 零 |
| AI 术语/知识库 | 网页抓取 + 手动整理 | ✅ 高（静态内容，变化少） | 零（时间成本） |

**关键判断**：对于本项目规模，"抓取 + 手动整理"方案成本**远低于**采购第三方数据（后者通常需数千元/年起）。以 1-2 人团队、覆盖 30-50 个主流 AI 工具计，手动维护的初期投入约每周 3-5 小时。

## 9.4 关键技术风险

1. **C++ Web 框架学习成本**（方案 2 特有）：Drogon/Crow 等框架的学习周期约 1-2 周，可能挤压 MVP 开发时间
2. **网页抓取稳定性**：目标网站改版导致抓取失效，需监控和适配
3. **API 配额限制**：免费 API 通常有日/月调用上限（如 X API 免费层 1500 次/月），对高频采集场景可能不足
4. **信息更新时效性**：AI 行业周更/月更，内容维护需要持续的人工投入

> **建议**：MVP 阶段优先选择方案 1 或方案 3（避免 C++ Web 框架学习曲线），同时用少量时间对方案 2 做技术 Spike（2-3 天验证 C++ Web 框架可行性），为后续演进做准备。

| 准确率与时效性 | 信息过期风险极高（AI 行业周更），需设计自动+人工双重更新机制 |
| 模型幻觉 | 如使用 AI 辅助生成评测内容，需人工审核 |
| API/模型供应商依赖 | 如使用大模型辅助评测，需考虑成本和稳定性 |
| 提示词注入安全 | 如包含用户评论/UGC 功能，需防护 |
| 人工复核 | 评测结果的准确性需人工抽查机制 |

> **关键未知 → 方法论立场（2026-07-18 确立，F2）**：是否使用 AI 来辅助评测 AI 工具（"AI 评测 AI"）？本项目确立如下立场：
> - **MVP 阶段：不使用 AI 自动生成评测结论**。所有评测内容为人工整理 + 公开数据（benchmark、官方文档），AI（Claude Code）仅用于**辅助**（资料检索、格式整理、草稿拟写），**不作为评测主体**，最终判断由开发者人工把关。
> - **原因**：① 用户信任度仅 10.7%（Q10），引入"AI 评测 AI"会加剧黑箱感；② 模型幻觉风险与系统性偏见难控；③ 团队无 LLM/Agent API 预算（Q2 明确排除此类支出）。
> - **v1.0+ 可选探索**：若引入 AI 辅助，必须满足三个前提——公开提示词与方法论、人工抽查可追溯、与人工评测并存对比（不替代）。在此之前此条不阻塞可行性结论。
> - **可行性判断**：AI 特定维度全部可控——信息源合法性有 C3 把关；时效性有更新流水线（⑧ 维护）；其余通过人工复核 + 透明方法论缓解。本项目"定位为人工聚合 + 透明方法论"足以化解元风险。

# 16. 风险分析与缓解措施

## 16.1 风险等级定义

采用方法文档标准：

| 概率 | 说明 | 影响 | 说明 |
|:---:|------|:---:|------|
| 1 | 很低，几乎不会发生 | 1 | 影响轻微 |
| 2 | 较低，可能发生 | 2 | 局部影响 |
| 3 | 中等，有一定概率 | 3 | 影响项目局部目标 |
| 4 | 较高，较可能发生 | 4 | 影响关键里程碑或预算 |
| 5 | 很高，大概率发生 | 5 | 导致项目失败或重大损失 |

**风险等级 = 概率 × 影响**：低 (1-6) / 中 (7-12) / 高 (13-19) / 极高 (20-25)

## 16.2 风险登记表

### R1：网页数据采集涉及法律或 ToS 风险

| 字段       | 内容                                                                          |
| -------- | --------------------------------------------------------------------------- |
| **风险描述** | 通过网页抓取获取 AI 工具信息（价格、功能描述）可能违反目标网站的 ToS，或在某些法域下构成未经授权的数据采集                   |
| **根本原因** | 数据采集方式（爬虫）的合法边界模糊；各网站 ToS 条款不一致                                             |
| **概率**   | 3（中等）——个人小规模抓取不太可能被主动追责，但风险不可忽略                                             |
| **影响**   | 4（影响关键里程碑）——如被投诉，需立即下线相关内容或停止抓取                                             |
| **等级**   | **12（中）**                                                                   |
| **触发信号** | 收到目标网站的 cease & desist 通知；GitHub Pages 因 DMCA 投诉被下架；API 访问被限流或封禁            |
| **缓解措施** | 优先使用官方 API（X、YouTube、Bilibili）；对网页数据注明来源链接；控制抓取频率（每秒 ≤1 次）；W1 完成主要网站 ToS 审查 |
| **应急措施** | 停止抓取该数据源 → 切换为纯手动整理或寻找替代 API；极端情况下移除争议内容                                    |
| **责任角色** | 开发者                                                                         |
| **剩余风险** | **低**——即使完全放弃网页抓取，仅靠官方 API + 手动整理也能完成 MVP                                   |

| **影响** | 4（影响关键里程碑）——MVP 延期直接违背用户的核心时间约束 |
| **等级** | **12（中）** |
| **触发信号** | W1 末技术验证未完成；W2 末核心页面未成型；W3 末内容覆盖 < 10 个工具 |
| **缓解措施** | 严格的 MVP 范围控制（P0 功能优先，P1/P2 不阻塞发布）；每个里程碑预留 2-3 天缓冲；Claude Code 辅助编程提效 |
| **应急措施** | 如 W2 延期 > 1 周，缩减内容范围（从 20 个工具降到 10 个），保 P0 功能上线；MVP 可先以"可本地浏览的静态站"形式交付 |
| **责任角色** | 开发者 |
| **剩余风险** | **低-中**——有明确的缩减路径，最差情况是"内容少但功能完整的 MVP" |

### R4：目标用户不使用或不持续使用

| 字段 | 内容 |
|------|------|
| **风险描述** | MVP 上线后目标用户（学生群体）访问量低，或首次访问后不回访，无法收集足够反馈 |
| **根本原因** | 学生群体信息获取习惯以社交媒体为主（82.1%），主动访问静态网站的习惯未建立；竞品（社交媒体 AI 博主）提供更强的社交粘性 |
| **概率** | 4（较高）——静态站在用户习惯和社交粘性上先天劣势 |
| **影响** | 3（影响项目局部目标）——反馈不足影响后续迭代方向判断 |
| **等级** | **12（中）** |
| **触发信号** | MVP 上线 1 周内独立访客 < 30；GitHub Star < 10；无自发用户反馈 |
| **缓解措施** | 在原有问卷渠道（微信/QQ 群）主动推广 MVP；内容中嵌入社交分享按钮；利用 GitHub README 做 SEO；场景化页面设计为"可分享的独立入口"（如 `/scenes/write-paper.html` 可在微信群直接分享） |
| **应急措施** | 在目标用户社群做定向推广（发问卷的群、V2EX、即刻）；如 2 周内反馈仍不足，直接联系问卷中留了联系方式的受访者做定向访谈 |
| **责任角色** | 开发者（推广） |
| **剩余风险** | **中**——推广效果不可控，但即便用户量小，项目的学习价值不变 |

### R5：信息内容被质疑公正性或有商业利益冲突

| 字段 | 内容 |
|------|------|
| **风险描述** | 用户或 AI 工具厂商质疑评测结果的公正性——认为存在付费推广或主观偏见 |
| **根本原因** | 缺乏标准化的评测方法论和透明度机制；行业普遍存在"付费评测"问题，用户默认持怀疑态度 |
| **概率** | 3（中等） |
| **影响** | 4（影响关键里程碑）——信任是产品的核心价值主张，公正性被质疑可能直接导致项目失败 |
| **等级** | **12（中）** |
| **触发信号** | GitHub Issue 或社交媒体上出现公正性质疑；某 AI 工具厂商要求修改对其不利的评测结论 |
| **缓解措施** | 公开评测方法论和评分标准（参考问题定义文档第 7 章框架）；明确标注"主观判断"vs"客观数据"；对所用 AI 工具使用统一的评测模板；在页面中公开利益声明（"本项目不接收 AI 工具厂商赞助"）；提供"纠错/反馈"通道 |
| **应急措施** | 对被质疑的内容启动复核流程；如评测确实有误，及时更正并在更新日志中记录；如为观点分歧，增加"用户自评"区域让多方声音并存 |
| **责任角色** | 开发者 |
| **剩余风险** | **低-中**——开源透明策略是应对公正性质疑的最强防御 |

### R6：开发者失去动力或时间投入不可持续

| 字段 | 内容 |
|------|------|
| **风险描述** | 开发者在项目中期因学业/工作/生活压力或个人兴趣转移，减少或停止投入，项目停滞 |
| **根本原因** | 开源免费项目无外部激励（薪资、合同义务）；单人项目无同伴压力或监督机制 |
| **概率** | 3（中等）——2 个月时间窗口相对短，但单人项目的持续性天然不稳定 |
| **影响** | 5（导致项目失败）——唯一开发者流失 = 项目直接终止 |
| **等级** | **15（高）** |
| **触发信号** | 连续 1 周无 Git commit；里程碑连续延期 2 次以上；开发者自述"没时间"或"没动力" |
| **缓解措施** | 将项目目标与个人学习目标深度绑定（每完成一个功能 = 掌握一项技能）；设定小而可完成的周目标，保持成就感；公开发布开发进度（GitHub Projects / 开发日志），制造"公开承诺"的软约束；Claude Code 协作降低枯燥工作的阻力 |
| **应急措施** | 以当前状态发布 GitHub Release，标记为"存档项目"；撰写 README 说明项目状态和未完成功能，欢迎社区 fork 继续 |
| **责任角色** | 开发者 |
| **剩余风险** | **中**——这是所有个人开源项目固有的风险，无完美解决方案 |

### R7：静态站架构限制后续功能扩展

| 字段 | 内容 |
|------|------|
| **风险描述** | 方案 1 的纯静态架构在 MVP 上线后，用户反馈要求动态功能（个性化推荐、实时数据），而静态站无法满足，需要架构迁移 |
| **根本原因** | 静态站天然缺乏服务端计算和实时数据处理能力 |
| **概率** | 4（较高）——用户对"AI 工具推荐平台"的心理模型通常包含搜索、筛选、推荐等动态功能 |
| **影响** | 2（局部影响）——这是预期的演进路径，不是意外 |
| **等级** | **8（中）** |
| **触发信号** | 用户反馈中频繁提到"搜索不够好用""能不能根据我的需求推荐""看不到最新信息"；GitHub Issues 中动态功能请求超过 5 条 |
| **缓解措施** | 这正是"方案 1 → 方案 3 渐进演进"策略已规划好的路径；MVP 阶段明确告知用户"功能持续完善中"；优先用浏览器端实现近似功能（Lunr.js 搜索、localStorage 偏好记录）作为过渡方案 |
| **应急措施** | 根据用户反馈优先级，加速 Serverless 迁移（G3 关口提前） |
| **责任角色** | 开发者 |
| **剩余风险** | **低**——这是预期内的演进，不是意外风险 |

| 变动假设 | 方案 1 新得分 | 方案 2 新得分 | 方案 3 新得分 | 是否改变推荐？ |
|----------|:---:|:---:|:---:|------|
| 基准（当前权重） | **4.10** | 2.95 | **3.95** | 方案 1 领先 |
| 进度可行性权重从 20%→10%，学习价值从 10%→20% | 3.85 | 3.25 | 3.85 | 方案 1 和 3 并列 |
| 技术可行性从 20%→15%，市场与用户从 15%→20% | 4.00 | 3.00 | 3.90 | 方案 1 仍然领先 |
| C++ Web 框架学习成本为零（假设开发者已掌握） | — | 3.35（技术→3） | — | 方案 2 仍低于方案 1/3 |
| 方案 3 进度可行性从 3→2（Serverless 学习超预期） | — | — | 3.75 | 方案 1 优势扩大 |

**核心结论**：在合理权重变动范围内，**方案 1 始终领先或并列领先**。方案 3 紧随其后。方案 2 即使在某些假设改善后仍不具竞争力。最关键的敏感性因素是"进度可行性"和"学习价值"的权重分配——当学习价值权重上升时，方案 3 与方案 1 并列。

# 18. 推荐结论及其成立条件

## 18.1 决策结论

> **建议：Conditional Go — 附条件继续。**

## 18.2 推荐方案

**首选方案：方案 1（轻量级静态内容站），以方案 3（SPA + Serverless）为演进目标。**

具体策略——**"静态起步，渐进增强"**：

| 阶段 | 时间 | 方案 | 目标 |
|------|------|------|------|
| **MVP（v0.1）** | 第 1-4 周（至 08-14） | 方案 1（静态站） | 快速上线：AI 工具数据库 + 场景化对比页面 + 浏览器端搜索 |
| **v0.2-v0.3** | 第 5-8 周（至 09-14） | 方案 1 → 方案 3 渐进迁移 | 添加动态功能：Serverless API 代理、自动数据采集、个性化推荐 |
| **v1.0** | 第 9 周（09-14） | 方案 3（SPA + Serverless） | 开源发布：完整功能 + 文档 + 社区建设 |

## 18.3 推荐理由

1. **时间可行性最高**：方案 1 的 1-3 周 MVP 周期是唯一能可靠满足"1 个月内第一个可用版本"的方案。方案 3 虽然综合价值更高，但进度风险（3 分）意味着可能延期。
2. **零经济风险**：GitHub Pages 免费，API 调用在免费额度内，完全在 200-500 元预算内。
3. **技能匹配最优**：HTML/CSS/JS + Markdown 无需额外学习，开发效率最高。
4. **不排斥演进**：静态站可以渐进式添加动态功能（先加浏览器端搜索，再加 Serverless 后端），不会被锁定。本质上方案 1 是方案 3 的"第一步"。
5. **先验证再投入**：MVP 快速上线后，可根据用户反馈（GitHub Issues、页面访问数据）判断是否值得投入更多时间做方案 3 的迁移。

## 18.4 反对理由（为什么不推荐方案 2 和方案 3 作为起点）

- **方案 2（C++ 自研 Web）**：进度风险过高（1 个月 MVP 几乎不可能）；C++ Web 框架学习成本挤压开发时间；服务器运维增加长期负担。**适合作为"下一个项目"而非本项目**——本项目中积累的经验可为将来的 C++ Web 项目打下基础。
- **方案 3（SPA + Serverless）作为 MVP 起点**：虽然综合得分 3.95（接近 Go），但 Serverless 平台学习（3-5 天）+ 开发 + 内容填充的并行压力，可能导致 1 个月 MVP 延期。**更安全的做法是先以方案 1 快速上线，再逐步迁移到方案 3。**

## 18.5 成立条件（Conditional Go 的"条件"）

以下条件必须满足方可继续推进：

| 编号 | 条件 | 验证方式 | 截止时间 |
|:---:|------|----------|----------|
| C1 | 完成信息采集 PoC（至少 3 个数据源的 API/抓取验证通过） | 技术 Spike（W1） | 2026-07-20 |
| C2 | 初始内容覆盖 ≥ 20 个主流 AI 工具（基本信息 + 场景标签 + 价格） | 内容清单 Review | 2026-08-10（MVP 上线前） |
| C3 | 确定网页抓取的合规边界（至少查阅主要目标网站的 ToS 并记录） | ToS 审查清单 | 2026-07-20 |
| C4 | 开发者确认每周可投入 ≥ 15 小时 | 自我评估 | 2026-07-14（已确认推进） |
| C5 | MVP 上线后 2 周内收集 ≥ 10 条有效用户反馈 | GitHub Issues / 社群 | 2026-08-28 |

## 18.6 反对理由（内部批判）

- **"静态站不是软件"**：方案 1 本质是内容站而非软件产品，与项目名称"AI 信息获取**软件**开发"存在定位偏差。回应：MVP 阶段以验证问题和快速上线为优先；v1.0 迁移到方案 3 后即成为完整的软件产品。
- **"手动维护不可持续"**：如果项目成功（工具数量增长、更新频率提高），手动维护将成为瓶颈。回应：这正是渐进迁移到方案 3 的触发条件——当手动维护成本 > 自动化开发成本时启动迁移。
- **"学习价值有限"**：方案 1 的技术深度不如方案 2 和 3。回应：W1-W4 快速交付 MVP 建立信心和用户基础；W5-W9 的 Serverless 迁移阶段提供充分的学习机会。

## 18.7 置信度

**推荐置信度：中-高。**

- 技术可行性和经济可行性的评分置信度高（技术成熟、成本明确）
- 进度可行性的置信度中等（取决于开发者实际投入时间）
- 市场与用户可行性的置信度中等（仅验证了学生群体，且未验证用户是否会主动使用静态站）
