# R2：信息更新时效风险

## 风险回顾

来自 [[可行性研究报告.md#R2：信息更新跟不上 AI 行业变化速度|可行性研究报告 §16.2 R2]]：

| 字段 | 内容 |
|------|------|
| **风险描述** | AI 工具以周/月为单位更新功能、价格、模型版本，静态站内容快速过时，用户不再信任 |
| **根本原因** | 单人维护，时间有限；AI 行业变化频率客观极高 |
| **概率** | 5（很高）——必然发生，只是程度问题 |
| **影响** | 4（影响关键里程碑）——内容过时直接损害产品核心价值主张 |
| **等级** | **20（极高）**——项目最大长期风险 |
| **剩余风险** | **中-高**——无法完全消除，只能通过自动化+社区协作持续缓解 |

## 解决方案总览

采用 **“手动标注 + 众包纠错 + 自动采集”三管齐下** 的分层策略，按时间线逐步增强：

```
MVP 阶段                  v0.2-v0.3 阶段              v1.0+ 阶段
┌────────────────┐       ┌────────────────┐        ┌──────────────────────┐
│ 手动标注 +      │ ──▶  │ 增加众包纠错    │ ──▶   │ Serverless 自动采集    │
│ 时效透明        │       │ (GitHub Issues) │        │ (Cron 定时任务)        │
└────────────────┘       └────────────────┘        └──────────────────────┘
```

## 方案二：众包纠错流水线（MVP 即部署）

### 三层信息更新流水线

已完整部署在 [[../08-maintenance/README.md]] 和 [[../08-maintenance/CONTRIBUTING.md]]：

```
用户提交 ──▶ AI 初审（v1.0+）──▶ 人工审核 ──▶ 入库
   │            │                  │
 GitHub       预审过滤           维护者确认
 Issues       低质量提交         合并入库
```

| 层 | 职责 | 阶段 |
|------|------|:---:|
| 用户提交 | 通过 GitHub Issue 模板结构化提交纠错/新工具 | ✅ MVP |
| AI 初审 | 自动预审：字段完整性、来源可信度、事实抽查 | 🔜 v1.0+（可选） |
| 人工审核 | 维护者最终确认合并 | ✅ MVP |

### Issue 模板（`.github/ISSUE_TEMPLATE/`）

| 模板 | 用途 |
|------|------|
| `data-correction.yml` | 结构化纠错（tool_name/field/current_info/correct_info/source 必填） |
| `new-tool.yml` | 结构化新工具推荐 |

> **部署前必做**：模板中的 `wozore` 占位符需替换为实际 GitHub 用户名。

### 审核流程

```
提交 Issue/PR
    │
    ├── 核对数据字段（必填项检查）
    │
    ├── 通过 ──→ 自动合并（小改动）
    │
    └── 标记可疑 ──→ 人工审核
                        │
                        ├── 通过 ──→ 合并 + 更新 last_updated
                        │
                        └── 驳回 ──→ 在 Issue/PR 中说明理由
```

审核周期：**2-3 天内完成**。

## 原始风险回顾

来自 [[可行性研究报告.md#R4：目标用户不使用或不持续使用|可行性研究报告 §16.2 R4]]：

| 字段 | 内容 |
|------|------|
| **风险描述** | MVP 上线后目标用户（学生群体）访问量低，或首次访问后不回访，无法收集足够反馈 |
| **根本原因** | 学生群体信息获取习惯以社交媒体为主（82.1%），主动访问静态网站的习惯未建立；竞品提供更强的社交粘性 |
| **概率** | 4（较高） |
| **影响** | 3（影响项目局部目标——反馈不足影响迭代方向判断） |
| **等级** | **12（中）** |
| **触发信号** | MVP 上线 1 周内独立访客 < 30；GitHub Star < 10；无自发用户反馈 |

原始缓解措施（报告中已有）：
- 在原有问卷渠道（微信/QQ群）主动推广 MVP
- 内容中嵌入社交分享按钮
- 利用 GitHub README 做 SEO
- 场景化页面设计为“可分享的独立入口”
- 在目标用户社群做定向推广（V2EX、即刻等）
- 直接联系问卷中留了联系方式的受访者

## 新补充方案

### SEO 工具站策略（零成本持续获客）

你的站本质是 **“工具站”而非“内容站”**——用户来是为了“对比AI工具”，不是读文章。工具站的 SEO 策略与内容站完全不同：

| 维度 | 内容站 | 你的站（工具站） |
|------|--------|----------------|
| 核心流量来源 | 文章页面 | 场景对比页面 / 工具详情页 |
| SEO重点 | 内容质量+更新频率 | 页面标题/描述 + 功能完整度 + 用户停留时长 |
| 内链策略 | 文章互链 | 博客文章→工具页，单向引流 |
| 外链策略 | 铺量买链接 | 靠产品好用自然获取推荐链接 |
| 核心KPI | 流量和广告点击 | **用户留存和转化率** |

**分三期操作：**

- **P0（上线前）**：给场景对比页加上 `SoftwareApplication Schema`（评分、价格），给 FAQ 加 `FAQPage Schema`；配好 OpenGraph 标签（og:title、og:description、og:image），确保分享到社交平台显示精美卡片
- **P1（上线第一周）**：配好 Google Search Console + Google Analytics，提交 Sitemap，做好内链布局
- **P2（长期）**：持续产出“AI工具对比”“如何选AI写论文”等长尾关键词内容

> 关键是：工具站的第一 KPI 不是流量，是用户留存。用户留住了，SEO 自然会好。

### 由外到内的推广飞轮

```
SEO 长尾流量 ──→ 用户通过搜索找到场景页
     ↑                    ↓
     │              对比后有收获
     │                    ↓
  更多外链 ←── 分享到社交媒体/博客
                    ↓
              → 首次访问完成“激活” ←
              → 通过 NewsLetter/RSS 回访 ←
              → 提交反馈/参与社区 ←
```

**关键环节：**

1. **激活（Activation）**——用户首次访问必须在 3 秒内理解价值，完成一次“有用的动作”（比如选一个场景→看到对比→做出决策），这是留存的前提
2. **回访机制**——AI 行业变化快，每月发一封“AI 工具月报”Newsletter/博客更新，让回访成为习惯
3. **社交传播**——每个场景页设计为“可独立分享”，自带 OpenGraph 卡片，分享到微信群/B站/知乎就像在发一个独立内容
4. **社区建设**——GitHub Discussions + 微信群双通道，用户反馈有回应、有闭环
