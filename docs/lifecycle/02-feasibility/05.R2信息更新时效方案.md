# R2 风险缓解方案：信息更新跟不上 AI 行业变化速度

## 风险回顾

来自 [[可行性研究报告.md#R2：信息更新跟不上 AI 行业变化速度|可行性研究报告 §16.2 R2]]：

| 字段 | 内容 |
|------|------|
| **风险描述** | AI 工具以周/月为单位更新功能、价格、模型版本，静态站内容快速过时，用户不再信任 |
| **根本原因** | 单人维护，时间有限；AI 行业变化频率客观极高 |
| **概率** | 5（很高）——必然发生，只是程度问题 |
| **影响** | 4（影响关键里程碑）——内容过时直接损害产品核心价值主张 |
| **等级** | **20（极高）**——项目最大长期风险 |
| **剩余风险** | **中-高**——无法完全消除，只能通过自动化+社区协作持续缓解 |

---

## 解决方案总览

采用 **"手动标注 + 众包纠错 + 自动采集"三管齐下** 的分层策略，按时间线逐步增强：

```
MVP 阶段                  v0.2-v0.3 阶段              v1.0+ 阶段
┌────────────────┐       ┌────────────────┐        ┌──────────────────────┐
│ 手动标注 +      │ ──▶  │ 增加众包纠错    │ ──▶   │ Serverless 自动采集    │
│ 时效透明        │       │ (GitHub Issues) │        │ (Cron 定时任务)        │
└────────────────┘       └────────────────┘        └──────────────────────┘
```

---

## 方案一：信息透明与时效标注（MVP 即做）

### 1.1 每个工具页标注"最后更新日期"

已在以下层面落实：

- **FR-CORE-03**（[[软件需求规格说明书.md]] §2）：每条记录应显示"最后更新日期"
- **数据字段规范**（[[软件维护/CONTRIBUTING.md]]）：`last_updated` 为必填字段，格式 `YYYY-MM-DD`
- **开发计划 B10**（[[开发计划.md]]）：时效标注系统，每个工具页面标注"最后更新日期"

### 1.2 高频变化维度免责标注

| 维度 | 变化频率 | 标注方式 |
|------|:------:|---------|
| 价格/免费额度 | 高（月/周） | 标注"仅供参考，请以官网为准" |
| 功能描述 | 中（月） | 标注最后更新日期 |
| 模型版本 | 高（月） | 标注最后更新日期 + 官网链接 |
| 基本信息/场景分类 | 低（季度） | 标注最后更新日期 |

已录入 **NFR-TRUST-02**（[[软件需求规格说明书.md]] §3）：高频变化维度标注"仅供参考，以官网为准"。

### 1.3 页面时效提示机制

- **预防性维护**（[[软件维护/README.md]] §四类维护活动）：时效提示机制列入预防性维护
- **应急**：页面顶部添加醒目时效提示横幅
- **触发信号**：用户报告"价格已变更""功能已更新"等过时信息

## 方案二：众包纠错流水线（MVP 即部署）

### 2.1 三层信息更新流水线

已完整部署在 [[软件维护/README.md]] 和 [[软件维护/CONTRIBUTING.md]]：

```
用户提交 ──▶ AI 初审（v1.0+）──▶ 人工审核 ──▶ 入库
   │            │                  │
 GitHub       预审过滤           维护者确认
 Issues       低质量提交         合并入库
```

| 层 | 职责 | 阶段 |
|------|------|:---:|
| 用户提交 | 通过 GitHub Issue 模板结构化提交纠错/新工具 | ✅ MVP |
| AI 初审 | 自动预审：字段完整性、来源可信度、事实抽查 | 🔜 v1.0+（可选） |
| 人工审核 | 维护者最终确认合并 | ✅ MVP |

### 2.2 Issue 模板（`.github/ISSUE_TEMPLATE/`）

| 模板 | 用途 |
|------|------|
| `data-correction.yml` | 结构化纠错（tool_name/field/current_info/correct_info/source 必填） |
| `new-tool.yml` | 结构化新工具推荐 |

> **部署前必做**：模板中的 `wozore` 占位符需替换为实际 GitHub 用户名。

### 2.3 审核流程

```
提交 Issue/PR
    │
    ├── 核对数据字段（必填项检查）
    │
    ├── 通过 ──→ 自动合并（小改动）
    │
    └── 标记可疑 ──→ 人工审核
                        │
                        ├── 通过 ──→ 合并 + 更新 last_updated
                        │
                        └── 驳回 ──→ 在 Issue/PR 中说明理由
```

审核周期：**2-3 天内完成**。

### 2.4 四类维护活动

| 类型 | 说明 | 对应工作 |
|------|------|---------|
| 改正性 | 修正错误信息 | 数据纠错（CONTRIBUTING + Issue 模板） |
| 适应性 | 适配环境变化 | 网站改版适配、API 变更适配 |
| 完善性 | 新增/增强功能 | 见《开发计划.md》D9-D18 |
| 预防性 | 防患于未然 | ToS 监控、时效提示机制 |

## 方案三：Serverless 自动采集（v0.2+ 渐进引入）

### 3.1 时间规划

| 时间 | 措施 | 来源 |
|:---:|------|------|
| W5 起 | 引入 API 自动价格监控（Serverless 定时任务） | 可行性研究报告 §16.2 |
| v0.2-v0.3 | 自动数据采集、AI 热点聚合 | [[总体设计说明书.md]] §3.2 |
| v1.0 | Serverless Cron 全量定时采集 | [[总体设计说明书.md]] §4 |

### 3.2 自动采集架构

```
┌──────────────────────┐
│ Serverless Functions │
│  - API 代理          │
│  - 采集 Cron         │  ← Cloudflare Workers / Vercel Functions
│  - 推荐逻辑          │
└──────┬───────────────┘
       │
┌────────────▼────────────┐
│ Cloudflare KV / JSON    │（数据缓存层）
└─────────────────────────┘
       │ 采集
┌────────────▼────────────┐
│ 外部 API + 网页         │（API 代理降低直接抓取法律风险）
└─────────────────────────┘
```

### 3.3 模块演进

| 模块 | MVP | v1.0 |
|------|:---:|:---:|
| 工具信息库 | ✅ 静态 JSON | ✅ KV + Cron 更新 |
| 热点聚合 | ❌ | ✅ Serverless Cron（X/YouTube/Bilibili API） |
| 数据更新方式 | 手动 + 众包 | 手动 + 众包 + Serverless 定时采集 |

### 3.4 采集目标

| 数据类型 | 获取方式 | 频率 | 阶段 |
|---------|---------|:---:|:---:|
| AI 热点新闻/动态 | X API、YouTube API、Bilibili API | 每日 | v1.0 |
| 工具价格/权益 | 网页抓取 + 手动更新 | 每周 | v0.2+ |
| Benchmark 数据 | LMSYS、Artificial Analysis API | 每周 | v1.0 |

## 方案四：差异化竞争优势（竞品对比）

与竞品相比，InfoCatcher 在信息时效性方面已经建立了差异化优势：

| 维度 | 竞品（导航站） | InfoCatcher |
|------|:----------:|:-----------:|
| 信息可信度标注 | ❌ 无 | ✅ **最后更新日期 + 来源标注** |
| 更新频率 | 不定期 | 按需 + API 自动 |
| AI 热点聚合 | ❌ 无 | ✅ **计划 P1（Bilibili/YT/X API）** |

详见 [[poc/competitive_analysis.md]]。
