## 1. 功能概述

InfoCatcher 定期更新 AI 工具动态（新工具发布、价格变更、功能更新等），订阅模块允许用户按自己的方式接收这些更新推送，而不是被动等待用户回访网站。

---

## 2. 功能需求

### 2.1 推送渠道（目标）

| 渠道 | 实现方式 | 当前可行性 |
|:----:|---------|:---------:|
| **浏览器通知** | Web Push API + Service Worker | ✅ 方案1 可行（需 HTTPS） |
| **RSS/Atom 订阅源** | 构建时自动生成 feed.xml | ✅ 方案1 可行，纯静态 |
| **微信公众号/飞书机器人** | Serverless 调用平台 API 发送 | ❌ 需方案3 + 公众号/飞书应用 |
| **B 站动态** | B 站开放平台 API | ❌ 需方案3 + OAuth 授权 |
| **X (Twitter)** | X API v2 | ❌ 需方案3 + OAuth 授权 |
| **邮件订阅** | Serverless 调用邮件服务 | ❌ 需方案3 + 邮件服务商 |

### 2.2 推送时机

| 模式 | 说明 | 方案1 | 方案3 |
|:---:|------|:----:|:----:|
| 跟随站点更新 | 开发者发布更新后立即推送 | ✅ RSS | ✅ 全渠道 |
| 每 N 天固定时间 | 用户设定每日/每周 X 点推送 | ❌ | ✅ |
| 每隔 N 小时推送 | 固定间隔聚合推送 | ❌ | ✅ |
| 自定义 API 调用 | 用户通过 API 触发推送 | ❌ | ✅ |

### 2.3 推送内容

- AI 工具上新通知
- 价格/免费额度变更提醒
- 热门工具排行更新
- 新评测报告发布

## 3. 不登陆行吗？— 逐项评估

| 依赖项 | 不登陆 | 影响 |
|-------|:-----:|------|
| **知道推给谁** | ❌ 无法区分用户 | 所有用户收到相同推送，无法个性化 |
| **绑定社交账号** | ❌ 每个平台需 OAuth | 需要用户身份才能授权绑定 |
| **存储推送偏好** | ❌ localStorage 仅限当前浏览器 | 换设备丢失，无法跨平台同步 |
| **调用平台 API** | ⚠️ 部分需要 | RSS 不需要；微信/B站/X 都需要 |
| **防滥用（API 限频）** | ❌ 无法识别单个用户 | 无登录意味着无法按用户限流 |

**结论：推送渠道越强，对登录的依赖越强**

```
功能强度:
RSS/Atom  ←  浏览器通知  ←  邮件订阅  ←  社交媒体推送
 无需登录      仅需HTTPS      需要身份     需要OAuth+后端
    ✅            ⚠️部分         ❌             ❌
```

### 折衷方案（不登陆也能用的）

| 功能 | 方案1 可实现 | 说明 |
|------|:-----------:|------|
| **RSS/Atom 源** | ✅ 简单 | 构建脚本生成 `feed.xml`，用户用 RSS 阅读器订阅 |
| **GitHub Releases Watch** | ✅ 利用现成 | 用户 Watch 仓库 → GitHub 通知，零开发 |
| **Web 浏览器通知** | ⚠️ 需要 Service Worker | 用户访问网站时弹权限请求，可推送更新提醒 |

## 4. 分阶段落地

### 阶段一：方案1（环 B）— 零登录，零后端

| 任务 | 产出 | 优先级 |
|------|------|:------:|
| 建立 AI 动态定期手动更新流程 | 开发者每 N 天更新 `news/` 数据 | P1 |
| 构建时生成 RSS/Atom feed.xml | 用户可用阅读器订阅更新 | P1 |
| 页面添加"订阅更新"入口（链接到 RSS / GitHub Watch） | 用户可发现订阅方式 | P2 |

### 阶段二：方案3（环 C）— 完整订阅系统

| 任务 | 先决条件 |
|------|---------|
| 用户注册/登录系统（OAuth GitHub/Google） | Serverless 后端就绪 |
| 用户偏好设置（推送渠道 + 推送时机） | 登录系统就绪 |
| Serverless 定时调度 + 多平台推送 | 偏好存储 + 各平台 API Key |
| 推送 API（供第三方调用） | API 认证机制 |
