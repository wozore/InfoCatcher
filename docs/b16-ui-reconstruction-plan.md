## 1. 目标与边界

B16 是一次**全站 UI 系统重构**，围绕“AI 信息搜索”重新组织视觉、信息展示与交互，并在可审查原型中呈现未来 AI 搜索体验。

目标用户覆盖两类人群：

- **初学者**：不了解或不熟悉 AI 搜索，不知道怎样表达问题、如何判断答案可信度或使用引用；
- **知识工作者与熟练用户**：需要更高效地检索、比较、核验和追踪信息。

默认体验采用：

> **初学者友好的入口 + 面向熟练用户的渐进式深度。**

即：默认界面先提供清楚的提问引导、简明结论、关键来源与下一步操作；高级筛选、完整来源、搜索过程、比较、追踪与历史能力不应在首次视图中争夺焦点，而应按需出现。

### 1.2 产品能力路线与视觉布局路线必须分开

这两组“方向”属于不同决策维度，严禁混淆。

| 决策轴 | B16 | v1.0 | 不采用 / 限制 |
|---|---|---|---|
| **产品能力路线** | **方向 1：基于现有静态数据的 AI 信息搜索体验层**。使用现有工具、场景、热点、概念等静态数据重构体验；不虚构实时 AI 回答、联网检索、流式生成或真实会话。 | **方向 3：真实 AI 搜索产品 / 轻量 AI 工作台**。后续接入搜索 API、模型调用、流式响应、来源聚合、引用式回答、会话历史等。 | **方向 2：静态 mock AI 回答**不作为正式业务能力；仅可作为原型验证材料，且必须显著标注。 |
| **视觉与布局路线** | **极简编辑部**。完成全站 UI 系统重构，首页强调单一任务，阅读和资料页面按任务采用适当的信息密度。 | 在 B16 视觉基础上逐步吸收真实 AI 工作流所需的实时状态和高阶交互；不要求直接复制某个高密度工作台布局。 | “可信研究台”不作为全站主视觉，但其个别信息组织方式可局部借鉴。 |

### 1.3 双模式切换：B16 不做显式开关，但预留演进空间

B16 首期**不提供显式的“简洁模式 / 专业模式”切换**。默认体验固定采用“初学者友好的入口 + 面向熟练用户的渐进式深度”。

原因是：初学者不应先承担“选择模式”的额外认知负担；在模式差异尚未由真实使用验证前，双模式会增加设置、持久化状态、响应式适配、可访问性和测试复杂度。

B16 应通过渐进式展开、筛选入口、默认信息密度与默认展开状态来满足不同熟练度，而非维护两套页面或业务逻辑。后续 v1.0 如需引入模式切换，应遵循：

- 模式主要改变信息密度、信息默认展开状态和高级能力入口；
- 不复制或分叉业务逻辑；
- 先以 B16 的渐进式能力验证真实需求，再决定是否提供显式切换；
- UI 系统应保留支持密度变化的令牌和结构空间，但 B16 不接入用户偏好持久化。

### 1.4 B16 不改变的内容

- 所有现有视图都进行 UI 重构；
- 现有业务能力、静态数据能力、数据契约、筛选逻辑、对比规则、热点数据处理及详情信息含义保持不变；
- 不开发真实搜索后端、实时模型调用、真实流式生成、真实引用校验、账户系统或持久化会话；
- 不引入前端框架、UI 组件库、字体依赖或第三方图标库；
- 不将用于审查的静态 mock 表述为真实产品能力。

### 1.5 B16 原型允许做什么

可制作一条**主流程可操作、状态可演示、数据固定、逻辑有限**的静态 mock，用来验证未来 AI 搜索的界面结构：

- 输入问题、点击示例问题、触发“演示检索”；
- 用 2–3 个固定阶段演示搜索过程；
- 展示固定的搜索摘要、引用、来源、匹配资料和示例历史；
- 支持有限筛选、展开/收起、恢复示例查询、本地反馈；
- 展示空输入、无匹配、部分不可用和处理失败状态；
- 支持桌面端与移动端布局验证。

不得在 B16 mock 中模拟或暗示：任意问题动态生成答案、真实外部检索、真实引用校验、复杂多轮对话、真实账户或持久化历史、真实进度、额度与后台任务。

所有原型必须持续、清楚地标注类似：

> **静态演示 / 原型内容，不代表当前已接入真实 AI 搜索。**

## 2. 极简原则与信息密度

### 2.1 核心原则

> **极简不等于机械地减少数据或降低信息密度。极简是让信息密度与页面任务匹配，做到层级清晰、所见即所得，并尽量减少不必要的滚动和定位成本。**

因此，不得把“单列”“折叠更多内容”“减少信息”自动视为更极简的方案。

### 2.2 按任务决定布局

| 页面类别 | 主要任务 | 已确认布局原则 |
|---|---|---|
| 入口/介绍页 | 理解产品、开始提问 | 简洁聚焦一个核心任务；避免多个高权重区域同时争夺注意力。 |
| 搜索结果/引用式回答 | 阅读结论、对照并核验证据 | 可使用较高且合理的信息密度；桌面端允许摘要与来源并列，让结论—证据在同一视野中对照。 |
| 工具/场景详情 | 阅读、比较具体资料 | 按内容关系采用并列或分栏，避免不必要的纵向滚动。 |
| 热点/概念浏览 | 连续阅读、发现内容 | 编辑部式纵向内容流。 |

### 2.3 全站原则

> **设计系统统一，页面布局按任务匹配。**

统一的是色彩、字体、间距、边框、控件、状态、导航层级和无障碍规则；不统一的是栏数、卡片数量、是否单列或是否折叠。

## 3. 信息架构与导航

### 3.1 导航层级

```text
InfoCatcher
├── AI 搜索（唯一主入口）
├── 发现工具
│   ├── 工具库
│   ├── 场景
│   └── 对比
├── 了解 AI
│   ├── AI 热点
│   └── AI 概念
└── 关于
```

### 3.2 导航规则

- “AI 搜索”是唯一高优先级导航项；
- “工具库、场景、对比”直接服务于工具发现与选择，应易于访问；
- “AI 热点、AI 概念”属于浏览与学习入口，不与搜索主任务争夺同等视觉权重；
- “关于”移入用户菜单或页脚，不占据主导航空间；
- 桌面端保留简洁一级导航，但弱化非主入口；
- 移动端采用 Logo + 当前页标题 + 搜索/菜单入口，其他页面从分组菜单访问；
- 不使用默认高密度侧边栏导航。

## 4. 视觉系统

### 4.1 视觉方向：极简编辑部

整体应明亮、克制、专业、清晰，突出信息阅读、来源核验和下一步操作，不做娱乐化或过度装饰。

- 不使用大面积渐变、玻璃拟态、强装饰插画或强动效；
- 不采用“所有内容均为悬浮卡片”的仪表盘式外观；
- 视觉重点放在搜索输入、阅读结论、来源证据与下一步操作；
- 动效仅服务状态变化和展开/收起，并支持减少动效偏好。

### 4.2 色彩

采用**暖白编辑部基调 + 蓝灰交互焦点 + 低饱和状态色**：

| 角色 | 方向 |
|---|---|
| 页面背景 | 很浅暖灰米色 |
| 内容表面 | 暖白 |
| 主文字 | 深灰棕或近黑，不使用纯黑 |
| 次级文字 | 中性灰褐 |
| 主操作 | 克制深色按钮或深棕色 |
| 链接、引用、交互焦点 | 稳重蓝灰色 |
| 成功 | 低饱和绿色 |
| 警告 | 低饱和琥珀色 |
| 错误 | 低饱和红色 |

不使用大面积高饱和蓝色，避免回到 SaaS 仪表盘感；状态不得仅靠颜色区分。

### 4.3 字体

采用**阅读内容用衬线、操作和结构化信息用无衬线**的双字体层级，且 B16 不新增字体依赖。

| 字体角色 | 适用内容 |
|---|---|
| 系统中文衬线字体栈 | 首页主标题、搜索摘要正文、热点文章标题与正文、概念详情正文、场景导语等连续阅读内容。 |
| 系统无衬线字体栈 | 导航、输入框、按钮、筛选器、工具名、标签、状态、时间、来源标题、来源类型、链接、对比表和结构化数据。 |

正文不得过小；移动端应保持舒适字号和行高；英文产品名/技术名词继续使用无衬线，避免中英衬线混排不稳定。

### 4.4 容器、圆角与阴影

> **平面分隔优先，圆角和阴影只服务于交互和层级。**

- 正文：留白 + 排版 + 分隔线；
- 来源：编号 + 层级 + 分隔线；
- 搜索输入、按钮：小圆角；
- 标签/筛选器：可使用小胶囊，但数量受控；
- 工具列表：细边框列表项；仅在悬浮反馈或特定操作时使用轻微圆角；
- 浮层、菜单、抽屉：可使用较明显圆角与弱阴影；
- 禁止大面积玻璃拟态、强阴影、连续嵌套卡片和过度圆润的 SaaS 风格。

### 4.5 图标

- 系统控件使用少量、统一线性风格的**内联 SVG**；
- 不引入 Font Awesome、Material Icons 等第三方图标库；
- 搜索、返回、编辑、筛选、展开、外链、菜单、历史等采用一致 SVG 语义；
- 关键图标必须配合可见文字或 `aria-label`；
- 状态不能只用图标表达；
- 数据中原有的工具品牌 Emoji 可作为内容标识有限保留，不得作为系统控件主图标。

## 5. 轻量 UI 系统与技术边界

### 5.1 已确认技术现状

前端为零依赖的原生单页应用：

- 原生 HTML、CSS、浏览器原生 JavaScript；
- 无 React、Vue、Angular、Svelte、Tailwind、Bootstrap 等框架或 UI 库；
- 无 `package.json`、锁文件、TypeScript、Vite、Next.js 等前端构建配置；
- 单页通过 `.view.active` 与 `switchView()` 切换视图，无前端路由库；
- 浏览器用 `fetch()` 读取静态 JSON，不直接调用平台 API；
- Node.js 20 用于采集、构建和校验脚本。

关键前端文件：

- [src/web/index.html](../../src/web/index.html)
- [src/web/css/style.css](../../src/web/css/style.css)
- [src/web/js/app.js](../../src/web/js/app.js)

### 5.2 UI 系统实现策略

建立**设计令牌 + CSS 原语 + HTML 结构约定**的轻量 UI 系统，不引入框架或完整组件运行时。

1. **设计令牌**：颜色、字体角色、字号、行高、间距、边框、圆角、阴影、内容宽度、响应式断点、焦点与状态样式。
2. **CSS 原语**：页面容器、页面标题、查询条、按钮、筛选器、来源项、状态提示、折叠区、模态层、对比表、内容列表等。
3. **HTML 结构约定**：各视图按需保持差异，但共享导航、标题区、操作控件、信息状态、来源/更新时间、空错误状态与移动端收拢规则。

明确不做：引入 React/Vue、复杂模板编译系统、完整组件运行时、为组件化重写数据加载与业务函数、修改现有数据契约。

## 6. 首页与搜索入口

### 6.1 首页结构

采用**单列、居中的编辑部式首页**，首屏只承担“提出问题”这一主任务：

```text
AI 信息搜索
把你想了解的事，说清楚一点。

[ 用自然语言描述你的问题……                         ]
                                                [搜索]

你可以试试：
[写论文与查资料] [比较编程工具] [了解近期 AI 热点]

最近探索 / 从这里继续
（首屏下方或可折叠，低视觉权重）
```

规则：

- 不在首屏并列展示工具卡片、热点流或复杂筛选；
- 示例问题帮助初学者起步，但不得制造过多选择；
- 最近探索仅用于回访，不成为首页主视觉；
- 工具、场景、热点、概念通过导航或搜索结果进入。

### 6.2 查询输入

保持**单一自然语言输入框**，不拆分成多个结构化字段。

- 占位提示描述“工具、场景或问题”；
- 输入框下可提供少量示例问题；
- 用户输入过宽泛时，提供 2–3 条轻量改写建议，如补充任务、使用场景、限制条件、中文支持、免费层或引用需求；
- 高级筛选只出现在结果页，不阻塞首次搜索；
- 熟练用户应能直接输入、直接搜索。

## 7. 搜索过程、结果页与查询编辑

### 7.1 搜索过程

不设置独立进度页。用户点击搜索后，在结果内容区域显示短暂、固定的静态演示过渡，例如：

```text
正在整理你的问题
匹配已收录资料
准备示例摘要
```

规则：

- 仅 2–3 个阶段；
- 不显示百分比、预计剩余时间或虚假实时进度；
- 过渡后直接进入结果布局；
- 明确标注为静态演示流程；
- 支持减少动效；
- 重复提交相同示例时不强制重复长等待；
- 未支持的示例查询进入“暂无对应示例”，不得伪造回答；
- v1.0 可在同一位置升级为真实检索/流式状态。

### 7.2 结果页顶端与查询编辑

结果页默认显示**当前问题的只读状态**，点击“修改问题”后才展开编辑；不持续展示首页级别的大搜索框。

```text
← 返回 AI 搜索

当前查询
适合中文写论文、查资料的 AI 工具有哪些？   [修改问题]

────────────────────────

搜索摘要                     关键来源
```

- 点击“修改问题”后，将当前问题置入输入框；
- 可编辑、提交、取消；
- Enter 可触发新的静态演示查询；
- 不在结果页默认显示首页的示例问题组；
- 移动端同一逻辑纵向排列；
- 未来 v1.0 可自然升级为真实再次检索入口。

## 8. 搜索摘要、来源与引用

### 8.1 B16 的真实性表达

搜索摘要、热点摘要和概念解释等页面级内容统一遵循第 1.5 节的静态演示边界。搜索结果页具体使用“搜索摘要”或“信息整理”，不称为“AI 回答”，并保留以下提示：

> 静态演示 · 不代表实时联网检索或 AI 生成结果。

这样可以审查未来 AI 搜索结果的结构，同时不会把静态内容误导为模型推理、实时检索或动态证据链。v1.0 接入真实模型后，可在保留布局的前提下升级为“AI 综合回答”。

### 8.2 桌面端结果布局

采用已确认的**方案 2：左摘要 + 右来源**：

```text
┌──────────────────────────────┬─────────────────┐
│ 搜索摘要 / 信息整理           │ 关键来源        │
│ 结论、解释、内联引用 [1][2]   │ [1] 来源标题    │
│ 下一步建议                    │ [2] 来源标题    │
│                               │ [3] 来源标题    │
└──────────────────────────────┴─────────────────┘
```

此处允许合理的高信息密度：左侧负责连续阅读，右侧负责即时证据核验，减少频繁鼠标滚轮和“结论—来源”之间的定位成本。

右侧来源栏采用**仅在结果区域内适度粘性定位**：

- 进入结果区域后保持可见，到结果区域底部时停止；
- 不固定在整页视口，不遮挡导航、查询条或页脚；
- 不创建来源栏内部的复杂第二滚动容器；
- 默认显示前 2–3 条关键来源，更多来源经“查看全部来源”展开；
- 窄屏或大字号环境自动退化为普通双栏或上下布局。

### 8.3 移动端结果布局

移动端不强行压缩为双栏，采用自然上下流：

```text
搜索摘要
结论与解释……
[查看关键来源 3 条]

关键来源
[1] 来源标题
    来源类型 · 更新时间
    摘要
    查看资料 →

[2] …
[3] …

[返回摘要]
```

- 摘要下提供“查看关键来源”快捷锚点；
- 来源自然置于摘要之后；
- 提供“返回摘要”；
- 不使用底部固定来源抽屉或固定粘性来源栏，避免遮挡正文和增加原生 JS 交互复杂度。

### 8.4 引用和来源信息

采用**正文内联引用 + 桌面右侧关键来源 / 移动端下方关键来源**。

来源项至少包含：

- 编号；
- 标题；
- 来源类型；
- 更新时间；
- 一行摘要；
- 可追溯入口（资料详情或外链）。

规则：

- 默认仅显示直接关联摘要的 2–3 条来源；
- 更多来源折叠于“查看全部来源”；
- 来源信息不完整时明确写“更新时间未知”或“来源信息待补充”，不得默认伪装为最新；
- “静态演示”标识和“来源真实性/更新时间”标识必须分开表达；
- 不把每条来源包装为厚重卡片，优先编号和分隔线。

### 8.5 引用联动

已确认采用**双向定位 + 短暂高亮，不使用弹窗**。

- 点击摘要内联引用 `[1]`、`[2]` 等：定位到桌面右侧或移动端下方的对应来源，并短暂高亮来源项；不直接打开外部链接，用户仍需显式选择“查看资料”。
- 点击来源编号：定位回摘要中的对应引用或关联段落，并短暂高亮该引用/段落。
- 此联动不改变当前查询、筛选条件或页面结构。
- 引用与来源必须使用真实锚点/链接关系；高亮除颜色外，应配合边框、图标或“当前引用 / 当前来源”文字。
- 焦点移动应可预期，键盘用户可返回原位置；移动端从来源回到摘要后仍保留“查看关键来源”的快捷入口。
- 不使用弹窗、抽屉或来源栏内部第二滚动容器。

### 8.6 来源详情展开

已确认采用**当前页内联展开有限说明，完整资料再进入详情页**：

- 来源默认展示标题、来源类型、更新时间、一行摘要和可追溯入口；
- 点击来源项后，在当前页面内联展开有限的证据说明；
- 展开内容可包括关联结论/证据片段、来源类型、更新时间状态和来源与摘要的关系；
- 完整资料通过明确的“查看完整资料”入口进入详情页或原文，不在当前页伪造完整网页正文；
- 同时最多展开一个来源，避免来源栏无限增长；
- 移动端沿用自然上下结构；
- 展开控件必须支持键盘操作，并提供清晰的 `aria-expanded` 与关联内容；

### 8.7 历史记录与最近探索

已确认采用**首页低权重有限展示、结果页末尾继续探索、不建立复杂历史工作台**：

- 首页最多展示 2–3 条“最近探索”；没有历史时隐藏整个区域，不显示空容器；

### 9.8 全站 AI 概念索引联动

已确认新增一项跨全站功能：用户可在可阅读文本中识别 AI 概念词，并通过悬停预览和点击跳转理解概念。

2. 在概念词附近显示简短解释框；

5. 点击概念词或解释框，切换到 AI 概念视图，并显示对应概念。

- 优先匹配更长、更具体的概念词；
- 同一文本区间只标记一个概念；
- 已经是链接的文本不重复包裹；
- 概念词使用稳定概念 ID，跳转后由 AI 概念视图选中并展示对应条目；
- 仅处理用户可阅读内容，不处理导航/按钮、输入框内容、URL、时间/价格/评分等结构化字段、代码、解释框自身或其他排除区域。

### 9.8.1 键盘与移动端交互

- `Enter` 进入 AI 概念视图并显示对应概念；

- 解释框使用合适的非模态说明语义，不阻断页面其他内容。

#### 移动端/触屏

- 第一次点击概念词显示简短解释框；
- 第二次点击概念词或点击解释框中的“查看概念”进入 AI 概念视图；
- 点击页面其他区域关闭解释框；

- 概念词和“查看概念”均必须是可操作、可感知的控件。

### 9.8.2 概念词匹配字段与误匹配控制

已确认：**只匹配 glossary 的名称/别名，使用稳定概念 ID；通过长词优先、排除词、上下文规则和 DOM 排除区域控制误匹配**。

允许匹配的字段：

- `concept.name`；
- `concept.aliases[]`；
- 已确认的中英文名称或缩写。

不自动匹配：

- 定义正文、示例正文；
- 相关工具名称；
- 热点标题中的普通词；
- URL、价格、日期、评分；
- 任意外部文本中的临时词。

控制规则：

- 优先匹配更长、更具体的词；
- 对短缩写设置最小上下文或大小写规则；
- 对普通多义词建立排除列表；
- 同一文本区间只包裹一次；
- 跳过已是链接、按钮、输入框、代码和结构化数据的 DOM 区域；
- 只有 glossary 中存在稳定概念 ID 的词才生成解释框；
### 9.8.3 概念解释框内容与视觉形式

已确认采用**概念名称 + 一句话定义 +“查看 AI 概念”操作的轻量信息卡**：

- 默认仅显示概念名称、简短定义和跳转操作；
- 简短定义来自 glossary 现有字段；
- 文案控制在一两句话，不显示完整示例、相关工具列表或长来源；
- 桌面端解释框靠近概念词定位，超出视口时自动调整方向；
- 概念词与解释框之间应允许鼠标移动，不因小间隙立即消失；
- 使用弱边框、暖白表面和轻微阴影，不做强视觉弹窗；

- 不显示未经核验的推荐或动态 AI 内容。

- 简短解释来自 glossary 静态数据；

| AI 概念 | 查阅定义、建立理解 | 桌面轻量索引 + 文章式详情；移动端上下布局；支持全站 glossary 概念索引联动 |
| 关于 | 理解产品定位 | 单列叙事页 |

这些是已确认或明确标注状态的布局原则，并不增加现有页面业务能力。

## 10. 状态与反馈

### 10.1 异常状态的通用结构

所有异常状态采用：

> **发生了什么 + 影响范围 + 下一步操作。**

不得使用单一“没有结果”覆盖所有情形，不得用乐观文案掩盖资料缺失，也不得生成没有依据的摘要。

| 状态 | 表达重点 | 可提供操作 |
|---|---|---|
| 空输入 | 请先描述想了解的内容，并给出示例。 | 输入/选择示例问题 |
| 无匹配 | 当前静态资料没有覆盖该问题。 | 修改问题、查看示例问题 |
| 部分资料不可用 | 已保留可用内容；缺失资料不等于没有相关信息。 | 查看可用结果、稍后重试 |
| 处理失败 | 演示整理未完成；不会生成无依据摘要。 | 重新尝试、返回搜索 |

- 静态 mock 的失败不可伪装成真实搜索服务失败；
- 状态颜色仅辅助，文字和操作必须完整；
- 为 v1.0 预留超时、来源缺失和服务降级等状态映射。

### 10.2 反馈

原型可以提供“有帮助 / 没有帮助”的本地状态，用于验证位置和交互；B16 不假定存在真实反馈持久化能力。

已确认：**B16 保留本地反馈、详情、来源、对比和搜索操作；暂不做真实收藏、账户同步、分享和个人工作区**。

可以保留：

- “有帮助 / 没有帮助”本地反馈；
- “加入对比”（仅在当前条目已有现有对比能力时）；
- 查看工具详情；
- 查看来源；
- 重新搜索/修改问题；
- 复制查询或复制摘要（仅用于原型验证位置，不接入云端）。

B16 暂不做：

- 账号级收藏、云端同步、分享链接；
- 文件夹、标签、批量管理或收藏夹页面；
- 真实反馈上报或基于反馈改变推荐结果；
- 一键执行或外部工具调用；
- 个人工作区。

收藏、保存、继续追问和分享等能力待 v1.0 真实会话模型确定后再设计。

### 10.3 加载状态

已确认采用**首次加载结构占位、局部刷新状态、搜索区域内静态阶段过渡，不使用全屏等待遮罩**：

#### 首次加载

- 工具库、场景列表、热点列表等内容区域显示少量结构占位，模拟标题、摘要和列表行；
- 不使用大量闪烁动画，并支持 `prefers-reduced-motion`；
- 页面导航和已加载的静态框架保持可见。

#### 局部刷新

- 搜索、筛选、排序时只在受影响区域显示“正在整理/正在更新”；
- 搜索按钮进入短暂处理中状态；
- 不遮挡整个页面；
- 原有内容可以保留并降低视觉强调，避免页面突然变空。

#### 静态搜索 mock

静态搜索阶段统一遵循第 7.1 节定义：使用 2–3 个固定阶段，明确标注静态演示，不使用真实百分比、剩余时间或虚假实时进度。此处仅补充加载区域的局部刷新和减少动效要求。

不采用全屏 loading 遮罩、页面中央长期旋转图标、所有页面完全相同的骨架结构，或将静态数据伪装成复杂后台任务。



## 11. 响应式与无障碍

### 11.1 响应式策略

已确认采用**内容驱动的宽桌面 / 窄桌面或平板 / 移动端三档策略**，最终断点由内容可读性决定，而不是由固定设备型号决定。

#### 宽桌面

- 展示摘要/来源并列；
- 展示概念索引/详情双区；
- 对比图表和结构化表格保留横向关系；
- 工具库可使用双列；
- 来源栏可在结果区域内适度粘性定位；
- 桌面导航显示分组后的主要入口。

#### 窄桌面/平板

- 结果页根据可用宽度决定双栏或上下布局；
- 右侧来源栏取消粘性；
- 概念索引可收窄为可折叠或顶部选择；
- 对比表允许横向滚动；
- 工具库从双列逐步降为单列；
- 导航减少次级文字，保留菜单入口。

#### 移动端

- 摘要与来源上下排列，取消来源粘性；
- 概念索引与详情上下排列；
- 对比图表按指标分组，定性信息逐工具卡；
- 工具库、场景、热点、概念详情单列；
- 使用 Logo + 当前页标题 + 菜单；
- 优先保证触控目标、正文行高和解释框可读性。

最终断点应由最小可读正文宽度、来源栏最小宽度、图表标签碰撞、导航溢出、触控目标和大字号设置共同决定，不在方案阶段预先锁死具体像素值。



### 11.2 无障碍基线

- 使用语义 HTML：`header`、`nav`、`main`、`article`、`aside`、`button`、`form` 等；
- 图标按钮提供可读 `aria-label`；
- 键盘可访问搜索、查询编辑、引用、来源、筛选和折叠控件；
- 焦点状态清晰可见，不仅通过颜色或阴影表达；
- 引用 `[1]` 与来源存在可理解的链接关系；
- 来源高亮不只使用颜色；
- 折叠区域具备正确展开状态和关联内容；
- 加载/错误状态使用文本或 `aria-live` 传达；
- 支持 `prefers-reduced-motion`；
- 文字/背景对比度达标；
- 移动端触控目标保持足够可操作尺寸；
- 不以 Emoji 代替关键图标或状态。

不在 B16 首期承诺：所有历史无障碍缺陷的完整清零、复杂专用屏幕阅读器导航模式、独立无障碍设置中心。

本文已固化到已确认的第 100 项；第 101–103 项在第 14 章补充记录。AI 热点采集、AI 处理、人工审核和公开展示的已确认规则已记录在本章；未确认内容不属于正式实施方案。

2. 热点和概念详情的来源/更新时间展示细节；

### 13.1 决策 46：B16 AI 热点审核管理方式

已确认采用**GitHub Issue/PR + CLI 过渡审核**，B16 暂不建设独立可视化管理后台。

推荐的 B16 目标流程为：

```text
采集候选热点
  ↓
AI 处理并生成审核材料
  ↓
通过 GitHub Issue/PR + CLI 提交人工审核
  ↓
管理者选择通过 / 保留 / 丢弃
  ↓
GitHub Actions 读取审核结果
  ↓
只有通过内容进入 hotspots.json 和公开热点视图
```

该方案符合当前 GitHub Actions + GitHub Pages + JSON 的架构，避免在 B16 阶段引入后端、数据库、认证和新的部署系统。独立私有管理端可以作为 v1.0 的演进方向，但在本项决策中不作为 B16 首期实现范围。

### 13.2 决策 47：AI 热点审核材料的主要载体

已确认采用**PR 作为主要审核载体，Issue 作为异常讨论和补充记录**。

推荐分工：

- **PR**：提交候选热点的结构化审核材料，供管理者查看原始来源、AI 处理结果和 JSON 差异，并通过合并作为进入后续发布流程的审核信号；
- **Issue**：记录来源争议、处理失败、需要补充的信息、规则误判和其他不适合直接通过 PR diff 表达的异常情况。

PR 作为主要审核载体的理由：

- 候选热点最终需要落入 JSON，PR diff 与数据审核天然匹配；
- 多条热点可以在同一批次中审核；
- Git 历史可以保留审核前后的结构化数据变化；
- 合并动作比解析 Issue 评论中的自然语言状态更稳定。

本项只确定载体分工，不提前确定具体审核字段、标签命名、批量审核命令或 PR 合并后的公开投影实现。

### 13.3 决策 48：PR 中的热点审核状态表达

已确认采用**每条热点使用独立的审核状态字段**，不以 PR 合并动作直接代表整批热点全部通过。

建议状态值为：

- `pending`：待审核；
- `approved`：通过，可进入公开投影；
- `held`：保留在审核数据中，暂不公开；
- `discarded`：丢弃，不进入公开投影。

该决策意味着：

- 一个 PR 可以同时包含多条候选热点，并分别处理其审核结果；
- PR 合并不自动意味着其中所有热点都通过；
- 只有单条记录的 `review_status` 为 `approved` 时，才具备进入 `hotspots.json` 的资格；
- `held` 和 `discarded` 记录可以继续保留在内部审核数据中，用于复审、审计和规则改进；
- 审核结果不依赖解析 Issue 评论或 PR 自然语言内容。

本项只确认审核状态的表达方式；`held` 的语义见决策 50，公开投影触发方式见决策 59。

### 13.4 决策 49：AI 热点候选数据与公开热点数据分层

已确认采用**内部候选 JSON + 最终公开 `hotspots.json` 的两层数据流程**：全部抓取候选先进入不公开的内部数据，经过 AI 初步审核和管理者人工审核后，再生成整合后的公开 `hotspots.json`。

```text
全部抓取内容
  ↓
内部候选 JSON（不发布、不供浏览器读取）
  ↓
AI 初步审核与结构化处理
  ↓
管理者逐条设置 review_status
  ↓
构建脚本整合、过滤并生成公开 hotspots.json
  ↓
热点视图和 RSS 只读取最终公开结果
```

内部候选数据可以保留：

- 全部抓取候选，包括视频和暂时无法判断的内容；
- 原始标题、描述、来源链接、发布时间、平台、native ID 和抓取时间；
- AI 初步判断、AI 置信度、AI 结构化摘要和处理状态；
- 重复关系、过滤原因、处理失败信息和审核状态；
- 后续人工审核所需的原始来源和处理记录。

内部候选数据不得通过公开构建发布到 `dist/`，浏览器也不得直接读取。建议继续使用现有运行时目录边界，例如：

```text
data/news/runtime/hotspot-candidates.json
```

公开数据仍使用：

```text
data/news/output/hotspots.json
```

它代表经过公开资格过滤后的最终整合结果。公开资格总规则：

- `review_status = approved`；
- `ai_processing_status = completed`；
- AI 初步审核判断为有效 AI 热点；
- 视频内容具备可追溯字幕/文字稿依据并通过人工审核时，同样可以进入公开数据；
- 内容属于近期时间窗口；
- 标题、摘要、来源链接和发布时间等公开字段完整；
- 未被判定为重复、丢弃或已被替代；
- 关键 AI 摘要和要点具备可追溯原始依据。

公开投影和 RSS 均只消费满足上述条件的最终数据。后续章节如涉及视频、`held`、`error` 或来源依据，只补充特例，不重复定义公开资格。

这项决策保留第 48 项“每条热点独立设置审核状态”的规则，同时明确：审核状态作用于内部候选记录，公开 `hotspots.json` 是审核完成后的下游投影，而不是审核队列本身。具体字段组织和 AI 处理记录存储方式在实施前复核。

### 13.5 决策 50：`held` 保留状态的语义

已确认采用**“保留 = 内部暂存、后续复审、不公开”**的定义。

`held` 用于处理当前信息不足、暂时不能通过，但也没有足够理由直接丢弃的候选内容。例如：

- 内容看起来可能是有效的 AI 产品或技术热点；
- 当前来源只是转载，缺少官方来源或可靠上下文；
- 发布时间缺失或无法确认近期性；
- 原始描述过短，暂时无法核验 AI 相关性；
- 需要等待补充来源、重新抓取或再次 AI 处理。

四种审核状态的区别：

| 状态 | 含义 | 是否进入公开 `hotspots.json` | 后续动作 |
|---|---|---:|---|
| `pending` | 当前等待管理者审核 | 否 | 管理者现在处理 |
| `approved` | 已确认可以公开 | 是（还需通过公开资格校验） | 进入公开投影 |
| `held` | 暂时不能决定，但保留候选 | 否 | 等待补充信息或后续复审 |
| `discarded` | 已确认不应公开 | 否 | 保留记录用于审计，通常不再处理 |

推荐状态流转：

```text
pending
  ├── approved
  ├── discarded
  └── held
        ↓
    补充信息 / 重新处理
        ↓
      pending
```

`held` 与 `pending` 的显著区别是：`pending` 表示“现在请审核”，`held` 表示“当前暂缓决定，等待条件满足后再审核”。`held` 不是暂时公开、默认展示或自动通过；它不会进入热点视图，也不会进入 RSS。

进入 `held` 时应记录原因，例如“等待官方来源”“发布时间待确认”或“内容上下文不足”，必要时记录预计复审时间。重新进入 `pending` 必须产生新的审核记录，不应静默修改历史状态。

本项继续沿用每条热点独立设置 `review_status` 的规则，并确认 `held` 只作用于内部候选数据。

### 13.6 决策 51：AI 初审结果与人工审核队列（按视频内容澄清修订）

原先“视频候选默认隐藏、不进入 AI 初审”的表述已被本次需求澄清修订，不再作为有效方案。热点视图“不展示视频信息”的含义不是排除视频来源，而是**不直接展示视频本体及其全部原始内容；视频内容也应进入 AI 处理，通过字幕或可获取的文字稿进行浓缩，提取要点后再参与审核和展示**。

因此，目标流程调整为：

```text
全部候选进入内部 JSON
  ↓
识别内容类型
  ├── 非视频内容 → 提取标题、正文、描述等文字
  └── 视频内容 → 获取可用字幕/文字稿，并提取视频元信息
  ↓
AI 初步审核与内容浓缩
  ↓
管理者审核 AI 提取结果
  ↓
通过的内容以统一的热点摘要形式进入公开 hotspots.json
```

视频与非视频内容都可以进入 AI 初步处理。差异在于 AI 的输入材料：

- 非视频内容主要使用标题、正文、摘要或帖子文本；
- 视频内容优先使用字幕或文字稿，并结合标题、简介、发布时间和来源信息；
- 字幕或文字稿缺失、过短或无法可靠提取时，不能凭标题臆造要点，应标记为信息不足，进入待补充、`held` 或处理失败路径；
- 不使用绕过平台限制、逆向接口或违反现有采集边界的方式获取视频内容。

视频经审核通过后，与文字内容一样进入热点视图，展示的是浓缩后的热点内容（AI 工具、AI 产品、AI 概念、AI 技术动态、AI 行业事件等），而不是视频本体、完整字幕或全部原始内容。热点视图不把“视频 / 非视频”作为展示分类，也不以“视频来源”作为热点内容的主要标识；来源平台等元信息仍作为来源信息的一部分保留，但视频来源标识的具体呈现形式以热点内容分类为优先，后续单独确认。

因此，视频不再默认从审核队列中隐藏，也不再统一标记为不可公开。管理者审核的是 AI 浓缩后的要点及其来源依据；只有管理者设置单条 `review_status` 为 `approved`，并通过公开资格校验后，才进入 `hotspots.json`。

本项暂不确定 AI 结果枚举的最终命名、字幕获取范围、视频摘要所需的最小证据、默认队列的筛选字段、管理者查看处理失败候选的具体 CLI 参数，以及视频来源在公开视图中的链接和标识形式。

### 13.7 决策 52：视频字幕缺失时的处理

决策 51 已定义视频进入 AI 处理的整体路径。本节只规定字幕/文字稿异常的状态映射和复审规则：

已确认：**YouTube 视频优先使用可获取的自动字幕或其他文字稿进行 AI 浓缩；Bilibili 当前采集已搁置；字幕或文字稿缺失、过短或质量不足时进入 `held`；技术获取失败时进入 `ai_processing_status: error`。**

处理规则：

- YouTube 视频优先尝试获取自动字幕；如果存在人工字幕或其他可靠文字稿，也可以作为 AI 处理输入；
- AI 输入应记录字幕/文字稿的来源类型、获取状态和内容指纹，便于追溯本次浓缩依据；
- 字幕缺失、文本过短或质量不足时，保留原始候选、标题、简介、链接和发布时间，但不能仅凭这些信息生成确定性摘要；此类情况标记为证据不足，设置 `review_status: held`，并记录 `hold_reason`；
- 如果字幕或文字稿的技术获取过程失败，设置 `ai_processing_status: error`，同时保留候选并进入人工异常处理；
- 后续补充字幕或文字稿后，重新进行 AI 处理，并将候选重新置为 `pending`，由管理者再次审核；
- `held` 候选不进入公开 `hotspots.json`，也不进入 RSS；
- 本项不改变现有关于 Bilibili 自动采集和平台边界的决定，Bilibili 字幕获取留待未来重新启用相关采集时单独讨论；
- 不使用绕过平台限制、逆向接口或违反现有采集边界的方式获取字幕。

推荐的视频异常状态路径为：

```text
YouTube 视频
  ↓
尝试获取自动字幕/可靠文字稿
  ├── 技术获取失败 → ai_processing_status: error → 异常处理
  ├── 获取成功 → AI 浓缩 → pending → 人工审核
  └── 获取成功但缺失、过短或质量不足 → review_status: held → 后续补充字幕 → 重新处理
```

### 13.8 决策 53：AI 对标题的处理边界

已确认采用**保留原始标题，AI 生成展示标题建议，由管理者决定是否采用**的方式。

审核材料中同时保留：

- 原始标题：来自来源的不可变记录，不能被 AI 覆盖；
- AI 展示标题建议：用于把过长、口语化或标题党表达整理成适合热点视图的标题；
- 管理者最终展示标题：人工可以采用 AI 建议，也可以修改或继续使用原始标题；
- AI 摘要和要点：必须能够回溯到原始正文、字幕或文字稿中的依据；
- 原始来源链接、发布时间以及字幕/文字稿引用信息。

AI 不能静默修改或删除原始标题。管理者最终确认的展示标题必须保留修改记录，并能追溯到对应的候选版本和审核动作。

### 13.9 决策 54：AI 处理结果与原始依据的并列审核

已确认：**管理者审核时必须同时看到 AI 处理结果和原始依据，不能只根据 AI 摘要或要点做决定。**

PR 审核材料至少应并列提供：

- 原始标题；
- AI 展示标题建议；
- AI 摘要和提取要点；
- 原始正文、描述或帖子文本中的依据片段；
- 视频字幕或文字稿中的依据片段；
- 视频依据对应的字幕时间段（如果可以获取）；
- 来源名称、来源链接、内容类型和发布时间。

视频审核材料可以采用以下形式：

```text
AI 要点：
该工具新增了本地知识库问答功能。

字幕依据：
02:14–02:42
“现在用户可以上传自己的文档，并在本地知识库中进行问答……”
```

原始依据应保持可追溯，不能只保留 AI 选出的片段而丢弃原始来源关系。管理者需要能够从 AI 要点回到对应原文、字幕或文字稿位置；如果无法建立可靠依据关系，应降低审核信心或使用 `held`，而不是直接通过。

依据要求细化到要点级：

- AI 生成的每个要点应尽量对应原始正文、描述或字幕中的一段可定位依据；
- 审核材料显示“要点 ↔ 依据”的对应关系；
- 无法定位依据的要点，在审核材料中明确标记为“无直接依据”；
- 管理者通过时，应确认关键要点有依据支撑；
- 无依据的要点不能作为公开内容的确定性表述。

示例：

```text
要点：该工具新增本地知识库问答
依据：字幕 02:14–02:42“……本地知识库问答……”

要点：支持团队协作
依据：无直接依据（标记提示）
```

本项只确定审核材料必须同时包含 AI 结果和原始依据，并细化到要点级证据，不提前确定 PR 中的具体 Markdown 模板、依据片段长度、字幕时间段格式和完整原文的存储方式。

### 13.10 决策 55：管理者修改审核状态的方式

已确认采用**管理者直接编辑 PR 中候选 JSON 的 `review_status`，并填写审核理由和基本审核信息**的方式。

管理者可以对每条候选执行：

```text
pending → approved
pending → held
pending → discarded
```

本项的目的和边界：

- 与“每条热点独立状态字段”的决策保持一致；
- Git diff 可以直接显示每条记录的审核变化；
- 不需要解析 PR 评论中的自然语言来推断审核结论；
- GitHub Actions 可以稳定读取状态字段并生成最终公开投影；
- 一次 PR 可以审核多条候选，但每条候选仍必须单独设置状态；
本项只确认管理者通过编辑 PR 中 JSON 完成审核；审核字段、版本号、批次号和追加式审核日志统一见决策 70。

### 13.11 决策 56：明确选中候选的批量通过

已确认支持**批量通过热点，但批量范围必须来自管理者明确选中的候选记录**。

推荐流程：

```text
管理者明确选择候选 A、B、C
  ↓
执行批量通过
  ↓
分别为 A、B、C 写入 approved 和对应审核信息
  ↓
继续执行统一公开资格校验
```

批量通过规则：

- 只处理管理者明确选中的记录；
- 不支持“当前筛选结果全部通过”等隐式范围操作；
- 每条记录仍保留独立的 `review_status`；审核字段、审核理由和审核记录统一按决策 70 的追加式日志规则处理；
- 视频字幕不足、AI 处理失败、记录已变化或存在版本冲突的候选，应逐条阻止或报告，不能因为批量操作而绕过条件；
- 某一条记录失败不应静默覆盖其他记录的审核结果；
- 批量设置为 `approved` 后，仍必须经过公开资格校验，不能直接写入公开 `hotspots.json`；
- 批量操作本身也应在 PR diff 和审核记录中可追溯。

本项只确认批量通过的范围和安全边界，不提前确定批量操作由 CLI 命令、脚本还是人工批量编辑完成。

### 13.12 决策 57：AI 处理失败与 `error` 异常审核状态

已确认增加独立的 **`error` 状态**，表示 AI 处理流程失败；错误内容可以被单独筛选、指派和人工处理，但不能直接进入公开数据。

推荐状态关系：

```text
候选内容
  ↓
AI 处理
  ├── 成功 → pending，等待人工审核
  ├── 失败 → error，进入异常审核队列
  └── 证据不足 → held，等待补充材料
```

`error` 与其他状态的区别：

| 状态 | 含义 | 主要原因 |
|---|---|---|
| `error` | AI 处理流程没有成功完成 | API 超时、技术获取字幕失败、返回格式错误、额度或网络问题 |
| `held` | 内容暂时无法判断，等待补充或复审 | 字幕过短、来源上下文不足、发布时间待确认 |
| `pending` | 已经有完整审核材料，等待管理者判断 | 正常人工审核 |
| `approved` | 管理者确认可以公开 | 进入公开资格校验 |
| `discarded` | 管理者确认不应公开 | 不进入公开投影 |

`error` 不等于“完全没有任何文本”。失败时可能是：

- 完全没有 AI 输出；
- 只有不完整的标题建议、摘要或要点；
- 有完整文本，但结构校验失败或缺少可追溯依据。

因此，`error` 记录可以保留原始标题、描述、来源链接、发布时间、已获取的字幕/文字稿、部分 AI 输出、错误类型、是否可重试和重试次数，但不应把不完整结果当作正常审核材料或公开内容。

错误内容允许两条后续路径：

```text
error
  ├── 重新执行 AI 处理 → 成功后进入 pending
  └── 指派人工处理 → 补齐结构化内容和依据 → 回到 pending
```

人工补齐后仍必须回到 `pending`，再由管理者确认 `approved`，避免同一处理动作直接绕过正常审核。可以使用类似以下结构区分处理状态和审核结论：

```json
{
  "ai_processing_status": "error",
  "error_type": "transcript_unavailable",
  "retryable": true,
  "retry_count": 1,
  "review_status": "pending"
}
```

在当前 GitHub PR + CLI 过渡方案下，`error` 候选可以通过专门标签或筛选条件进入异常审核队列，并指派给具体处理者；处理完成后仍通过 PR diff 留下记录。

本项只确认 `error` 的语义、人工处理路径和不得直接公开的边界，不提前确定错误类型枚举、指派字段、重试次数上限和具体 CLI 命令。

### 13.13 决策 58：按抓取批次组织审核 PR

已确认采用**一轮抓取生成一个批次审核 PR**的方式。

一个批次 PR 可同时包含不同审核状态的候选；具体公开投影流程见决策 59，AI 初审时机见决策 60，PR 模板与过大批次拆分见决策 71。

采用批次 PR 的理由：

- 同一轮抓取的候选集中在一个明确范围内；
- 管理者可以在同一 PR 中查看本批次的变更和 AI 审核材料；
- 支持对明确选中的多条记录批量通过；
- Git diff 可以保留本轮新增、更新和审核状态变化；
- 避免每条热点单独创建 PR，降低通知和管理负担。

PR 过大时，可以按平台或其他明确规则拆分，但每个 PR 必须保持批次范围清晰，并在 PR 描述中注明抓取批次、来源范围和候选数量。

### 13.14 决策 59：PR 合并后的公开投影

已确认采用**PR 合并后由 GitHub Actions 自动触发公开数据构建，并在校验通过后生成最终 `hotspots.json`**的方式。

```text
PR 合并
  ↓
GitHub Actions 自动触发
  ↓
检查每条记录：
  - review_status 是否为 approved
  - AI 处理是否成功
  - 是否有标题、摘要、来源和发布时间
  - 是否有可追溯依据
  ↓
生成最终 hotspots.json
  ↓
部署到公开热点视图
```

如果校验失败：

- 不生成新的公开投影；
- 保留上一版有效的 `hotspots.json`；
- 在 GitHub Actions 中报告失败原因；
- 不影响已经公开的上一版内容。

本项只确认 PR 合并后的自动构建和失败保护；具体校验脚本、发布工作流拆分、RSS 同步方式和部署触发细节在实施前复核，公开资格条件统一见第 13.4 节。

### 13.15 决策 60：AI 初步审核的运行时机

已确认采用**每次抓取完成后自动运行 AI 初步审核与内容浓缩，再生成批次审核 PR**的方式。其流程与批次 PR 组织见决策 58；本项只补充 AI 初审在抓取完成后的触发时机。

### 13.16 决策 61：审核 PR 中的原始内容保留范围

决策 54 已定义 AI 结果与原始依据必须并列核验。本节只规定存储范围：**PR 中保留审核所需的原始依据片段，完整正文和完整字幕仅保存在内部记录。**

- PR 保留足以核验要点的原始标题、必要片段、字幕时间段、来源和链接；
- 完整正文、完整字幕、完整 AI 原始响应和内部处理过程不直接放入 PR；
- 完整内部记录继续用于审计、重新处理和数据核对；
- 证据片段不足时设为 `held`、`error` 或指派补充材料，不直接通过。

本项只确认 PR 中展示依据片段的存储范围，不重复定义决策 54 的要点级证据要求。

### 13.17 决策 62：候选去重、同事件多来源处理与重复内容的审核方式

已确认采用**原生 ID 强去重 + 事件级聚合保留多来源；主记录正常审核，重复来源作为佐证，不单独创建审核任务**的方式。

```text
同一 platform:native_id
  → 只保留一个主记录（强去重）

不同来源报道同一事件
  → 保留多个来源观察
  → 归并到同一事件
  → 主来源 + 其他来源作为佐证

审核时
  → 主记录进入 pending，正常审核
  → 其他来源作为该主记录的佐证来源附加
  → 不为主记录之外的重复来源单独创建审核任务
```

具体规则：

- **强去重**：`platform:native_id` 相同的记录视为同一条内容，只保留一条主记录，避免重复抓取和重复审核；
- **事件聚合**：不同来源报道同一事件时，不强行合并成一条热点，而是保留多个来源观察并归并为同一事件；
- **审核组织**：主记录正常进入审核队列；其他来源作为佐证来源附加到主记录，不单独进入审核队列，不为主记录之外的重复来源单独创建审核任务；
- 公开时可以为事件选择一条主来源，其余来源作为佐证来源保留；
- 事件聚合只作为候选线索，不自动判断哪个来源更权威；
- 无法确认是否属于同一事件时，不强行归并，标记为“疑似同事件”，交由管理者确认是否归并；如果管理者判断不是同一事件，则拆开分别审核；
- 去重和聚合都不删除原始观察记录，只调整主记录、来源关系和事件归属。

本项只确认去重、同事件聚合与重复内容的审核组织方式，不提前确定事件 ID 生成规则、主来源选择标准、疑似同事件的具体判定阈值、佐证来源在审核材料中的展示格式和公开数据的来源展示格式。

### 13.18 决策 63：公开热点的时间窗口

已确认采用**默认 30 天近期窗口，以内容的发布时间为准，并在公开投影时作为硬性校验条件**的方式。

具体规则：

- 默认近期窗口暂定为 30 天，作为配置项而不是硬编码；
- 使用内容的**发布时间**判断近期性，不使用抓取时间伪装；
- 公开投影生成时再次检查时间窗口，确保过期内容不会长期停留在热点视图；
- 发布时间缺失或明显异常的内容不能进入公开数据；
- 未来时间超出容错范围的内容标记为异常，进入 `held` 或 `error` 处理路径；
- 前端可以再次隐藏超出时间窗口的记录，作为第二道防线；
- 窗口天数作为配置，后续可以调整。

本项只确认时间窗口的默认值和校验边界，不提前确定配置的具体存放位置、未来时间容错分钟数，以及前端重新隐藏记录的具体实现。

### 13.19 决策 64：旧热点数据迁移

已确认采用**旧数据进入内部候选库，标记为 legacy，进入待审核流程，不自动公开**的方式。

```text
现有 hotspots.json 旧数据
  ↓
导入内部候选库
  ↓
标记为 legacy 旧记录
  ↓
进入 pending 或 held
  ↓
管理者逐批审核
  ↓
通过后再进入新的公开 hotspots.json
```

具体规则：

- 不违反“只有审核通过才能公开”的新规则；
- 避免旧数据被自动批准；
- 管理者可以决定哪些旧内容值得保留；
- 旧记录可以增加类似标记，便于识别来源和迁移状态：

```json
{
  "legacy": true,
  "original_source": "旧 hotspots.json"
}
```

- 公开热点数量可能在迁移期间暂时下降，需要在空状态或视图中说明当前数据处于审核建立阶段，而不是系统故障。

本项只确认旧数据迁移的总体方式，不提前确定旧数据的字段映射、审核批次拆分、旧记录与现有来源的对应关系，以及空状态文案。

### 13.20 决策 65：热点视图的展示内容与分类维度

已确认：**热点视图展示的是“热点内容”，而不是视频或任何视频相关内容。热点内容按内容类型分类，可以包括但不限于：**

- AI 工具；
- AI 产品；
- AI 概念；
- AI 技术动态；
- AI 行业事件；
- 其他与人工智能相关的热点内容。

关键边界：

- 热点视图的展示维度是**内容类型**，不是“视频 / 非视频”等来源媒体类型；
- 视频或文字只是信息来自哪里，不影响热点如何分类和展示；
- 视频来源的内容经过字幕提取和 AI 浓缩后，产出的是上面这些“热点内容”，不是“视频内容”；
- 热点视图不直接播放视频、不展开完整字幕、不呈现完整原始内容，也不把“视频”作为展示分类；
- 来源平台、来源链接和发布时间等元信息仍作为来源信息的一部分保留，具体展示形式后续确认，但热点内容分类始终优先于来源媒体标识。

本项只确认热点视图展示的内容类型和分类维度，不提前确定热点类型枚举的最终命名、内容卡片的具体字段和热点视图布局。

### 13.21 决策 66：热点类型的归属决定

已确认采用**AI 初步建议热点类型，管理者在审核时确认或修改**的方式。

规则：

- 热点类型（AI 工具、AI 产品、AI 概念、AI 技术动态、AI 行业事件、其他等）是审核材料的一部分；
- AI 只提供类型建议，不能决定最终类型；
- 管理者可以确认、修改或重新归类热点类型；
- 管理者对热点类型的修改保留在审核记录中，可以追溯到修改动作和原因；
- “其他”类型尽量少用，只有 AI 与管理者都认为无法归入已有类型时才使用；
- 未完成审核或 AI 处理失败的内容不进入公开数据，因此不会以“其他”等临时类型公开。

本项只确认热点类型由管理者最终决定，不提前确定热点类型枚举的完整集合、管理者修改类型时的字段定义和类型与来源的对应关系。

### 13.22 决策 67：AI 输入材料的最小范围

已确认采用**AI 只处理已采集到的标题、正文、摘要或字幕，不主动抓取外部网页全文**的方式。

输入规则：

- 非视频内容：使用标题 + 正文 / 摘要 / 帖子文本；
- 视频内容：使用标题 + 简介 + 字幕 / 文字稿；
- 不要求 AI 自动访问来源链接去抓取完整网页；
- 标题、正文或字幕都不足时，进入 `held` 或 `error` 处理路径，而不是让 AI 自行联网补全；
- 字幕或正文过长时，可以分段处理或截取关键部分，但需保留处理记录，说明截取或分段方式。

选择这个方式的原因：

- 保持 AI 处理成本可控；
- 减少对外部网页和平台的运行时依赖；
- 避免来源链接变化导致处理不稳定；
- 审核仍以内部抓取并保存的原始材料为依据，便于追溯和重新处理。

本项只确认 AI 的输入边界，不提前确定截取或分段的触发阈值、正文上限长度和分段处理的具体实现。

### 13.23 决策 68：内部候选数据与 AI 处理记录的分文件存储

已确认采用**候选主记录与 AI 运行记录、字幕、审核日志分文件存储**的方式，但不拆成过多小文件。

建议内部候选数据按职责目录组织：

```text
data/news/runtime/candidates/
├── 候选主记录（每条候选的结构化审核结果）
├── ai-runs/（AI 处理运行记录）
├── transcripts/（字幕 / 文字稿）
└── review-events/（审核事件日志）
```

各文件职责：

- **候选主记录**：包含 AI 摘要结果、依据片段、热点类型、审核状态和审核信息，是管理者在 PR 中直接查看和修改的核心文件；
- **AI 运行记录**：保存模型、提示词版本、输入输出指纹、token 用量、原始响应引用和处理状态，单独存放以避免候选主记录和 PR 过大；
- **字幕 / 文字稿**：保存完整字幕等原始材料，符合“完整正文 / 字幕不进 PR”的决策，供需要时查看和重新处理；
- **审核事件日志**：只追加、不改写，记录每次审核状态变化，便于审计和追溯。

边界：

- 候选主记录必须是一份完整、可直接审核的 JSON，不为每个字段单独建文件；
- 分文件存储只用于隔离体积较大、不需要管理者逐条查看的内容；
- 所有文件仍位于内部运行时目录，不发布到公开 `dist/`。

本项只确认存储拆分方向，不提前确定目录的确切命名、候选主记录与 AI 运行记录的字段清单，以及字幕文件的命名规则。

### 13.24 决策 69：AI 处理状态与人工审核状态作为独立状态轴

已确认采用**`ai_processing_status` 与 `review_status` 作为两个独立状态轴，公开投影时同时校验**的方式。

两者描述的内容不同：

| 状态轴 | 描述什么 | 状态值示例 |
|---|---|---|
| `ai_processing_status` | AI 处理流程是否成功完成 | `not_requested` / `queued` / `processing` / `completed` / `error` |
| `review_status` | 人工审核的结论 | `pending` / `approved` / `held` / `discarded` |

规则：

- 系统失败（如 `error`）与人工决定（如 `discarded`）不能混淆，必须由不同状态轴表达；
- AI 未处理完成时，不应出现 `approved`；
- 一个候选可能有多条 AI 运行记录，但当前生效的处理结果只有一个；
- 公开资格校验必须同时检查两个状态，例如：

```text
仅当 ai_processing_status = completed
  AND review_status = approved
才可进入公开投影
```

本项只确认两个状态轴的存在与公开校验方式，不提前确定各状态轴的完整枚举值、两个状态轴的非法组合列表和校验失败时的具体处理。

### 13.25 决策 70：审核记录的完整字段

已确认采用**审核字段 + 版本号 + 批次号，审核日志只追加、不改写历史**的方式。

审核记录至少应包含：

```json
{
  "review_status": "approved",
  "review_reason": "来源可靠，字幕依据充分",
  "reviewer": "审核者标识",
  "reviewed_at": "2026-08-01T00:00:00Z",
  "from_status": "pending",
  "candidate_version": 3,
  "batch_id": "batch_20260801"
}
```

字段说明：

- `review_status`：当前审核状态；
- `review_reason`：审核依据；
- `reviewer`：审核者标识；
- `reviewed_at`：审核时间；
- `from_status`：变更前的状态，用于审计；
- `candidate_version`：候选记录版本号，用于并发检测，防止审核者之间互相覆盖；
- `batch_id`：所属抓取批次。

规则：

- 每次状态变化都写入审核事件日志，日志只追加、不改写历史；
- 候选主记录只保存当前状态，历史状态从审核日志追溯；
- `from_status`、`candidate_version` 和 `reviewed_at` 共同保证审核可审计、可追溯。

本项只确认审核记录的字段方向，不提前确定 `reviewer` 的具体取值方式（GitHub 账号名、自定义标识等）、版本号递增规则和审核日志的完整字段结构。

### 13.26 决策 71：PR 模板与批次过大的拆分规则

已确认采用**批次默认不设严格上限，单 PR 过大时按平台拆分**的方式。

规则：

- 一个 PR 对应一轮抓取的一个批次；
- 批次大小默认不设固定上限；
- 当单个 PR 过大（候选数量过多、diff 过大、或不便逐条审核）时，按平台拆分：

```text
batch_20260801
├── PR-A：YouTube
├── PR-B：X / 其他文字来源
└── PR-C：异常 / error / held 专项
```

- 拆分必须保持每个 PR 范围清晰，并在 PR 描述中注明抓取批次、来源平台和候选数量；
- 拆分不改变审核状态字段，每个候选仍独立审核；
- 拆分的 PR 之间不共享或覆盖候选状态，避免同一候选被两个 PR 同时修改。

本项只确认批次拆分方式，不提前确定拆分阈值、PR 描述模板和“异常 / error / held 专项 PR”是否始终单独拆分。

### 13.27 决策 72：公开数据源与公开出口的过滤规则一致

已确认采用**`hotspots.json`、RSS 与其他公开投影使用同一套过滤规则，基于单一公开数据源生成**的方式。

```text
审核通过 + AI 处理完成
  + 有效 AI 热点类型
  + 近期时间窗口
  + 标题 / 摘要 / 来源 / 发布时间齐全
  → 同一份公开数据源
```

规则：

- RSS `feed.xml` 从这份数据源生成，不额外引入不同规则；
- 不会出现“热点视图有这条，RSS 却没有”或相反的情况；
- 过滤规则集中在一处，修改时同时影响所有公开出口；
- 校验复用同一逻辑，避免规则漂移；
- 公开数据源与内部候选数据严格分离，未通过审核的记录不会进入任一公开出口。

本项只确认公开出口共用一个过滤规则，不提前确定 RSS 的具体字段映射、公开数据源的确切文件结构和校验代码的模块位置。

### 13.28 决策 73：AI 处理错误的分类、重试上限与人工指派

已确认采用**错误分为可重试 / 不可重试两类，可重试错误默认重试上限 3 次，人工指派通过标签完成**的方式。

```text
error 分类：
├── 可重试错误（temporarily_failed）
│   └── 字幕获取超时、AI 请求失败、来源暂时不可达
└── 不可重试错误（permanently_failed）
    └── 字幕不存在、字段校验失败、来源已失效
```

规则：

- **可重试**：标记 `retryable: true`，可以重新运行 AI 处理，默认重试上限 3 次；
- **不可重试**：标记 `retryable: false`，需人工处理或转为 `held`；
- **人工指派**：在 PR 或 Issue 中使用标签表达，例如：

```text
needs-manual-review
assigned-to-<审核者>
```

- 重试次数达到上限仍失败时，自动进入人工异常队列，不再自动重试；
- 每次重试都应产生独立的 AI 运行记录，保留失败原因和重试次数。

本项只确认错误分类、重试上限和指派方式，不提前确定具体错误代码清单、重试间隔策略和人工异常队列的筛选方式。

### 13.29 决策 74：热点卡片与来源平台的展示层级

已确认采用**内容类型作为主分类；平台保留在来源记录中，但不在热点卡片默认展示；点击来源后再显示平台、时间等简要来源信息**的方式。

设计规则：

- 热点卡片默认只展示热点内容本身、内容类型、摘要和必要的核验入口；
- 不在卡片默认区域展示 YouTube、X、Bilibili 等平台标签、平台数量或平台筛选器；
- 一个工具或事件在多个平台有记录时，仍聚合为同一热点实体，不重复渲染多张相同卡片；
- 平台、原始链接、发布时间、来源名称等仍必须保留在来源数据中；
- 用户点击“查看来源”或进入热点详情后，再展示简要来源信息，包括平台、时间和原始链接；
- 来源展开层可以列出多个平台来源，但不将平台信息全部前置到热点卡片；
- 该层级设计不依赖固定平台集合，未来增加新平台时不需要改动卡片结构；
- 内容类型仍是热点的主分类维度，平台不取代内容类型，也不作为默认主筛选；
- 多平台事件聚合、原生 ID 强去重和疑似同事件人工确认继续遵循决策 62。

该决策的核心是：**平台是来源核验信息，不是热点卡片的主阅读信息**，以控制默认信息密度并保持结构可扩展。
### 13.30 决策 75：热点来源详情的默认展开方式

已确认：**热点来源详情默认采用卡片内联展开；可将“内联展开 / 抽屉或弹窗”保留为未来可选设置或迭代方向，但 B16 当前默认不启用切换。**

默认交互：

- 热点卡片默认不显示平台、时间和来源列表；
- 点击“查看来源”后，在当前卡片下方内联展开来源信息；
- 一个热点可以展开多个来源，但同一时间默认只展开一个热点的来源区域；
- 来源项展示平台、来源名称、内容发布时间、数据更新时间（如有）、简短依据和原始链接；
- 不直接播放视频、不展开完整字幕、不展示完整原始正文；
- 多平台来源列在同一热点的来源区域内，不重复创建热点摘要；
- 展开/收起不改变筛选条件，不使用强制弹窗；
- 移动端沿用内联展开，来源条目自然上下排列；
- 完整来源通过明确的外链查看，并标识将离开当前页面；
- 来源缺失时显示“来源信息待补充”，不隐藏缺失状态。

可选设置的边界：

- 未来可以评估让用户选择内联、抽屉或弹窗等来源呈现方式；
- 该设置不应改变来源数据结构、审核规则或热点实体关系；
- B16 先验证内联展开的阅读连续性、信息密度和移动端适配，不为设置切换提前增加复杂状态。

### 13.31 决策 76：热点来源依据的内容与入口权重

已确认采用**平台/时间 + 核验摘要或依据片段 + 原始链接**的简要证据结构；来源入口使用低视觉权重设计，尽量不干扰热点正文阅读。

来源展开内容：

- 平台；
- 内容发布时间；
- 与热点摘要直接相关的核验摘要或依据片段；
- 数据更新时间（如有）；
- 原始来源链接。

展示规则：

- “依据摘要”来自已审核的 AI 浓缩结果或审核材料中的依据片段，不得把 AI 摘要冒充原文；
- 视频来源如有可用字幕/文字稿，可显示简短片段和时间段；
- 没有可定位依据时显示“暂无可展示的直接依据”，不得伪造；
- 不展示完整字幕、完整帖子、完整网页正文或视频播放器；
- 来源依据应与热点摘要建立可理解的对应关系；
- 与决策 54 一致，来源依据必须支持对 AI 处理结果的核验。

来源入口权重：

- 默认不使用高对比度主按钮，不在标题或摘要中插入醒目的平台标签；
- “查看来源”可设计为靠近卡片元信息区域的轻量文本入口，或低视觉权重的线性图标 + 文本入口；
- 入口与标题、摘要保持足够间距，避免打断连续阅读；
- 默认状态只显示简短的“查看来源”或来源图标，不展示来源数量、平台列表和详细时间；
- 悬停、键盘聚焦和触屏操作时，入口必须清晰可见并有明确焦点状态；
- “隐晦”只表示降低视觉优先级，不表示隐藏、不可发现或不可访问；
- 入口仍必须有可读文本或 `aria-label`，满足键盘、触屏和无障碍访问；
- 点击后在当前卡片内联展开来源依据，展开状态使用明确的文字和 `aria-expanded` 表达。

### 13.32 决策 77：热点卡片默认字段层级

已确认热点卡片默认采用**内容类型 + 管理者确认后的展示标题 + 浓缩摘要 + 时间线索 + 低视觉权重来源入口**，不在卡片默认区域展示平台、来源数量、完整评分或内部审核字段。

默认展示：

- 内容类型；
- 管理者确认后的展示标题；
- AI 浓缩摘要或公开摘要；
- 内容发布时间或日期线索；
- 低视觉权重的“查看来源”入口；
- 必要的公开状态提示，例如“资料待补充”。

来源展开后再展示平台、来源名称、该热点唯一内容发布时间、各来源记录的来源/抓取时间或数据更新时间、核验摘要/依据片段、原始链接和视频字幕时间段（如有）。

不在公开卡片展示：`review_status`、`ai_processing_status`、AI 置信度、内部错误类型、重试次数、审核者/审核时间、原始标题与 AI 展示标题建议的内部差异和完整来源内容。这些字段继续保留在内部候选数据与 PR 审核材料中。
### 13.33 决策 78：热点时间线索与排序

已确认采用**按热点内容实体的唯一内容发布时间倒序排列，并进行轻量时间分组；热度作为可选排序**的方式。

时间语义：

- 一个热点/工具内容实体只保留一个 canonical 内容发布时间；
- 多平台来源属于同一热点的来源记录，不产生多个内容发布时间；
- 列表排序和“今天/昨天/近 7 天/更早”等时间分组只依据该内容实体的唯一内容发布时间；
- 来源展开层可以展示各来源记录的来源时间、抓取时间或数据更新时间，但不能把这些时间拼接成多个内容发布时间；
- 如果无法确定内容实体的发布时间，不能用某个平台记录的时间擅自替代；该记录不得进入公开热点，内部应进入 `held` 或 `error` 路径。

展示与排序：

- B16 不把无限滚动作为必选交互，避免用户失去位置和难以回看。

## 14. B16 实施阶段安排（前三阶段）

已确认当前只安排并细化以下三个 B16 阶段；B16 原型验收在三阶段完成后进行；v1.0 真实 AI 搜索演进暂不纳入本轮细化，待 MVP 剩余功能完成后另行规划。

### 14.1 决策 101：B16 前三阶段安排

阶段名称固定为：

- **P0：全站基础**；
- **P1-A：AI 搜索与引用主线**；
- **P1-B：AI 热点浏览与详情体验**。

#### P0：全站基础

目标：建立统一 UI 结构和设计基础，不改变现有业务能力。

安排：

1. 固化暖白编辑部视觉令牌：色彩、字体角色、间距、边框、圆角、阴影和内容宽度；
2. 建立页面标题区、查询条、按钮、输入框、筛选器、标签、来源项、模态框、状态提示和内联 SVG 图标等 CSS/HTML 原语；
3. 重构桌面端分组导航和移动端分组菜单；
4. 建立宽桌面、窄桌面/平板、移动端的内容驱动响应式骨架；
5. 统一加载、空、错误、不可用、成功、选中、焦点和减少动效规则；
6. 为全站概念词识别、解释卡、键盘/触屏交互预留统一结构；
7. 保留现有单页视图切换、静态 JSON 加载和数据契约。

预期产物：统一设计令牌、基础 CSS 原语、导航/标题区/状态骨架、响应式基础，以及不改变业务行为的全站外壳迁移方案。

主要影响范围：`src/web/index.html`、`src/web/css/style.css`、`src/web/js/app.js` 的共享结构和样式部分；不新增框架、依赖或运行时后端。

依赖与风险：P0 无前置阶段；最大风险是现有单页 DOM 与 JS 选择器耦合，迁移必须保持兼容并逐步替换。

#### P1-A：AI 搜索与引用主线

目标：验证“提问 → 静态整理 → 阅读摘要 → 核验来源 → 继续行动”的核心 UI 闭环。

安排：

1. 重构单列、居中的 AI 搜索首页，只突出自然语言输入、示例问题和轻量改写提示；
2. 建立静态搜索过程的 2–3 个阶段过渡，不伪装真实检索进度；
3. 建立结果页当前问题只读条与点击编辑交互；
4. 实现桌面端左摘要/右来源、来源区域内适度粘性，以及移动端上下布局；
5. 实现内联引用与来源双向定位、短暂高亮和来源有限内联展开；
6. 按工具、场景、热点、概念分组展示少量匹配资料；
7. 接入概念索引联动：基于 glossary 名称/别名识别、悬停/聚焦预览、触屏替代和概念视图跳转；
8. 实现最近探索、空输入、无匹配、部分不可用和处理失败等静态状态；
9. 只使用固定演示数据，所有静态 AI 内容持续标注为原型，不改变现有数据能力。

预期产物：可操作的搜索主线静态 mock、引用/来源交互预览、概念索引联动预览、桌面/移动端结果布局和状态覆盖清单。

主要影响范围：共享 UI 原语、搜索入口与结果视图结构、原生 JS 的演示状态和锚点交互、glossary 读取/匹配适配；不接入真实搜索 API、模型、流式响应或会话持久化。

依赖与风险：依赖 P0；需要确认现有 glossary 的名称、别名和稳定 ID 字段是否足以支持自动识别，必要时使用原型适配层，不直接改写既有数据契约。

#### P1-B：AI 热点浏览与详情体验

目标：将已公开审核数据呈现为低干扰、可探索、可核验的编辑部式热点体验。

安排：

1. 以审核后的内容类型作为一级筛选，卡片以低权重标签显示；
2. 默认按热点实体唯一内容发布时间倒序，保留最近/热度排序；
3. 默认卡片只显示概要，悬停/键盘聚焦时显示保持模糊的次级预览；
4. 点击卡片打开热点详情对话框，不新增独立热点详情路由；
5. 对话框采用摘要—来源核验—关联资料三段式结构，来源默认收起；
6. 来源信息在对话框内联展开，入口低视觉权重，不默认展示平台；
7. 关联资料按稳定 ID 进入工具、概念或场景现有视图；
8. 区分筛选无匹配、没有公开热点、审核建设期和加载失败状态；
9. 不向公开视图暴露 `pending`、`held`、`error`、AI 置信度、重试次数或内部审核信息；
10. 保留平台、来源时间、依据片段和原始链接在来源展开层；不展示完整字幕、正文或视频播放器。

预期产物：热点低干扰卡片、模糊预览、详情对话框、来源核验和关联资料交互预览，以及公开状态覆盖清单。

主要影响范围：热点公开 JSON 的消费结构、热点视图 HTML/CSS、原生 JS 的筛选/排序/对话框/来源展开逻辑；审核流水线和公开投影规则由决策 46–73 提供数据依赖，但本阶段不建设审核后台。

依赖与风险：依赖 P0 和稳定的审核后公开 `hotspots.json`；公开字段、唯一内容发布时间、内容类型、稳定关联 ID 与来源关系必须明确，内部候选数据不能进入浏览器。

### 14.2 决策 102：B16 原型验收标准

已确认采用**主流程可走通 + 全站视图覆盖 + 状态覆盖 + 响应式覆盖 + 无障碍基线 + 能力边界诚实**六类标准：

#### 主流程可走通

- 首页 → 输入/选择示例问题 → 静态搜索阶段 → 搜索摘要 → 来源定位/展开 → 匹配资料 → 修改问题或继续探索；
- 热点列表 → 内容类型筛选 → 最近/热度排序 → 悬停/键盘聚焦模糊预览 → 热点详情对话框 → 来源依据 → 关联工具/概念/场景 → 关闭并回到原列表位置。

#### 全站视图覆盖

AI 搜索、工具库、场景、对比、推荐、AI 热点、AI 概念、关于。

#### 状态覆盖

首次加载、局部加载、空输入、无匹配、部分不可用、处理失败、工具库无筛选结果、热点筛选无匹配、没有公开热点、审核建设期、数据加载失败、对比数据暂无/不可比/不适用/过期、成功反馈、模态框开关、来源展开/收起。

#### 响应式覆盖

宽桌面、窄桌面/平板、移动端、大字号或较窄内容宽度、对比表横向关系、热点详情对话框接近全屏、来源栏粘性切换和导航收拢。

#### 无障碍基线

键盘访问搜索/筛选/模态框/来源/引用/概念词/菜单；焦点清晰且关闭后返回原控件；`aria-expanded`、`aria-live` 和对话框语义正确；模糊预览不影响屏幕阅读器清晰获取语义；状态不依赖颜色；支持 `prefers-reduced-motion`；触控目标可操作；文本背景对比度达标。

#### 能力边界诚实

静态演示明确标注；mock 摘要不称为真实 AI 回答；静态阶段不称为真实检索进度；内部审核状态不公开；不伪造来源、跑分、时间或推荐结论；未实现的 v1.0 能力不暗示为当前可用。

验收问题分为：阻塞问题（主流程、信息真实性或核心可用性）、非阻塞问题（局部视觉、文案或细节）和 v1.0 延后项。
