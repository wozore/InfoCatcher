>

>

## 1. 目标与边界

### 1.1 B16 目标

B16 是一次**全站 UI 系统重构**，围绕“AI 信息搜索”重新组织视觉、信息展示与交互，并在可审查原型中呈现未来 AI 搜索体验。

目标用户覆盖两类人群：

- **初学者**：不了解或不熟悉 AI 搜索，不知道怎样表达问题、如何判断答案可信度或使用引用；
- **知识工作者与熟练用户**：需要更高效地检索、比较、核验和追踪信息。

默认体验采用：

> **初学者友好的入口 + 面向熟练用户的渐进式深度。**

即：默认界面先提供清楚的提问引导、简明结论、关键来源与下一步操作；高级筛选、完整来源、搜索过程、比较、追踪与历史能力不应在首次视图中争夺焦点，而应按需出现。

### 1.2 产品能力路线与视觉布局路线必须分开

这两组“方向”属于不同决策维度，严禁混淆。

| 决策轴 | B16 | v1.0 | 不采用 / 限制 |
|---|---|---|---|
| **产品能力路线** | **方向 1：基于现有静态数据的 AI 信息搜索体验层**。使用现有工具、场景、热点、概念等静态数据重构体验；不虚构实时 AI 回答、联网检索、流式生成或真实会话。 | **方向 3：真实 AI 搜索产品 / 轻量 AI 工作台**。后续接入搜索 API、模型调用、流式响应、来源聚合、引用式回答、会话历史等。 | **方向 2：静态 mock AI 回答**不作为正式业务能力；仅可作为原型验证材料，且必须显著标注。 |
| **视觉与布局路线** | **极简编辑部**。完成全站 UI 系统重构，首页强调单一任务，阅读和资料页面按任务采用适当的信息密度。 | 在 B16 视觉基础上逐步吸收真实 AI 工作流所需的实时状态和高阶交互；不要求直接复制某个高密度工作台布局。 | “可信研究台”不作为全站主视觉，但其个别信息组织方式可局部借鉴。 |

### 1.3 双模式切换：B16 不做显式开关，但预留演进空间

B16 首期**不提供显式的“简洁模式 / 专业模式”切换**。默认体验固定采用“初学者友好的入口 + 面向熟练用户的渐进式深度”。

原因是：初学者不应先承担“选择模式”的额外认知负担；在模式差异尚未由真实使用验证前，双模式会增加设置、持久化状态、响应式适配、可访问性和测试复杂度。

B16 应通过渐进式展开、筛选入口、默认信息密度与默认展开状态来满足不同熟练度，而非维护两套页面或业务逻辑。后续 v1.0 如需引入模式切换，应遵循：

- 模式主要改变信息密度、信息默认展开状态和高级能力入口；
- 不复制或分叉业务逻辑；
- 先以 B16 的渐进式能力验证真实需求，再决定是否提供显式切换；
- UI 系统应保留支持密度变化的令牌和结构空间，但 B16 不接入用户偏好持久化。

### 1.4 B16 不改变的内容

- 所有现有视图都进行 UI 重构；
- 现有业务能力、静态数据能力、数据契约、筛选逻辑、对比规则、热点数据处理及详情信息含义保持不变；
- 不开发真实搜索后端、实时模型调用、真实流式生成、真实引用校验、账户系统或持久化会话；
- 不引入前端框架、UI 组件库、字体依赖或第三方图标库；
- 不将用于审查的静态 mock 表述为真实产品能力。

### 1.4 B16 原型允许做什么

可制作一条**主流程可操作、状态可演示、数据固定、逻辑有限**的静态 mock，用来验证未来 AI 搜索的界面结构：

- 输入问题、点击示例问题、触发“演示检索”；
- 用 2–3 个固定阶段演示搜索过程；
- 展示固定的搜索摘要、引用、来源、匹配资料和示例历史；
- 支持有限筛选、展开/收起、恢复示例查询、本地反馈；
- 展示空输入、无匹配、部分不可用和处理失败状态；
- 支持桌面端与移动端布局验证。

不得在 B16 mock 中模拟或暗示：任意问题动态生成答案、真实外部检索、真实引用校验、复杂多轮对话、真实账户或持久化历史、真实进度、额度与后台任务。

所有原型必须持续、清楚地标注类似：

> **静态演示 / 原型内容，不代表当前已接入真实 AI 搜索。**

## 2. 极简原则与信息密度

### 2.1 核心原则

> **极简不等于机械地减少数据或降低信息密度。极简是让信息密度与页面任务匹配，做到层级清晰、所见即所得，并尽量减少不必要的滚动和定位成本。**

因此，不得把“单列”“折叠更多内容”“减少信息”自动视为更极简的方案。

### 2.2 按任务决定布局

| 页面类别 | 主要任务 | 已确认布局原则 |
|---|---|---|
| 入口/介绍页 | 理解产品、开始提问 | 简洁聚焦一个核心任务；避免多个高权重区域同时争夺注意力。 |
| 搜索结果/引用式回答 | 阅读结论、对照并核验证据 | 可使用较高且合理的信息密度；桌面端允许摘要与来源并列，让结论—证据在同一视野中对照。 |
| 工具/场景详情 | 阅读、比较具体资料 | 按内容关系采用并列或分栏，避免不必要的纵向滚动。 |
| 热点/概念浏览 | 连续阅读、发现内容 | 编辑部式纵向内容流。 |

### 2.3 全站原则

> **设计系统统一，页面布局按任务匹配。**

统一的是色彩、字体、间距、边框、控件、状态、导航层级和无障碍规则；不统一的是栏数、卡片数量、是否单列或是否折叠。

## 3. 信息架构与导航

### 3.1 导航层级

```text
InfoCatcher
├── AI 搜索（唯一主入口）
├── 发现工具
│   ├── 工具库
│   ├── 场景
│   └── 对比
├── 了解 AI
│   ├── AI 热点
│   └── AI 概念
└── 关于
```

### 3.2 导航规则

- “AI 搜索”是唯一高优先级导航项；
- “工具库、场景、对比”直接服务于工具发现与选择，应易于访问；
- “AI 热点、AI 概念”属于浏览与学习入口，不与搜索主任务争夺同等视觉权重；
- “关于”移入用户菜单或页脚，不占据主导航空间；
- 桌面端保留简洁一级导航，但弱化非主入口；
- 移动端采用 Logo + 当前页标题 + 搜索/菜单入口，其他页面从分组菜单访问；
- 不使用默认高密度侧边栏导航。

## 4. 视觉系统

### 4.1 视觉方向：极简编辑部

整体应明亮、克制、专业、清晰，突出信息阅读、来源核验和下一步操作，不做娱乐化或过度装饰。

- 不使用大面积渐变、玻璃拟态、强装饰插画或强动效；
- 不采用“所有内容均为悬浮卡片”的仪表盘式外观；
- 视觉重点放在搜索输入、阅读结论、来源证据与下一步操作；
- 动效仅服务状态变化和展开/收起，并支持减少动效偏好。

### 4.2 色彩

采用**暖白编辑部基调 + 蓝灰交互焦点 + 低饱和状态色**：

| 角色 | 方向 |
|---|---|
| 页面背景 | 很浅暖灰米色 |
| 内容表面 | 暖白 |
| 主文字 | 深灰棕或近黑，不使用纯黑 |
| 次级文字 | 中性灰褐 |
| 主操作 | 克制深色按钮或深棕色 |
| 链接、引用、交互焦点 | 稳重蓝灰色 |
| 成功 | 低饱和绿色 |
| 警告 | 低饱和琥珀色 |
| 错误 | 低饱和红色 |

不使用大面积高饱和蓝色，避免回到 SaaS 仪表盘感；状态不得仅靠颜色区分。

### 4.3 字体

采用**阅读内容用衬线、操作和结构化信息用无衬线**的双字体层级，且 B16 不新增字体依赖。

| 字体角色 | 适用内容 |
|---|---|
| 系统中文衬线字体栈 | 首页主标题、搜索摘要正文、热点文章标题与正文、概念详情正文、场景导语等连续阅读内容。 |
| 系统无衬线字体栈 | 导航、输入框、按钮、筛选器、工具名、标签、状态、时间、来源标题、来源类型、链接、对比表和结构化数据。 |

正文不得过小；移动端应保持舒适字号和行高；英文产品名/技术名词继续使用无衬线，避免中英衬线混排不稳定。

### 4.4 容器、圆角与阴影

> **平面分隔优先，圆角和阴影只服务于交互和层级。**

- 正文：留白 + 排版 + 分隔线；
- 来源：编号 + 层级 + 分隔线；
- 搜索输入、按钮：小圆角；
- 标签/筛选器：可使用小胶囊，但数量受控；
- 工具列表：细边框列表项；仅在悬浮反馈或特定操作时使用轻微圆角；
- 浮层、菜单、抽屉：可使用较明显圆角与弱阴影；
- 禁止大面积玻璃拟态、强阴影、连续嵌套卡片和过度圆润的 SaaS 风格。

### 4.5 图标

- 系统控件使用少量、统一线性风格的**内联 SVG**；
- 不引入 Font Awesome、Material Icons 等第三方图标库；
- 搜索、返回、编辑、筛选、展开、外链、菜单、历史等采用一致 SVG 语义；
- 关键图标必须配合可见文字或 `aria-label`；
- 状态不能只用图标表达；
- 数据中原有的工具品牌 Emoji 可作为内容标识有限保留，不得作为系统控件主图标。

## 5. 轻量 UI 系统与技术边界

### 5.1 已确认技术现状

前端为零依赖的原生单页应用：

- 原生 HTML、CSS、浏览器原生 JavaScript；
- 无 React、Vue、Angular、Svelte、Tailwind、Bootstrap 等框架或 UI 库；
- 无 `package.json`、锁文件、TypeScript、Vite、Next.js 等前端构建配置；
- 单页通过 `.view.active` 与 `switchView()` 切换视图，无前端路由库；
- 浏览器用 `fetch()` 读取静态 JSON，不直接调用平台 API；
- Node.js 20 用于采集、构建和校验脚本。

关键前端文件：

- [src/web/index.html](../../src/web/index.html)
- [src/web/css/style.css](../../src/web/css/style.css)
- [src/web/js/app.js](../../src/web/js/app.js)

### 5.2 UI 系统实现策略

建立**设计令牌 + CSS 原语 + HTML 结构约定**的轻量 UI 系统，不引入框架或完整组件运行时。

1. **设计令牌**：颜色、字体角色、字号、行高、间距、边框、圆角、阴影、内容宽度、响应式断点、焦点与状态样式。
2. **CSS 原语**：页面容器、页面标题、查询条、按钮、筛选器、来源项、状态提示、折叠区、模态层、对比表、内容列表等。
3. **HTML 结构约定**：各视图按需保持差异，但共享导航、标题区、操作控件、信息状态、来源/更新时间、空错误状态与移动端收拢规则。

明确不做：引入 React/Vue、复杂模板编译系统、完整组件运行时、为组件化重写数据加载与业务函数、修改现有数据契约。

## 6. 首页与搜索入口

### 6.1 首页结构

采用**单列、居中的编辑部式首页**，首屏只承担“提出问题”这一主任务：

```text
AI 信息搜索
把你想了解的事，说清楚一点。

[ 用自然语言描述你的问题……                         ]
                                                [搜索]

你可以试试：
[写论文与查资料] [比较编程工具] [了解近期 AI 热点]

最近探索 / 从这里继续
（首屏下方或可折叠，低视觉权重）
```

规则：

- 不在首屏并列展示工具卡片、热点流或复杂筛选；
- 示例问题帮助初学者起步，但不得制造过多选择；
- 最近探索仅用于回访，不成为首页主视觉；
- 工具、场景、热点、概念通过导航或搜索结果进入。

### 6.2 查询输入

保持**单一自然语言输入框**，不拆分成多个结构化字段。

- 占位提示描述“工具、场景或问题”；
- 输入框下可提供少量示例问题；
- 用户输入过宽泛时，提供 2–3 条轻量改写建议，如补充任务、使用场景、限制条件、中文支持、免费层或引用需求；
- 高级筛选只出现在结果页，不阻塞首次搜索；
- 熟练用户应能直接输入、直接搜索。

## 7. 搜索过程、结果页与查询编辑

### 7.1 搜索过程

不设置独立进度页。用户点击搜索后，在结果内容区域显示短暂、固定的静态演示过渡，例如：

```text
正在整理你的问题
匹配已收录资料
准备示例摘要
```

规则：

- 仅 2–3 个阶段；
- 不显示百分比、预计剩余时间或虚假实时进度；
- 过渡后直接进入结果布局；
- 明确标注为静态演示流程；
- 支持减少动效；
- 重复提交相同示例时不强制重复长等待；
- 未支持的示例查询进入“暂无对应示例”，不得伪造回答；
- v1.0 可在同一位置升级为真实检索/流式状态。

### 7.2 结果页顶端与查询编辑

结果页默认显示**当前问题的只读状态**，点击“修改问题”后才展开编辑；不持续展示首页级别的大搜索框。

```text
← 返回 AI 搜索

当前查询
适合中文写论文、查资料的 AI 工具有哪些？   [修改问题]

────────────────────────

搜索摘要                     关键来源
```

- 点击“修改问题”后，将当前问题置入输入框；
- 可编辑、提交、取消；
- Enter 可触发新的静态演示查询；
- 不在结果页默认显示首页的示例问题组；
- 移动端同一逻辑纵向排列；
- 未来 v1.0 可自然升级为真实再次检索入口。

## 8. 搜索摘要、来源与引用

### 8.1 B16 的真实性表达

B16 不应直接把固定内容命名为“AI 回答”。正式界面应使用：

- **搜索摘要**，或
- **信息整理**。

并显著标注：

> 静态演示 · 不代表实时联网检索或 AI 生成结果。

这允许审查未来 AI 搜索结果的结构，但不会把静态内容误导为模型推理、实时检索或动态证据链。v1.0 接入真实模型后，可在保留布局的前提下升级为“AI 综合回答”。

### 8.2 桌面端结果布局

采用已确认的**方案 2：左摘要 + 右来源**：

```text
┌──────────────────────────────┬─────────────────┐
│ 搜索摘要 / 信息整理           │ 关键来源        │
│ 结论、解释、内联引用 [1][2]   │ [1] 来源标题    │
│ 下一步建议                    │ [2] 来源标题    │
│                               │ [3] 来源标题    │
└──────────────────────────────┴─────────────────┘
```

此处允许合理的高信息密度：左侧负责连续阅读，右侧负责即时证据核验，减少频繁鼠标滚轮和“结论—来源”之间的定位成本。

右侧来源栏采用**仅在结果区域内适度粘性定位**：

- 进入结果区域后保持可见，到结果区域底部时停止；
- 不固定在整页视口，不遮挡导航、查询条或页脚；
- 不创建来源栏内部的复杂第二滚动容器；
- 默认显示前 2–3 条关键来源，更多来源经“查看全部来源”展开；
- 窄屏或大字号环境自动退化为普通双栏或上下布局。

### 8.3 移动端结果布局

移动端不强行压缩为双栏，采用自然上下流：

```text
搜索摘要
结论与解释……
[查看关键来源 3 条]

关键来源
[1] 来源标题
    来源类型 · 更新时间
    摘要
    查看资料 →

[2] …
[3] …

[返回摘要]
```

- 摘要下提供“查看关键来源”快捷锚点；
- 来源自然置于摘要之后；
- 提供“返回摘要”；
- 不使用底部固定来源抽屉或固定粘性来源栏，避免遮挡正文和增加原生 JS 交互复杂度。

### 8.4 引用和来源信息

采用**正文内联引用 + 桌面右侧关键来源 / 移动端下方关键来源**。

来源项至少包含：

- 编号；
- 标题；
- 来源类型；
- 更新时间；
- 一行摘要；
- 可追溯入口（资料详情或外链）。

规则：

- 默认仅显示直接关联摘要的 2–3 条来源；
- 更多来源折叠于“查看全部来源”；
- 来源信息不完整时明确写“更新时间未知”或“来源信息待补充”，不得默认伪装为最新；
- “静态演示”标识和“来源真实性/更新时间”标识必须分开表达；
- 不把每条来源包装为厚重卡片，优先编号和分隔线。

### 8.5 引用联动（尚未正式确认）

第 29 项“摘要引用与来源的双向定位、短暂高亮、无需弹窗”仍在待用户确认状态，**不属于本决策包的已确认范围**。因此，本文已确认的范围仅包括：正文内联编号引用与对应来源在桌面/移动端的布局关系；不包含点击后如何定位、高亮、聚焦或跳转的具体交互规则。后续确认后再补充到本节。

## 9. 匹配内容、其他视图与布局分配

### 9.1 结果页默认阅读顺序

虽然桌面端摘要与关键来源并列，但整体阅读层级保持：

1. 当前问题；
2. 搜索摘要/信息整理；
3. 关键来源（桌面并列、移动端随后）；
4. 匹配内容（工具、场景、热点、概念）；
5. 继续探索与历史。

工具、场景、热点、概念等匹配内容默认显示少量条目，并提供“展开全部匹配内容”。筛选器仅在匹配条目较多时出现；搜索步骤默认降低权重或收起；历史不应使用高权重的固定侧栏。

### 9.2 各视图的布局方向

| 视图 | 主要任务 | 推荐布局 |
|---|---|---|
| AI 搜索首页 | 开始提问 | 单列居中 |
| 搜索结果 | 阅读摘要、核验证据 | 桌面左摘要 + 右来源；移动上下布局 |
| 工具库 | 浏览、筛选、发现工具 | 低密度列表或双列卡片 |
| 场景 | 按任务进入工具集合 | 场景导语 + 工具列表 |
| 对比 | 横向比较工具 | 桌面端对比表；移动端逐项对比卡 |
| AI 热点 | 连续阅读和发现 | 编辑部式内容流，按日期/主题分组 |
| AI 概念 | 查阅定义、建立理解 | 目录/索引 + 文章式详情 |
| 关于 | 理解产品定位 | 单列叙事页 |

这些是已确认的布局原则，并不增加现有页面业务能力。

## 10. 状态与反馈

### 10.1 异常状态的通用结构

所有异常状态采用：

> **发生了什么 + 影响范围 + 下一步操作。**

不得使用单一“没有结果”覆盖所有情形，不得用乐观文案掩盖资料缺失，也不得生成没有依据的摘要。

| 状态 | 表达重点 | 可提供操作 |
|---|---|---|
| 空输入 | 请先描述想了解的内容，并给出示例。 | 输入/选择示例问题 |
| 无匹配 | 当前静态资料没有覆盖该问题。 | 修改问题、查看示例问题 |
| 部分资料不可用 | 已保留可用内容；缺失资料不等于没有相关信息。 | 查看可用结果、稍后重试 |
| 处理失败 | 演示整理未完成；不会生成无依据摘要。 | 重新尝试、返回搜索 |

- 静态 mock 的失败不可伪装成真实搜索服务失败；
- 状态颜色仅辅助，文字和操作必须完整；
- 为 v1.0 预留超时、来源缺失和服务降级等状态映射。

### 10.2 反馈

原型可以提供“有帮助 / 没有帮助”的本地状态，用于验证位置和交互；B16 不假定存在真实反馈持久化能力。

## 11. 无障碍与响应式基线

B16 以 **WCAG 2.2 AA** 为设计目标基线；不另开独立无障碍专项，但全部新增和重构组件必须满足以下底线：

- 使用语义 HTML：`header`、`nav`、`main`、`article`、`aside`、`button`、`form` 等；
- 图标按钮提供可读 `aria-label`；
- 键盘可访问搜索、查询编辑、引用、来源、筛选和折叠控件；
- 焦点状态清晰可见，不仅通过颜色或阴影表达；
- 引用 `[1]` 与来源存在可理解的链接关系；
- 来源高亮不只使用颜色；
- 折叠区域具备正确展开状态和关联内容；
- 加载/错误状态使用文本或 `aria-live` 传达；
- 支持 `prefers-reduced-motion`；
- 文字/背景对比度达标；
- 移动端触控目标保持足够可操作尺寸；
- 不以 Emoji 代替关键图标或状态。

不在 B16 首期承诺：所有历史无障碍缺陷的完整清零、复杂专用屏幕阅读器导航模式、独立无障碍设置中心。
