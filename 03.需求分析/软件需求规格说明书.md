## 0. 文档说明

本说明书是 InfoCatcher 项目的需求规格说明（SRS），回答软件生命周期表中的问题：

> **③ 需求分析 —— 目标系统必须做什么？**

内容来源：可行性研究阶段已识别的"核心功能需求方向""非功能需求方向""范围边界""需求来源追踪""MVP 功能定义"。本阶段将这些**方向**转化为正式的**需求条目**，并补充需求建模与需求验证。

> 与可行性研究的分工：可行性研究判断"该不该做、哪种方案行得通"；需求分析定义"做出来的系统必须具备什么"。可行性报告中的方案选型、风险评估、经济/进度可行性不在此重复。

## 2. 功能需求（FR）

> 编号规则：FR-<模块>-<序号>。优先级 P0=必须(MVP)，P1=应纳入，P2=后续。
> `Dx`：[[开发计划.md]] `假设x`：[[AI信息获取软件开发.md]] `Cx`:[[可行性研究报告.md]]

### 2.1 工具信息库（FR-CORE）

| 编号         | 需求                                                                     | 优先级 | 验证假设            |
| ---------- | ---------------------------------------------------------------------- | :-: | --------------- |
| FR-CORE-01 | 系统应提供 AI 工具信息库，每条记录至少包含：名称、厂商、分类、功能描述、价格/权益、免费额度、访问门槛、中文支持、擅长场景、最后更新日期 | P0  | 假设1（用户不知道有哪些工具） |
| FR-CORE-02 | 每个工具应标注适用场景标签（写论文/写代码/做PPT/写周报/翻译等）                                    | P0  | 假设4（工具-场景映射缺失）  |
| FR-CORE-03 | 每条记录应显示"最后更新日期"以缓解"信息过时"信任问题                                           | P0  | 假设15            |
| FR-CORE-04 | 初始内容覆盖 ≥ 20 个主流 AI 工具（含国产）                                             | P0  | C2 条件           |
| FR-CORE-05 | 信息应支持众包纠错（用户提交 → 审核入库）                                                 | P1  | 信息时效性风险缓解       |
| FR-CORE-06 | 推荐结果应优先落到可实际使用的具体模型、产品版本、变体或套餐；泛化品牌/入口只能作为集合，并展示已核实的当前子项 | P1 | 假设4、假设8 |
| FR-CORE-07 | 高频变化的模型、API价格、套餐与上下文信息必须保留官方优先的来源链接和查询时间；缺失、冲突或检索失败时应明确降级，不得推测补全 | P1 | 假设15、可信评测 |
| FR-CORE-08 | LLM 模型应按权威资料展示缓存命中输入、缓存未命中输入和输出的每百万 tokens 价格，并标明币种、计价条件和 1M 上下文支持状态；非 LLM 不强制展示 | P1 | 付费焦虑、信息透明 |
| FR-CORE-09 | 集合入口应以厂商总览呈现精简说明与可区分优点/限制的特点；模型与工具采用可追溯层级导航，叶节点数据面板仅替换模型与工具区域 | P1 | 信息过载、可信评测 |

### 2.5 AI 热点与动态（FR-NEWS）

> 质量判断口径见 [AI热点质量评估标准.md](AI热点质量评估标准.md)。S2 采用“GitHub Actions 构建时采集 → 静态 JSON → GitHub Pages 展示”，不引入运行时后端。

| 编号 | 需求 | 优先级 | 验证假设 |
|------|------|:---:|------|
| FR-NEWS-01 | 系统应聚合 YouTube、X 的自动采集内容，并支持通过人工精选补充 Bilibili 标准化 AI 内容，展示标题、来源、作者、发布时间、内容类型、标签、评分分项与溯源状态 | P0 | 信息分散、更新快 |
| FR-NEWS-02 | 系统应通过 Node.js 构建脚本和 GitHub Actions 每日生成静态热点 JSON，并由 GitHub Pages 展示；凭据不得进入前端或仓库 | P0 | 时效性、密钥安全 |
| FR-NEWS-03 | 来源应支持多标签；B站视频、动态和专栏均可作为热点内容，且来源覆盖、缺失字段、人工收录和暂停自动采集状态应显式记录 | P0 | 来源多样性、避免误判沉默 |
| FR-NEWS-04 | 系统应区分重复观察、转载、评论与独立解读；同主题多观点应并列保留，不得简单合并为单一结论 | P1 | 软文多、信息重复 |
| FR-NEWS-05 | 内容与来源评估应保存评分维度、规则、证据、置信度、商业披露和异常判定依据；证据不足时不得作负面定性 | P1 | 可信评测 |
| FR-NEWS-06 | 系统应采用 UTC 固定天数半开时间层 `[0,1)`、`[1,7)`、`[7,30)`、`[30,90)`、`[90,270)`；当前层全部适用自动来源到达终态后才进入下一层，进度应可恢复；B站人工条目不参与自动历史回溯 | P1 | 批量采集完整性 |
| FR-NEWS-07 | YouTube 进入下一层前应检查平台独立额度；B站请求额度仅适用于显式 RSSHub 诊断，默认构建不得因人工精选消耗B站网络额度 | P1 | 成本与平台限制 |
| FR-NEWS-08 | 系统应为每个检测过的视频建立持久记录，以 `platform:native_id` 为主键，并区分发现、详情、分析、过滤、重复、失败、额度暂停和等待授权状态 | P1 | 防重与审计 |
| FR-NEWS-09 | 低频高质量来源在近期样本不足时可按配置回溯第3/4层；低频不得降低长期质量，停止条件、页数、条数和最早日期应可配置 | P1 | 低频来源保护 |
| FR-NEWS-10 | 已授权五层均无未记录新视频时，系统应生成待确认任务；用户可继续到指定日期、持续至首个新视频、跳过或停止，所有决定和安全上限应持久化 | P1 | 无界回溯防护 |
| FR-NEWS-11 | 系统应提供经过校验的单条/批量来源管理入口，防止同平台账号重复添加，且无需修改采集核心代码 | P1 | 来源扩展性 |

### 2.6 暂不纳入 MVP 的功能（Out of Scope for MVP）

| 功能 | 原因 |
|------|------|
| 用户注册/登录系统 | MVP 用 localStorage 即可，无强账户需求 |
| 用户评价/UGC 社区 | 冷启动风险高，先以 GitHub Issues 作轻量反馈 |
| AI 自动事实裁决/商单定性 | 首版采用规则 + 证据 + 置信度；模型辅助须待样本和评估就绪 |
| 运行时 Serverless 采集、数据库/KV、实时推送 | S2 只做 GitHub Actions 构建时采集和静态 JSON；完整后端留至环 C |

## 4. 范围边界（In/Out Scope）

**In Scope：**
- AI 工具信息聚合与展示
- 多维度场景化对比
- 价格与权益透明化对比
- 场景化推荐（行为推断，非硬标签）

**Out of Scope（明确不做）：**
- AI 工具的代理销售 / 分销
- 自有 AI 模型的训练
- 企业内部 AI 部署咨询
- LLM/Agent 类 API 的高频调用（预算约束，见可行性 Q2）
